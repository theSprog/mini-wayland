# 文档结构与写作规则

这一份定的是**文档自己的规矩**。之前的文档是边做边写累积的，
同一个事实在三四个地方各有一份、后面推翻了前面但前面还留着 ——
下面的分类和三条规则就是为了让这种情况不再发生。

---

## 一、按"生命周期"分类，不按"什么时候写的"分类

一份文档该怎么维护，取决于它记的是哪一类东西。混在一起就没法维护。

| 文件 | 记什么 | 怎么维护 |
| --- | --- | --- |
| `env.md` | 目标环境**当前**为真的事实 | **覆盖写**。被推翻的说法直接删，不留历史版本 |
| `open-questions.md` | 未解决问题、待验证项、`TODO(...)` 索引 | 条目关闭即**删除**，结论去向写进 `env.md` |
| `env-log/` | 实测原始输出，带日期 | **只增不改**。已归档的不再编辑 |
| `stepN-design.md` | 该 step 的**最终**设计与取舍 | step 收尾时**重写成终稿**，不是过程日志 |
| `lessons.md` | 跨 step 的方法论教训 | 只增。与具体 step 解耦 |
| `vendor-kmd-notes.md` | 厂商 KMD 读码结论 | 驱动更新时改 |
| `internal-lib.md` | `include/internal/` 的本地改动 | 改动时改 |
| `../learning-notes/NN-*.md` | 对外技术长文 | 发布后基本不动 |

## 二、三条规则

### 规则 1：一个事实只有一个家

环境事实的唯一信源是 `env.md`。step 文档、代码注释、`learning-notes`
一律**引用**它，不复制。

判据很简单：如果某个数字（节点名、pitch 对齐值、modifier 个数、
哪个节点跑 GL）在两份文档里各写了一遍，那它迟早会有两个不同的值，
而读的人无从判断哪个新。整理前 "GL 宿主是 renderD130" 这一条
在三个文件里各有一份，"syncobj 要问渲染节点" 也是三份。

### 规则 2：step 设计文档在收尾时重写，不追加

整理前的 `step2-design.md` 结构是：

```
§1-§6   设计阶段的判断
§7      "实现阶段的修正 …… 冲突时以本节为准"
```

这等于告诉读者**前 400 行不可信**，而且不指明哪几条被推翻了。
过程中的错误判断只有两种去处：

- 有教训价值 → 写进 `lessons.md`，**保留错误本身**，因为教训在错误里
- 没有教训价值 → 删掉

step 收尾时正文里只留最终成立的设计。

### 规则 3：状态词只有三个

`已确认` / `未解决` / `待验证`。每条带**日期**和**验证命令**。

整理前散落的 "待确认 / 未解决 / 已确认 / 未复现 / 已关闭 / 仍待确认"
六种说法混用，且没有一处能一次看全 —— 现在全部收进 `open-questions.md`。

## 四、写作约定

- 中文正文，**代码里的字符串一律英文**（这条是项目硬约束，文档里引用时保持原样）
- 每个结论要能回答"**怎么验的**"：命令、demo 名、或 `env-log/` 里的哪条
- 硬件观察进 `docs/`，不进 `include/` 和 `src/`（项目硬约束 10）
- 推论与实测要分开写。`env.md` 只放实测；从源码推出来但没实测的进
  `vendor-kmd-notes.md`，并标注"推论"
