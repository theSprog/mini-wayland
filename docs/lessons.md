# 方法论教训

从 step 设计文档里抽出来的、**与具体 step 无关**的部分。
这些是这个项目真正的产出之一：错误本身有价值，所以保留犯错的经过，
不要改写成"正确做法"。

只增不改。每条注明出处 step 与日期。

---

## L-1　返回码只证明接口被接受了，不证明数据到了

**Step 2，2026-09-03。** RenderDevice 方向的探测报了 PASS，60 fps 一帧不掉，
ioctl 完美配平，**屏幕全黑**。

这条链路上四层校验：

| 层 | 校验的东西 |
| --- | --- |
| `PRIME_FD_TO_HANDLE` | 内核建出了 GEM object |
| `addfb2` | format / stride / size 自洽 |
| `ATOMIC_TEST_ONLY` | plane 约束 |
| page flip event | CRTC 翻页了 |

**没有一层碰过像素。**

推论：**跨越信任边界的每一层，都要有一个独立于返回码的内容判据。**
能力探测如果只看返回码，就会在最需要它说实话的时候骗人。

## L-2　多个通道读回同一批采样点，判据是通道之间是否一致

**Step 2，2026-09-03。** L-1 那次黑屏期间，`glReadPixels` 和分配器给的
CPU 映射两列**都显示正确** —— 它们各自看到的是自己那一侧的视角，都在说谎。
只有第三列（直接 `mmap(dmabuf_fd)`）能拆穿。

所以 `--verify` 的判据不是任何单列的绝对值，是**列与列是否一致**。
读回失败也不退出，照常上屏 —— 屏幕上看到的和表格对照才有信息量。

推论：自检要设计成"至少三个视角，且它们的失败方式互不相关"。
两个视角只能告诉你有分歧，不能告诉你谁错。

## L-3　去问的时候要假设被问的一方可能会崩

**Step 2，2026-08-31。** 探测器要把一堆来路不明的 UMD 依次加载进本进程，
其中一个（视频编解码节点的驱动）直接段错误带走了整个工具，
导致**唯一真正能用的那个节点根本没被测到**。

进程内防不住：它崩在第三方 `.so` 里，没有返回值可检查，`expected` 接不住。
改成每个候选 `fork()` 一个子进程，崩了就记一条 `crashed` 继续下一个 ——
**这条记录本身就是结论**，一个会崩的 UMD 就是不能用的 UMD。

两个容易做错的细节：子进程要**自己 open** 设备节点（共用父进程的 fd，
子进程崩在建完 fb 之后会把内核对象留在父进程的 fd 上）；
退出用 `_exit` 不用 `exit`（后者 flush 继承来的 stdio 缓冲，日志打两遍）。

后续补充：那次"用户态段错误"其实是**内核 `BUG_ON`**，
从 `waitpid` 看两者一模一样。所以探测报告要提醒去看 dmesg ——
那是唯一能分开这两种情况的地方。子进程被隔离了，内核没有。

## L-4　一条判据在某些输入下会退化成恒真

**Step 2，2026-08-31。** GL 宿主节点的排名里有一项
"分配出的 bo 能被显示设备接受"。当候选节点**就是显示设备本身**时，
这一项恒真 —— 它不是能力，是同义反复。结果一条空结论让显示节点
压过了真正的渲染节点。**排名没错，判据错了。**

推论：探测器里每一条判据都该问一遍"**有没有哪种输入让它白送分**"。
这个错误的形状值得记：一个判据退化成恒真的时候，
恰好也是它最不该起作用的时候。

## L-5　配对关系不是能力判断，而且用它选设备的失败方式是静默的

**Step 2，2026-08-31。本步最贵的一个教训。**

`drmGetDevice2` 给出的"与这个 KMS 节点同属一个物理设备的 render node"
是**元数据关系**。照它选渲染设备，选中了一个没有对应 UMD 的节点，
Mesa **不报错**，退到软件光栅化。后果是一连串看起来合理但全错的结论：

- "渲染侧分配路径 DEGRD" —— 其实是软件后端分配不出可扫描输出的内存
- "这块板子没有硬件 GL" —— 有，跑在另一个节点上
- "渲染节点支持 timeline syncobj" —— 问错了节点，真正的那个报 0

三条结论、三个方向的设计决定，全部建立在一次错误的节点选择上，
而**每一步都没有任何东西报错**。

修法：对每个候选真的建一次 GBM + EGL + 渲染目标，按实测能力排名。
配对函数保留，但注释里写明它是元数据关系、不是能力判断。

## L-6　有些差异探测不出来，只能靠一个明确标注为启发式的提示

**Step 2。** 软件光栅化能**通过全部能力判据**，只是慢一百倍。
单靠能力分不出来，只能匹配几个众所周知的软件后备实现的名字。

这不是厂商判断（那些名字在任何机器上都可能出现），但它确实是启发式。
所以：只用于多个节点能力相当时打破平局，**一定打印出来让人复核，
主逻辑不读它**。

这是"运行时探测优于编译期假设"的补充：探不出来的时候，
把判断权明确交回给人，比偷偷猜一个好。

## L-7　降级路径是否安全，取决于降级前后的语义差

**Step 2，2026-08-31。** `add_with_fallback()` 原本的行为是
`AddFB2WithModifiers` 被拒就丢掉 modifier 重试。丢掉 modifier
意味着让驱动自己推断排布：

- 内存实际是线性的 → 推断出线性 → 结果正确
- 内存实际是 tiling / 压缩的 → 按线性去读 → **屏幕上是垃圾，而 addfb2 返回成功**

后者是这个项目最不能容忍的那类错误：**静默的错误结果**。
比响亮的失败糟糕得多，因为没有任何东西提示你去看这里。

`LINEAR → 无 modifier` 的语义差接近零；`某个 tiling → 无 modifier`
的语义差是"完全不同的内存解释"。**把它们写成同一段代码是一个分类错误。**

写降级路径时逐个问：**降级之后结果还正确吗？** 不正确就该失败，不该降级。

## L-8　一个恒定的偏差比没有计数更糟

**Step 2，2026-08-31。** 退出时报"还有 2 次提交在飞"，实际只有 1 次。
多出来的是 modeset：它让第一块 buffer 开始被扫描（所以确实要轮转），
但**不带 `PAGE_FLIP_EVENT`**，内核永远不会为它投递完成事件。
而计数把"轮转"和"等一个事件回来"绑在了一起，于是从第一帧起永久性地多 1。

"退出时还有 2 次在飞"是一句完全合理的话，不去手工算一遍不会有人怀疑它。
**这类计数器的正确性只能靠"手算一遍应该是多少"来验证。**

## L-9　"把 A 和 B 绑一起，因为分开没有用途"只在你已经枚举完所有用途时才成立

**Step 2，2026-08-30。** `DumbBuffer::create()` 原本把
"分配 + mmap + addfb2"绑成一步，理由是"单独持有一个没有 fb 的 dumb buffer
在本项目里没有用途"。

Step 2 自己的测试就撞上了：跨设备用例要在一个**没有 KMS 的节点**上分配，
捆绑的 addfb2 让它在分配阶段失败，报错还指向 `drmModeAddFB2 ... EINVAL`,
在板上表现为"跨设备导入不可行"——而那一步根本没被执行到。
Step 3 起 client 进程不是 master、也不该建 fb，是第二个反例。

**在一个还没写完的项目里，你没有枚举完所有用途。**
默认拆开，需要时提供一个组合的便捷函数，代价小得多。

## L-10　抄两份的直接后果是其中一份出了 bug 另一份照样绿

**Step 2。** 原计划两个 demo（CPU 绘制 / GL 绘制），差别只有"谁往 buffer
里写像素"这一段，而 modeset、帧循环、事件处理、退出清理、ioctl 记账
是逐字相同的几百行。合并成 `--draw cpu|gl` 一个开关。

而你会相信绿的那份。

（同一条理由决定了 Step 3 的 client/server 用单个二进制加 `--role`：
线格式的编解码两侧必须是同一份代码。）

## L-11　配平表的准入判据

**Step 1。** 把"DRM master"放进 create/destroy 配平表，报出
`acquired=0 released=1`。根因是建模错了：打开一个没人占用的节点会
**隐式成为 master**，不产生任何 ioctl；而释放照常调 `drmDropMaster`。

master 不是分配出来的内核对象，是一个**模式**：获取有两种方式
（隐式继承 / 显式 ioctl），释放只有一种。

准入判据：**有且只有一种获取方式、有且只有一种释放方式、两者一一对应。**

顺带：`acquired - released` 用 `uint64_t` 相减，负数下溢成天文数字。
而"释放多于获取"本身同样值得警惕（double free 或计数逻辑错），
不该被下溢掩盖 —— 两个方向分别报告。

## L-12　误报也有价值

**Step 1。** 泄漏报告第一次跑出假阳性：统计函数在 `run()` 内部调用，
而被统计的对象都是 `run()` 的局部变量，此时还没轮到析构。

最初的绕法是加一个内层作用域提前销毁一部分对象 ——
**那本身就是设计走偏的信号**。正确做法是把统计挪到 `main()`。

误报逼着把"资源到底什么时候真正释放"想清楚了一遍。

## L-13　跨函数的错误域假设

**Step 1。** `add_with_fallback()` 用 `errno_of(first.error())` 决定要不要降级，
但 `add()` 返回的是 **drm 域**错误，`errno_of` 恒返回 0 ——
降级逻辑写了等于没写。

两个函数分别都对，错在跨函数的错误域假设上，光看代码很难发现。
**驱动分支判断的原始 errno 要从 ioctl 包装那一层直接取，不要跨域推断。**

## L-14　明知故犯要写下来，并标好什么时候删

**Step 2。** `finish_rendering()` 现在就是 `glFinish()` —— CPU 阻塞等 GPU，
正是现代显示管线要消灭的东西。标了 `TODO(step6)`。

不依赖隐式同步（dmabuf reservation object 上的 fence）的理由：
**不保证存在**（挂不挂由驱动决定，跨设备路径尤其没谱），
且**不可观测**（成立时和 `glFinish` 效果一样，不成立时是偶发花屏）。
分不出这两种情况的机制，不能作为正确性依据。

**蒙对了比错了更糟**：错了会被立刻发现，蒙对了会在换一块板子时突然坏掉。

Step 6 删掉这一行时，帧率的变化就是显式同步带来的收益，可以直接量。

## L-15　"给你一块可写内存"和"写进去的东西会到那块 buffer 里"是两件事

**Step 3，2026-09-04。** 渲染侧分配路径：分配、导出、PRIME 导入、addfb2、
atomic commit **全部成功**，60 fps 一帧不掉，ioctl 完美配平，**屏幕全黑**。
与 L-1 一模一样的形状，但根因在用户态，而且是我自己写的那一行。

client 在启动时 `gbm_bo_map()` 拿到映射，之后每帧往里写，从不 `unmap`。
而 `gbm_bo_map()` **不保证给的是 bo 自己的内存** —— 实现可以给一块
staging buffer，真正的拷回发生在 `gbm_bo_unmap()`。于是每一帧都写进了
一块永远不会被送回去的影子内存。

三点值得记住：

1. **这个假设在 Step 2 就被写下来过。** `--unmap-each-frame` 那个开关的注释
   写的是"如果 unmap 之后画面才对，说明上面那次写落在了 staging buffer 里"。
   假设记下来了，但没有在新代码里被检查 —— **写下来的假设不会自己生效。**
2. **同一条链路上换一种画法就换了一套语义。** dumb 的 `mmap` 给的是
   GEM 对象背后那块内存，映射一次可以一直用；GBM 的 map 不是。
   两者在类型上长得一样（都是一段可写的 `span<uint8_t>`），
   于是"映射一次反复用"这个在一条路径上正确的写法，被原样搬到了另一条上。
3. **这一次没有任何自动判据能抓住它。** L2 要 `mmap(dmabuf)`，
   而这条路径上导出方拒绝 CPU 映射（EACCES）。所以它只能靠眼睛发现 ——
   这正是"writeback 是 Step 5 的必需品"的第一个实证。

## L-16　故障注入自己也会注入错

**Step 3，2026-09-04。** 九个故障用例里有三个是错的，而且三种错法不一样：

- **`tiny-buffer` 从来没被实现过。** 枚举里有、命令行里有、
  注入函数里落到 `default: break`。于是它发出一条完全合法的请求，
  server 收下、什么都不说，两边一起干等。
  **一个没被发现的故障，表现成了一个挂住的程序** —— 而"挂住"会把人
  引去查测试框架，不是查判据。
- **`extra-fd` 打错了目标。** 它和 `missing-fd` 共用了"把 num_planes 改成 2"
  这一行，可多发一个 fd 之后数量反而对上了，拒绝理由变成"plane 1 stride 为零"。
  拒是拒了，但测的不是想测的那条。**一个用例通过了，不等于它测了你以为的东西。**
- **`bad-modifier` 真的没被发现**，但那是被测方的问题，见 L-17。

三条推论：

1. 故障注入的用例表必须有一个"**未被发现**"的显式结果，不能只有"被拒绝"
   和"崩了"。沉默是一种结果，而且是最重要的那种。
2. 所有等待都要有超时。没有超时的等待会把测试失败伪装成工具故障。
3. 每个用例都要人工核对**拒绝理由是不是你想要的那条** ——
   只看退出码，上面第二种错法永远不会暴露。

## L-17　内核不一定替你校验跨信任边界进来的字段

**Step 3，2026-09-04。** client 声明了一个纯属编造的私有 modifier
（`0x00ff0000deadbeef`），server 原样传给 `drmModeAddFB2WithModifiers`，
**内核收下了**。fb 建成，上屏正常 —— 因为这块内存本来就是线性的，
而这版驱动的 addfb2 根本没看 modifier 字段。

危险的不是这一次的结果（碰巧正确），是这条推理：
"格式和 modifier 不合法的话 addfb2 会拒绝"。**它是一个假设，不是保证**，
而且换一个 modifier 值就会变成"屏幕上一堆垃圾且返回成功"。

正确做法：**合成器自己比对**。比什么是清楚的 —— 就是它自己在
`HELLO_ACK`（Step 4 起是 `linux-dmabuf-feedback`）里公告出去的那份集合。
公告过什么就接受什么，这条在协议层面本来就该成立。

顺带一条边界：这个判据只对**直出**成立。有 GPU 合成回退之后，
一个 plane 不接受的 modifier 未必要拒绝 —— 那时判据变成"渲染器能不能
采样它"，而不是"plane 能不能扫描它"。同一个字段，两层不同的判据。

## L-18　声明顺序即析构逆序，这条会在"持有者"和"被持有者"之间反复咬人

**Step 3，2026-09-04。** client 把设备 fd 声明在了 buffer 容器之后，
于是退出时 fd 先关，`DumbBuffer` 的析构再对着一个已关闭的 fd 下
`DESTROY_DUMB`，报出三行"GEM object leaked"。

两点：

- **泄漏是假的，记账是真错的。** 内核在 `close()` 时就把该 drm_file 上的
  GEM 对象全回收了。但配平表说"acquired=3 released=0"，
  而配平表的价值恰恰在于你**相信**它。一个会假报的配平表比没有更糟。
- 这个坑在 step2 的 demo 里有整段注释（"声明顺序即析构逆序，这里必须小心"），
  **写在别处的注释不会保护新写的代码**。凡是"持有者 + 一堆被持有者"的
  组合，声明顺序都要当成接口的一部分来审。

## L-19　把约束打印出来又不去用它，比没打印更糟

**writeback 探针，2026-09-04。** 探针枚举阶段老老实实打印了
`WRITEBACK_PIXEL_FORMATS` 的 19 个格式，然后在下一屏用写死的 XR24
去分配目标 buffer —— 而那 19 个里根本没有 XR24。

结果是 `TEST_ONLY` 被 ENOTSUP 拒，而拒绝理由看起来像
**"这块硬件不支持 writeback 与显示共存"**。差一点就把它记成一条
硬件能力结论，而错误的能力结论会一路影响到 Step 5 的验收方案。

三点：

1. **约束一旦被读出来，就必须成为下一步的输入。** 只打印不使用，
   等于给了自己一个"我检查过了"的错觉。
2. **一个失败要归因到"硬件不支持"之前，先确认请求本身是合法的。**
   ENOTSUP 说的是"这个请求我做不了"，不是"这类功能我没有"。
3. `bisect_rejection` 指对了地方（去掉 `WRITEBACK_FB_ID` 就通过），
   但当时属性没带名字，日志只有 `prop 72 (?)` —— **可读的诊断输出
   要在需要它之前就准备好**，出问题的那一刻没人有心情去查属性号。

## L-20　atomic 提交只描述你说到的属性，没说到的保持原样

**writeback 探针，2026-09-04。** headless 那一路在 `crtc#84` 上被 EINVAL 拒，
根因是 HDMI-A-1 还挂在那个 CRTC 上 —— 而那个绑定是**同一次运行里
上一个 coexist 尝试留下的**，我们自己造的残留状态。

于是"把 CRTC 的 mode 改成 writeback 自报的 3200x1920"这个请求，
对还挂着的显示器来说是做不到的时序，内核拒得完全正确。

这条和项目既有的"防御性完整 modeset，不假设 CRTC 状态干净"是同一条，
只是这次的脏状态来自自己：**同一个进程里跑多个拓扑实验时，
每次都要把不属于这次拓扑的对象显式解绑，而不是指望它们没被碰过。**

## L-21　用户态全绿不代表内核没在流血

**writeback 探针，2026-09-04。** 探针的正常路径完全成功：TEST_ONLY 通过、
提交成功、fence 正常 signal、回读的像素逐点精确相等、退出时资源全平。
**而内核那边每帧每页在报 page fault**（`DPU(AXI-1)`，`RW:0x1`，
一次运行 13844 条被抑制的回调）—— 因为一次写回提交之后引擎没停，
我们一释放 buffer 它就在往已释放的地址写。

这与 L-3 的补充是同一件事的两面：那次是"子进程崩溃与内核 BUG_ON
从 `waitpid` 看一模一样"，这次是"用户态的所有判据都通过，
故障只存在于 dmesg 里"。

推论：**在自研或半成品驱动上做的每一次能力探测，验收清单里都要有一行
"看 dmesg"。** 而且要能把日志归因到具体阶段 ——
`repro/wb-oneshot-fault/` 的做法是每进入一个阶段就往 `/dev/kmsg`
写一行标记，故障落在哪个阶段是读出来的，不是靠时间戳猜的。

## L-22　"最小复现"的最小是指路径最短，不是功能最全

**writeback 故障复现，2026-09-04。** 第一版写了 400 多行：四个阶段、
`/dev/kmsg` 阶段标记、校验和对比、connector/crtc/plane 自动选择、对照开关、
teardown。**而它在第一个阶段就 EINVAL 退出了** —— 自动选择挑中了一个没有
显示器的 CRTC，于是"启用 CRTC 但一个 connector 都不挂"，内核拒得完全正确。

两条：

1. **复现程序的读者是驱动同事，不是我们自己。** 他要的是"跑一下、看 dmesg、
   去查那三个寄存器"，不是一个带阶段划分的诊断框架。项目里已有的两个复现
   程序（`dpu-import-bug`、`vpu-import-bug`）都是几十行、设备路径写死、
   一路 `printf("ret = %d")` —— 那个形状才是对的。
2. **每多一个自动化环节，就多一个它自己会失败的地方**，而且失败在别人的
   机器上、由别人来调。对象 id 和属性 id 全部写死，比一个会挑错 CRTC 的
   选择循环可靠得多；换板子要改，那就写一行注释说要改。

重写后 94 行：开设备、建两块 dumb、一次带 `WRITEBACK_FB_ID` 的提交、
sleep、`RmFB`、sleep。没有阶段，没有 kmsg，没有选择逻辑。
