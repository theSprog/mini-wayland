## 上一讲结束时，屏幕上还只有我们自己画的东西

前两讲把一条链路走通了。第一讲用 dumb buffer 在 CPU 上画像素，通过 atomic modeset 把它送上屏幕，弄清楚了 connector、CRTC、plane 这几个 KMS 对象各自管什么。第二讲把 GPU 拉了进来，用 GBM 分配显存、用 EGL 把这块显存变成 GLES 的渲染目标、用 DMA-BUF 和 PRIME 把它从渲染设备递给显示设备，最后仍然由 atomic commit 送上屏幕。

到这里为止，整条链路都在一个进程里。分配的是我们，绘制的是我们，提交的也是我们。这个程序更像一个 demo 播放器，离合成器还差着最关键的一件事：**屏幕上的内容应该来自别的程序。**

浏览器、终端、视频播放器各自是一个独立进程，它们画自己的窗口内容，合成器负责把这些内容摆到屏幕上。这一讲要做的就是在链路中间切一刀，把"谁画"和"谁上屏"拆到两个进程里，然后想清楚这一刀带来了哪些新问题。

新问题一共四类：

- 像素怎么跨进程传递
- 元数据怎么描述
- 两个进程之间怎么协调一块内存的使用权
- 以及在这条链路上出错时怎么当场看见。

这一讲假设读者读过第二讲，知道 DMA-BUF 是什么、PRIME 导出导入在做什么、GEM handle 的作用域为什么是单个打开的设备文件。也假设读者有操作系统基础，知道 fd 是什么、ioctl 是什么、用户态驱动和内核态驱动大致怎么分工。至于显示相关的概念，这一讲需要用到的会重新讲一遍。



## 画面从哪里来：三种可能的分工

在讨论具体机制之前，先看看"让另一个进程来画"这件事总共有几种做法。历史上这三种做法都被真实的系统采用过，各自的取舍差别很大。

### 做法一：客户端把画好的像素发给合成器

客户端在自己的内存里画好一帧，通过某种 IPC 通道把整块像素发给合成器，合成器收下之后拷贝进自己的显存，再上屏。

这是最容易想到的做法，也是 X11 早期的做法之一。一帧 1920x1080 的 XRGB8888是 8294400 字节，60fps 下每秒要搬 475 MB。搬一次的开销在 CPU 和内存带宽上都是实打实的，而屏幕上并没有多出任何东西。

真正致命的是这块内存的位置。CPU 能访问的普通内存不一定能被显示控制器扫描，上一讲讲过，显示控制器读的是物理地址或者它自己的 IOVA，对齐、连续性、排布格式都有硬约束。所以合成器收到像素之后不只是拷贝一次，往往还要再走一次格式转换或者一次上传。



### 做法二：共享内存

客户端和合成器映射同一块匿名共享内存，客户端往里写，合成器直接读，少了一次拷贝。

问题在于这块内存通常还是"CPU 内存"。它能不能被显示控制器直接扫描输出，取决于分配它的方式；能不能被 GPU 当纹理采样，同样取决于分配方式。多数情况下合成器仍然要把它上传成一块 GPU 或显示控制器认得的内存，那次上传就是被省掉的拷贝换了个位置又出现了。

> `wl_shm` 走的就是这条路，今天仍然是 wayland 的保底通道。
>
> `wl_shm` 在今天的定位只是保底：客户端没有 GPU、或者 GPU 驱动不可用时，至少还有一条能画出东西的路。



### 做法三：共享一块设备内存的句柄

客户端从设备分配一块内存（第二讲的 GBM 或者 dumb buffer），在这块内存上直接绘制，然后把这块内存的**句柄**交给合成器。合成器不拷贝像素，只是把这个句柄变成自己能用的形式，挂到 plane 上，让显示控制器直接扫描它。

这条路就是现代 wayland 的主路，`linux-dmabuf` 协议做的事情。像素从被画出来到被扫描出光，一次都没有被拷贝过，所以叫零拷贝。

零拷贝的代价是复杂度全部转移到了元数据和生命周期上：

- 合成器要知道这块内存的宽高、格式、每个平面的偏移和跨距、内存排布的 modifier；
- 要知道什么时候客户端可以覆写它；
- 要知道客户端突然消失时怎么收拾。



### 为什么句柄能跨进程

第二讲讲过 GEM handle 的作用域。同一个 GEM 对象，在两个不同的打开的设备文件里是两个不同的 handle 数值，而且同一个数值在另一个 fd 上很可能指向完全无关的对象。

所以 GEM handle 不能直接传给别的进程，传过去也是错的，而且是**看起来能用的错**：对方拿这个数值去查表，很可能查到一个存在的对象，只是不是你想给它的那个。

DMA-BUF 解决的正是这件事。把一个 GEM 对象导出成 `dma_buf`，内核会为它创建一个 `struct file`，返回一个 fd。fd 是进程私有的数值，但它背后的`struct file` 是内核对象，可以被多个进程同时引用。

于是问题变成了：**怎么把一个 fd 从一个进程交给另一个进程。**



## 文件描述符怎么跨进程

### fd 是索引，不是内容

fd 是一个小整数，它是进程内文件描述符表的索引。表里的每一项指向一个 `struct file`。同一个 `struct file` 可以被多个表项指向，也可以被多个进程的表指向，内核用引用计数管理它的生命周期。

所以"把 fd 传给另一个进程"如果理解成"把这个整数发过去"，那是错的。整数 7 在你的进程里是一块 24MB 的显存，在对方进程里可能是它打开的日志文件。数值本身不携带任何信息。

正确的做法是让内核参与：告诉内核"把我这个 fd 背后的对象，在对方的描述符表里也装一份"。内核会在对方表里找一个空位，填上指向同一个 `struct file` 的指针，把引用计数加一，然后把那个新的索引值交给对方。两个进程的数值几乎肯定不同，指向的对象是同一个。

Unix domain socket 的 `SCM_RIGHTS` 就是干这件事的接口。

> `SCM_RIGHTS`（Socket-level Control Message: Rights）通过 UNIX 域套接字通信时，发送方写入 FD，内核在接收方进程的打开文件表里分配一个**新的空闲 FD**，并将其指向内核底层的同一个文件对象（`struct file`），同时递增引用计数。
>
> - 发送方发出的可能是 `fd = 3`。
> - 接收方收到的可能是 `fd = 7`。
> - 数字不同，但操作的是同一个底层底层文件实体。



### SCM_RIGHTS 长什么样

`sendmsg` 和 `recvmsg` 将数据分成两轨：

1. **普通业务载荷**：通过 I/O 向量（I/O Vector, IOV）的 `msg_iov` 发送常规业务字节。
2. **控制载荷（辅助数据）**：挂在 `msg.msg_control` 上的扁平字节数组。

`msg_control` 指向的内存在物理结构上排布如下：

```
|<------------------------- CMSG_SPACE ------------------------->|
+---------------------+-------------------------------+----------+
|   struct cmsghdr    |         CMSG_DATA             | 填充间隙 |
| (level, type, len)  |   [ fd1 ][ fd2 ][ fd3 ]...    | (对齐)   |
+---------------------+-------------------------------+----------+
|<----------------------- CMSG_LEN ------------------>|
```



假设进程 A 打开了两个文件，拿到 `fd = 3` 和 `fd = 4`，目标是通过 UNIX 域套接字一次性把它们交给进程 B。

在 64 位系统上，一个 `int` 占 4 字节，`struct cmsghdr` 头结构占 16 字节。

**1. 发送方：在内存里拼装“包裹”**

发送方需要传递 2 个 FD，数据总长（`CMSG_DATA`）是 $2 \times 4 = 8$ 字节。

- **`CMSG_LEN(8)` = 24 字节**：头部（16 字节）+ 数据（8 字节）。这是控制消息的实际有效净长度，直接填入 `cmsg->cmsg_len`。
- **`CMSG_SPACE(8)` = 24 字节**：头部 + 数据 + 对齐填充（24 正好是 8 的倍数，填充为 0）。发送方必须至少分配这么大的缓冲区。

这块内存（`control` 缓冲区）填充完毕后，在物理内存上的真实排布如下：

| **字节偏移** | **内存内容**     | **对应字段**             |
| ------------ | ---------------- | ------------------------ |
| `00 ~ 07`    | `24`             | `cmsg_len`（总有效长度） |
| `08 ~ 11`    | `SOL_SOCKET` (1) | `cmsg_level`             |
| `12 ~ 15`    | `SCM_RIGHTS` (1) | `cmsg_type`              |
| `16 ~ 19`    | `3`              | `CMSG_DATA`：第一个 FD   |
| `20 ~ 23`    | `4`              | `CMSG_DATA`：第二个 FD   |

设置好 `msg.msg_control` 指向该缓冲区、`msg.msg_controllen = 24`，并在 `msg.msg_iov` 里塞 1 字节普通数据（比如字符 `'A'`）后，调用 `sendmsg` 发出。

> 塞入这 1 字节普通数据（字符 `A`）并非多余，而是为了解决流式套接字下的 **EOF（End-of-File，文件结束符）歧义** 与 **历史兼容性**。
>
> - **避免被误判为连接断开（EOF）**：在 `SOCK_STREAM` 模式下，`read`、`recv` 或 `recvmsg` 返回 `0` 在语义上严格代表“对端关闭了连接”。如果只发辅助数据而不带常规数据，接收方调用的 `recvmsg` 将返回 `0`，接收逻辑便无法区分到底是“收到了带控制信息的 0 字节包”还是“对端挂断了”。
> - **辅助数据的从属地位**：在 POSIX 规范与传统 BSD 实现中，控制数据被定义为常规数据的“附属品”。许多内核实现在协议栈中若检测到没有常规业务载荷，可能直接丢弃辅助数据，甚至不触发接收端的读取就绪事件。因此，携带至少 1 字节常规数据是通用的稳妥做法。
> - 其实这本质上是一种工程妥协



**2. 内核中转：偷梁换柱**

内核截获到这个套接字消息，发现类型是 `SCM_RIGHTS`，会执行以下操作：

1. 从进程 A 的打开文件表里查出 `3` 和 `4` 对应的底层内核结构体指针（比如 `file_X` 和 `file_Y`）。
2. 将 `file_X` 和 `file_Y` 的引用计数加 1。
3. 原本数组里的 `3` 和 `4` 不会被原样发给进程 B。



**3. 接收方：接收与反算**

假设进程 B 预先申请了一个能容纳 4 个 FD 的较大缓冲区：`control[CMSG_SPACE(16)]`（共 32 字节），然后调用 `recvmsg`。

内核完成数据投递后，进程 B 的这块内存被内核改写成了下面的状态：

| **字节偏移** | **内存内容** | **说明**                                                   |
| ------------ | ------------ | ---------------------------------------------------------- |
| `00 ~ 07`    | **`24`**     | **内核改写了它**：告诉接收方本次实际只送来 24 字节有效数据 |
| `08 ~ 11`    | `SOL_SOCKET` | 协议层级                                                   |
| `12 ~ 15`    | `SCM_RIGHTS` | 控制类型                                                   |
| `16 ~ 19`    | **`8`**      | **内核分配的新 FD**（指向 `file_X`）                       |
| `20 ~ 23`    | **`9`**      | **内核分配的新 FD**（指向 `file_Y`）                       |
| `24 ~ 31`    | 未使用       | 预留的缓冲区剩余空间                                       |

接收方代码如何把 `8` 和 `9` 取出来：

1. 读出头部记录的实际长度：`cmsg->cmsg_len`（读到数字 `24`）。
2. 剥离头部长度：`CMSG_LEN(0)` 代表只有头部的尺寸（`16` 字节）。实际载荷字节数 = 24 - 16 = 8Byte
3. 计算 FD 个数：$$\text{FD 个数} = \frac{8}{\operatorname{sizeof}(\text{int})} = 2\text{ 个}$$
4. 通过 `int *fds = (int *)CMSG_DATA(cmsg)` 拿到数组首地址（偏移 `16`），直接读取：
    - `fds[0]` 是 `8`
    - `fds[1]` 是 `9`

此时进程 B 操作自身的 `fd = 8`，读写的就是进程 A 原来 `fd = 3` 指向的同一个文件。



### 三个必须记住的细节

- **`MSG_CMSG_CLOEXEC` 不能省** 

    > `ssize_t n = recvmsg(socket_fd, &msg, MSG_CMSG_CLOEXEC);`
    >
    > 不带这个标志收到的 fd 没有 `close-on-exec` 功能，进程随后 `fork` 加 `exec` 时会把它一路带进子进程。而这个 `fd` 理论上不应该在子进程存活，它只是用于给合成器提交渲染帧的 `dma_buf` 索引而已
    >
    > 合成器是一个会频繁拉起子进程的程序，漏出去一个 `dma_buf` 的后果是那块显存永远不会被释放，因为引用计数上永远挂着一个谁也不知道的持有者。这个问题在现场看不出来，它的症状是运行几个小时之后显存耗尽。

- **`MSG_CTRUNC` 要当致命错误处理**

    > 这个标志表示辅助数据被截断了。控制缓冲区装不下时，内核对那些没装进去的 fd 怎么处理，不同内核版本的行为并不完全一致，也没有一个可以依赖的承诺。
    >
    > 正确的做法是把接收缓冲区按协议允许的最大 fd 数静态开满，然后把 `MSG_CTRUNC` 当成"对端在乱发"来处理，直接断开连接。
    >
    > 依赖任何一种截断行为都是在给自己埋一个跨内核版本的坑。

- **收到的 fd 要立刻交给一个会自动关闭它的持有者（RAII）**

    > 解析一条消息的过程里有很多提前返回的分支，魔数、版本、长度都要查，平面数和 fd 数还要对得上。
    > 每一条分支上都要保证已经收到的 fd 被关掉。手写这件事迟早会漏，所以接收函数的契约要写死成"要么返回一组由 RAII 对象持有的 fd，要么一个都不留下"，中间状态不存在。



### 引用计数是怎么走的

一次完整的传递过程里，`struct file` 的引用计数变化如下：

```
客户端 PRIME 导出                 refcount = 1   （客户端持有）
客户端 sendmsg 带 SCM_RIGHTS      refcount = 2   （内核为传输持有一份）
合成器 recvmsg 拿到 fd            refcount = 2   （内核所有权转到合成器的表里）
客户端 close 自己那份             refcount = 1   （只剩合成器）
合成器 PRIME_FD_TO_HANDLE         refcount 不变，但 GEM 对象多了一个引用
合成器 close fd                   dma_buf 的引用回到 GEM 对象持有
```

这里有两个容易犯的错：

- 发送方在 `sendmsg` 之后不关闭自己那份 fd。传输本身不转移所有权，它是复制一份引用。发送方不关，那份引用就一直在，这块内存永远不会因为客户端退出而释放。

- 反过来，发送方在 `sendmsg` 返回之前就关掉 fd 也是错的，那时内核还没来得及为传输持有引用。正确的顺序是 `sendmsg` 成功返回之后再关。


在我们的实现里，传输层只**借用** fd，关闭的时机交给持有这块 buffer 的对象决定。传输层替调用方关 fd，会让所有权规则变成"看情况"，而这正是要消灭的东西。



## 一块 buffer 怎么自我描述

fd 递过去了，合成器手里现在有一个 dma_buf。它还是不知道这块内存里装的是什么。dma_buf 本身只是一段内存加一套 DMA 映射操作，它不携带宽高，不携带格式，不携带排布方式。这些信息必须由客户端另行告诉合成器。



### 至少要传哪些字段

第二讲讲过描述一块图像内存需要什么，这里复述一遍并补上跨进程带来的部分。

| 字段 | 含义 | 少了会怎样 |
| --- | --- | --- |
| width / height | 图像的像素尺寸 | 合成器不知道扫多少行 |
| format | fourcc，例如 `XR24` | 通道顺序和位宽全靠猜 |
| modifier | 内存排布，线性或者某种平铺压缩 | 按线性去读一块平铺内存，屏幕上是垃圾 |
| num_planes | 平面数，RGB 是 1，NV12 是 2 | 后面的字段没法解释 |
| 每平面 offset | 该平面在 dma_buf 里的起始偏移 | 读到别的平面或者越界 |
| 每平面 stride | 该平面每行的字节数 | 图像会斜过去 |
| flags | y_invert 之类 | 上下颠倒 |

其中 modifier 这一项是第二讲的重点，这里只提醒一句它在跨进程场景下的特殊性：**这个值现在来自另一个进程**，而它决定合成器怎么解释这块内存。



### 每个平面一个 fd

多平面格式（NV12 的 Y 平面和 UV 平面）在实现上有两种可能：两个平面在同一块 `dma_buf` 里靠 offset 区分，或者分成两块独立的 `dma_buf`。

协议层面的处理方式是**每个平面都带一个 fd**。两个平面共享同一块内存时，就发同一个 dma_buf 的两个 fd（`dup` 一下），offset 不同。

也可以设计成"检测到共享就只发一个 fd"，那样能省一次 `dup`。代价是所有权规则变成条件式的：收到的 fd 个数有时等于平面数，有时少于平面数，释放的时候要判断哪些是同一个对象。规则一旦带上条件，出错的地方就从"忘了释放"变成"在某种组合下忘了释放"，后者难查得多。

所以规则定成不带条件的那一种：**平面数是几，fd 就是几**。去重交给导入的那一层做，那里本来就要维护 dma_buf 到 GEM handle 的映射表。



### modifier 为什么拆成两个 32 位

`zwp_linux_buffer_params_v1` 的 `add` 请求里，modifier 是拆成 hi 和 lo 两个 32 位整数传的。我们的线格式沿用了这个形状。

原因是 wayland 的 wire 格式里没有 64 位整数类型。这是一个协议层面的历史细节，跟技术优劣无关。沿用它的理由也很简单：下一讲要换成真协议，字段形状一致的话，替换的是传输层，数据模型一行都不用动。

这条原则贯穿整个第三步的设计。**结构对齐 wayland，编码不对齐。** 字段集合按 `zwp_linux_dmabuf` 的形状来，但不去实现 wayland 的对象 id、opcode 和变长数组，那些属于下一讲要用库解决的部分，现在自己实现一遍等于付两遍代价。



### 消息头里的三个"冗余"字段

我们的消息头有五个字段。

```
magic        uint32   固定值，第一道判据
abi_version  uint16   协议版本
type         uint16   消息类型
body_size    uint32   载荷字节数
fd_count     uint32   随消息携带的 fd 个数
```

`body_size` 和 `fd_count` 看着都是冗余信息。SEQPACKET 已经给了消息边界，一次 `recvmsg` 读到多少字节是知道的；cmsg 里也能算出 fd 个数。为什么还要在头里再写一遍？

**因为冗余就是判据。** 收发两侧对同一条消息的理解一旦不一致，这两个数就对不上。最常见的原因是两个二进制不是同一次构建出来的：改了消息结构，只重新编译了一端。同机、同 ABI、同编译器，都不代表同版本。

这类错误不检查的话，表现形式是字段读出来是垃圾值。而垃圾值恰好落在合法区间时，症状就变成了"画面不对"，而不是"报错"。

版本号还可以用编译期断言绑到结构体尺寸上：

```
static_assert(kWireAbiVersion == 1)
static_assert(sizeof(CreateBufferBody) == 64)
static_assert(sizeof(CommitBody) == 32)
...
```

改了结构忘记加版本号，编译直接失败。这比运行时才发现要早得多。



### 消息集合

一共八条消息，每一条在 wayland 里都有对应物。这个对应关系是刻意保持的。

| 方向 | 消息 | 载荷 | wayland 对应 |
| --- | --- | --- | --- |
| C→S | HELLO | 协议版本、客户端能做什么 | `wl_display.get_registry` |
| S→C | HELLO_ACK | 推荐的分配方式、格式与 modifier 候选、输出尺寸 | `zwp_linux_dmabuf_feedback_v1` |
| C→S | CREATE_BUFFER | 完整的 buffer 描述 + N 个 fd | `zwp_linux_buffer_params_v1` |
| C→S | DESTROY_BUFFER | buffer id | `wl_buffer.destroy` |
| C→S | COMMIT | buffer id、帧序号、内容校验值 | `wl_surface.attach` + `.commit` |
| S→C | BUFFER_RELEASE | buffer id | `wl_buffer.release` |
| S→C | FRAME_DONE | 帧序号、翻页序号 | `wl_surface.frame` |
| S→C | ERROR | 错误码加英文描述 | `wl_display.error` |

有几个字段现在就占位但不填真值：COMMIT 里的 damage 区域、COMMIT 和 BUFFER_RELEASE 里的 fence 标志位、FRAME_DONE 里的时间戳。

先占位不是为了"以后好扩展"这种空泛理由。**它们会改变消息的语义边界。** 带 fence 的 release 和不带 fence 的 release 是两件不同的事：前者说的是"我给你一个信号，它一触发你就能复用"，后者说的是"我现在告诉你可以复用了"。把位置先留出来，后面改的是填充逻辑，而不是重新设计消息集合。



### 谁来决定客户端从哪里分配

这是设计上最值得说的一个决定。

第二讲有两条分配路径：从显示设备分配 dumb buffer，或者从渲染设备用 GBM 分配。跨进程之后，客户端也面临同样的选择。一个直觉的做法是给客户端一个命令行参数，让它自己挑。

这个做法在下一讲会被推翻。真实的客户端是 Mesa，它不认识显示设备，也不该认识。它分配用哪个设备、哪个格式、哪些 modifier，全部来自合成器发过来的`linux-dmabuf-feedback`。决策发生在合成器那一侧。

所以我们现在就把数据流向定成那个样子：

```
服务端启动
  → 探测本机的分配能力
  → 决定推荐哪条路径，以及该格式下的 modifier 候选
  → 放进 HELLO_ACK 发给客户端
客户端
  → 按推荐去分配
  → 做不到就报回去，让服务端换一个推荐
```

这样 HELLO_ACK 就是 `linux-dmabuf-feedback` 的雏形。下一讲换协议时替换的是传输，不是数据流向。如果这一步把决策写在客户端的命令行里，下一讲要推翻的就不是一个默认值，是整条数据的方向。



## 信任边界：来自另一个进程的字段都是可疑的

同一个进程里，一块 buffer 的宽高和跨距是自己算的，出错是自己的 bug。跨了进程之后，这些数字来自别人。客户端可能有 bug，可能版本不匹配，也可能是恶意的。合成器要在这些数字上做的每一个动作，都是在信任它们。

这一节讨论三件事：内核会替我们挡住什么，内核不会挡什么，以及我们自己必须挡住什么。

### 内核挡得住的部分

`drmModeAddFB2` 在建立 framebuffer 时会做一批校验，其中最有用的是尺寸检查。DRM 核心会拿每个平面的 `offset + stride * height` 和 GEM 对象的实际大小比较，超出就返回 `EINVAL`。

这条检查覆盖了两类常见错误：

**跨距报错。** 客户端说 stride 是 3840，实际分配的时候是 7680。合成器按 3840 去建 fb，尺寸算下来只有实际的一半，看起来是够的，但显示出来会是斜的。好在 DRM 这时候会拒绝，因为宽度 1920 的 XR24 至少需要 7680 字节每行，报的 stride 连一行都装不下。

**偏移越界。** offset 指到了 buffer 尾部之外，尺寸检查同样能发现。

我们的实现刻意**不在用户态重算一遍**这套尺寸规则。理由是这样会得到两套可能不一致的规则：内核那套是权威的，用户态那套是我们理解的。两套规则一致的时候用户态那套没用，不一致的时候用户态那套是错的。让内核去拒绝，我们负责把它的拒绝理由说清楚。



### 内核挡不住的部分

这块硬件上有一个实测结论，值得单独拿出来说。

我们在故障注入里构造了一条用例：客户端声明一个纯属编造的私有 modifier，一个不可能存在于任何硬件的值。预期是 `drmModeAddFB2WithModifiers` 拒绝它。

实际结果是内核收下了。fb 建成功，上屏正常，画面也正确。因为这块内存本来就是线性的，而这一版驱动的 addfb2 路径根本没有去看 modifier 字段。

这次的结果碰巧是对的，危险的是那条推理：「格式和 modifier 不合法的话 addfb2 会拒绝」。它是一个假设，不是保证。换一个 modifier 值，同样的路径就会变成"驱动按平铺格式去解释一块线性内存"，屏幕上一堆垃圾，而所有返回码都是 0。

推论很直接：**跨越信任边界进来的字段，不能指望内核替你校验。**



### 我们自己必须挡住的部分

合成器要自己比对的东西，判据其实是现成的：**它自己公告过什么，就只接受什么。**

HELLO_ACK 里发给客户端的格式与 modifier 候选，来自 plane 的 `IN_FORMATS` 属性。客户端送回来的 (format, modifier) 组合如果不在那份集合里，直接拒绝。这在协议层面本来就该成立：客户端不该使用一个从没被公告过的组合。

下一讲这条会变成 `linux-dmabuf-feedback` 的 tranche 和客户端选择之间的一致性检查，逻辑完全一样，只是数据来源换成了协议对象。

除了 modifier，还有几项也必须自己查：

- **fd 个数必须等于 num_planes。** 这两个数一个来自 cmsg，一个来自消息体，对不上就是协议错误。
- **宽高非零、每个平面的 stride 非零。** 这些是零成本的自洽性检查。
- **buffer id 不能重复，也不能引用不存在的 id。** 这属于协议状态机的部分。

有一条边界要提前写下来。上面那条"必须在公告过的集合里"只对**直出**成立。

第五步引入 GPU 合成回退之后，一个 plane 不接受的 modifier 未必要拒绝，因为那块 buffer 可能根本不打算直接扫描，而是要被渲染器采样。那时候判据变成"渲染器能不能采样它"。同一个字段，两层不同的判据，取决于这块 buffer的去向。



### 错误信息要说到什么粒度

这一节的最后一件事，是拒绝的方式。

一条"import failed"是不合格的。收到这句话的人接下来要做的第一件事就是去猜：是 fd 不对，是格式不对，还是尺寸不对。

合格的错误信息长这样：

```
failed to import plane 0 of 1920x1080 XR24 planes=1
  [0: fd=5 stride=7680 offset=0] modifier=INVALID:
  drmPrimeFDToHandle(fd=5) failed with EINVAL;
  if the importing device has no IOMMU it may require physically
  contiguous memory -- check dmesg for driver-side detail
```

里面有四类信息：失败的动作（哪个 ioctl，哪个参数），失败的对象（哪个平面，什么几何），内核给的原因（errno），以及一条指向下一步的提示（去看 dmesg）。

最后那条尤其重要。跨设备导入失败时，用户态拿到的永远只是一个 `EINVAL`，真正的原因往往只在内核日志里。一条提示能省掉别人半小时



## 谁在用这块内存：release 的时机

这一节是整个第三步里最容易写错的地方，而写错的症状是间歇性的。

### 为什么需要一条回向的消息

同一个进程里，buffer 的所有者和使用者是同一个人。第二讲的 swapchain 靠"轮转 N 个槽位，等翻页事件"就把复用时机管住了，因为提交和等待都在自己手里。

跨进程之后，情况变了。**决定何时可以覆写一块 buffer 的信息在合成器手里，而做覆写动作的是客户端。** 没有回向消息，客户端只有两种选择：

一种是每帧新分配一块。这样每帧都要 `PRIME_FD_TO_HANDLE` 加 `addfb2`，第二讲建立的稳态记账约束当场作废，而且掩盖了真正要学的东西。

另一种是盲写复用。正在被扫描的 buffer 被写花，表现是撕裂或者半帧，而且只在时序恰好的时候出现。帧率越稳，越难复现。

所以 release 不是顺手加的功能，它是跨进程零拷贝管线成立的前提。



### 一次注册，每帧提交

消息集合里 CREATE_BUFFER 和 COMMIT 是分开的，这个拆法直接决定了记账能不能延续第二讲的结论。

```
CREATE_BUFFER    每块 buffer 一生一次
                 服务端：导入 → addfb2 → 记进 buffer id 到 fb id 的表
COMMIT           每帧
                 只发 buffer id 和帧序号，不再传 fd
BUFFER_RELEASE   服务端判定该 buffer 不再被扫描之后发出
FRAME_DONE       翻页完成之后发出，客户端据此驱动下一帧
```

这样稳态里 `prime_fd_to_handle` 和 `add_fb` 的增量是 0，每帧仍然只有一次 atomic commit 加一次翻页。跨了进程之后这条不变，才说明这条边界是零成本的。

这也正是 `wl_buffer` 的模型。`wl_buffer` 是一个长生命周期的协议对象，`attach` 只是引用它。下一讲不需要改这里的任何语义。



### release 应该在什么时候发

一块 buffer 在**被另一块换下来**之前，一直在被扫描。

所以：第 N 帧翻页完成的时候，该释放的是**第 N-1 帧**用的那块，不是第 N 帧刚上去的那块。

写成后者的话，双缓冲的客户端会在正在扫描的 buffer 上作画。伪代码对比：

```
错误：
    收到翻页完成事件:
        release(刚刚上屏的那块)      ← 它正在被扫描

正确：
    收到翻页完成事件:
        release(上一块)              ← 它刚被换下来
        上一块 = 刚刚上屏的那块
```

这条规则在有了显式同步之后会放宽。第六步接入 fence 之后，release fence 一触发就能复用，不必等到下一次翻页。现在这条保守规则是正确的，只是不是最优的。代码里应该写明这一点，标好什么时候删。



### 流水线深度：服务端最多同时持有几块

这个算术值得单独算一遍，因为它决定了客户端至少要准备几块 buffer。

服务端在任一时刻可能同时持有三块：

```
on-screen    正在被扫描的那块
submitted    已经提交给内核、等翻页完成的那块
pending      客户端已经 COMMIT、还没轮到提交的那块
```

所以客户端手里的空闲槽位数是 `总数 - 3`。

三块的时候空闲槽位恒为 0，客户端每帧都要等一次 release。这是**预期行为**，不是故障：帧率不受影响，服务端手里始终有下一帧；只是客户端没法把绘制和服务端的工作重叠起来。实测三块和四块跑出来的帧率完全一致，都是 60.00fps 零丢帧。

四块的时候客户端始终有一块空闲，绘制和呈现可以重叠。默认取三块，让 release 时机的错误处在压力之下。这个选择是有意的：槽位越多，release 写错了越不容易被发现。



### 客户端没有空闲槽位时该做什么

答案是阻塞等待，不许新分配。

新分配能让程序继续跑下去，但它会掩盖 release 时机写错的问题：本来该暴露成"卡住了"的 bug，变成了"内存慢慢涨"。后者要跑很久才能发现。

等待的次数值得统计并打印出来，它是"release 时机是不是写对了"的直接体感指标。但统计口径要想清楚。我们第一版按循环次数计数，打出来是"602 提交，597 次等待"，看着吓人，实际上只反映了每帧要收两条消息（一条 release，一条 frame done）这个事实。改成每帧至多计一次之后，数字才有意义。

一个会误导人的计数器比没有计数更糟糕。这条在第二讲也出现过一次，当时是翻页计数永久性地多 1。



## 客户端死掉之后

客户端是一个独立进程，它可能崩溃，可能被 `kill -9`，可能自己退出而没有做任何清理。合成器要在任何一个时刻都能收拾残局，而这个残局里有一块正在被显示控制器扫描的内存。



### 先看资源的归属

跨进程之后，一块 buffer 上挂着的东西分布在两边：

```
客户端侧                        服务端侧
  GEM 对象（它分配的）            GEM handle（导入产生的）
  自己那份 dmabuf fd              dmabuf fd（收到的那份）
  CPU 映射                        framebuffer（addfb2 建的）
                                  plane 上的引用（正在扫描时）
```

客户端进程消失时，它那一列会被内核自动回收：进程退出，所有 fd 关闭，GEM 对象的引用计数下降。服务端那一列不会，因为那些引用挂在服务端的 `drm_file` 上，跟客户端的死活无关。

这是好事。它意味着客户端死了之后，屏幕上不会立刻变成一块无人管理的内存，那块内存的引用还被服务端持有着。



### 释放的顺序不能反

服务端在 socket 上读到 EOF，知道客户端没了。这时候它的 buffer 很可能**正在被扫描**。

处理顺序必须是：

```
1. 提交一帧服务端自有的 buffer（兜底帧）
2. 等这次翻页完成
3. RmFB、归还 GEM handle、关闭 fd
```

**不允许在 on-screen 状态下 RmFB。** 内核为了自保会去禁用 plane 或者 CRTC，表现是闪一下黑屏。更糟的是这个行为会掩盖真正的所有权错误：本来应该暴露成"你在释放一块还在用的资源"的问题，变成了"偶尔闪一下"。

兜底帧还顺带解决了另一个问题：程序启动到第一个客户端连上之间，屏幕上应该显示什么。有一块自有的 buffer，这段时间就有东西可显示，而不是黑屏或者上一个程序留下的画面。



### 反方向：服务端先死

客户端在 `send` 上收到 `EPIPE`，正常退出即可。它持有的 dmabuf 引用随进程退出由内核释放，不需要额外的协议动作。

有一个细节值得提：`sendmsg` 要带 `MSG_NOSIGNAL`，否则往一个已经关闭的 socket 上写会收到 `SIGPIPE`，默认动作是杀掉进程。合成器和客户端都应该处理这件事，要么带这个标志，要么忽略 `SIGPIPE`。





## 返回码不证明数据到了

这一节是这一讲方法论上的核心。

### 四层校验，没有一层碰过像素

客户端提交一帧，服务端把它送上屏幕，中间会经过这些检查：

| 层 | 它校验了什么 |
| --- | --- |
| `PRIME_FD_TO_HANDLE` | 内核成功建出了一个 GEM 对象 |
| `drmModeAddFB2` | 格式、跨距、尺寸自洽，且不超过 GEM 对象大小 |
| `ATOMIC_TEST_ONLY` | 这套 plane 配置硬件能接受 |
| 翻页完成事件 | CRTC 确实翻了一页 |

四层全过，帧率 60.00fps，一帧不掉，ioctl 计数完美配平。

**这四层里没有一层碰过像素。**

第二讲已经在这上面栽过一次：跨设备导入的方向报了 PASS，60fps 一帧不掉，屏幕全黑。根因是内核建出的映射表每一项都是 0，而没有任何一个返回码能反映这件事。

跨进程之后，同一类失败会以新的形式出现：fd 传错了，offset 和 stride 序列化时错位了，多平面的 fd 和平面对应错了，或者收到的是上一帧。这些都能让四层校验全部通过。

所以这一步的验收必须有一条**独立于返回码的内容判据**。



### 三层内容判据

判据分成三层，各自能抓住的错误不同：

```
客户端画像素
     │   L1  生产侧签名：客户端自己算一个校验值，随消息发过来
     ▼
 dmabuf 内存
     │   L2  消费侧回读：服务端映射导入的 dmabuf，比对签名
     ▼
 fb → plane → 显示控制器
     │   L3  显示侧回读：writeback 抓一帧，比对内容
     ▼
   屏幕
```

下面这张表列出每一层各自能抓住的失败模式。

| 失败模式 | L1 | L2 | L3 |
| --- | :-: | :-: | :-: |
| 客户端自己画错了 | 能 | 能 | 能 |
| fd 传错，发了 B 的 fd 说是 A | 不能 | 能 | 能 |
| offset / stride 序列化错位 | 不能 | 能 | 能 |
| 多平面时 fd 与平面对应错 | 不能 | 能 | 能 |
| 收到的是上一帧 | 不能 | 能 | 能 |
| 导入成功但指向别处 | 不能 | 能 | 能 |
| addfb2 成功但显示控制器读不到 | 不能 | 不能 | 能 |
| modifier 声明与实际排布不符 | 不能 | 不能 | 能 |
| plane 分配错、被别的层遮住 | 不能 | 不能 | 能 |

有一个判断很关键：**这一步新增的失败面全部落在 L2 能覆盖的范围内。** 

L3 覆盖的那几行是第二讲就已经存在、第五步才会真正高发的缺口。所以第三步的验收取 L1 加 L2，L3 作为独立的探针并行推进，不通过也不阻塞。这是有意的排期，不是妥协。



### L1：把签名画进像素里

客户端在每帧的**第 0 行第 0 列**开始，画一小块签名，编码这些字段：

```
magic         固定值
run_nonce     每次运行随机
frame_seq     帧序号
width height  几何
stride        跨距
format        格式
modifier_lo   modifier 的低 32 位
```

有三个设计点。

- **位置必须在最前面。**

    > 画在中间的话，stride 算错时签名块的位置会跟着一起漂移，于是"按错误的 stride 去读"反而能读到正确的签名，检测不出来。判据要放在错误会破坏它的位置上，不能放在跟着错一起漂移的位置上。

- **run_nonce 每次运行随机。**

    > 它的作用是让上一次运行残留在显存里的内容无法冒充本次的正确结果。复用显存的板子上这类误判是真实存在的，而且第一次遇到时会以为链路是通的：屏幕上确实有正确的图案，只是它是上次留下的。

- **每个字节编码成一个像素。** 

    > 第 i 个字节写成第 i 个像素，三个通道都填这个字节的值，alpha 填满。读的时候取任意一个通道的低 8 位。
    >
    > 这么绕一下是为了让 GL 路径也能写签名。GL 画不出精确的字节，但画得出 N 个1x1 的纯色块（scissor 加 clear）。CPU 路径直接写像素。两条路径共用同一个编码函数，不各写一遍。

> 这个方案的限制要写清楚，不能靠猜：只对 8 位每通道的 RGB 格式成立。YUV 或者 10bit 格式下应当跳过签名，并且**明确打印"这一帧没有内容判据"**，而不是静默降级。
>
> L1 单独用处不大，客户端自己算自己的，说什么都对。它的价值在于给 L2 一个 **期望值**：没有 L1，服务端读出来的东西只能自证一致，不能证明它就是客户端想画的那一帧。



### L2：服务端直接映射 dmabuf 读回来

服务端拿收到的 dmabuf fd 做 `mmap`，读出签名块比对。

这里有三条约束。

**`DMA_BUF_IOCTL_SYNC` 不能省。** 这是通用的 dma-buf UAPI，不是某个驱动的东西。CPU 访问一块 dma-buf 之前要发 `SYNC_START`，访问结束发 `SYNC_END`，两侧都不能少。跳过它，在有缓存一致性问题的平台上会读到陈旧数据，而且是**间歇性**的，这正是这个项目最怕的那类错误。

做成 RAII 是因为中间那段有很多提前返回：签名不对就返回，CRC 不对就返回。手写配对迟早会漏一条路径。

**`mmap(dmabuf_fd)` 是可选能力，不是保证。** 它需要导出方实现了 dma-buf 的 mmap 操作，有的驱动不实现，有的实现了但在策略上拒绝。我们这块板子上，显示设备导出的 dumb buffer 可以映射，GPU 导出的 buffer 返回 `EACCES`。

所以 L2 必须是**运行时探测出来的能力**，探不到就明确降级并打印，不能让验收静默地少一层。这一条在实际跑的时候救了我们一次，后面会讲。

**它是诊断路径，不是常规路径。** 每帧回读会在热路径上引入 mmap 和 sync，违反稳态零 ioctl 的约束。用法是只验前 N 帧，默认 8 帧，成本可以忽略，又能挡住绝大多数序列化类的错误。

时序类的错误（release 时机写错）不靠回读发现，靠槽位等待统计和肉眼。



### L3：显示侧回读

前两层都在内存这一侧。"显示控制器有没有真的读到这块内存"是它们回答不了的。

KMS 提供了一条路：writeback connector。它是一个特殊的 connector，不连显示器，而是把 CRTC 混合输出的那一帧写回到一块指定的 buffer 里。有了它，"屏幕上是什么"就变成了一块可以 `mmap` 读回来的内存。

用法上有几个特点值得记住。

**`WRITEBACK_FB_ID` 是一次性属性。** 内核在一次 commit 完成之后就把它消费掉，想抓下一帧必须重新设。这和 plane 的 `FB_ID` 完全不同，后者设了就一直生效。

**`WRITEBACK_OUT_FENCE_PTR` 的"值"是一个用户态指针。** 内核往那个地址写回一个 sync file 的 fd。属性值是指针这件事在 KMS 里只有这一处和 CRTC 的 `OUT_FENCE_PTR`，第一次见会以为自己写错了。拿到 fd 之后 poll 它，触发之后再去读 buffer，读早了就是在跟硬件抢。

**目标 buffer 的格式要取自 `WRITEBACK_PIXEL_FORMATS`。** 这是一个 blob 属性，里面是一串 fourcc。我们板子上它报了 19 个格式，里面**没有** XR24，有 AR24。

最后这一条让我们栽了一跤，值得展开讲，因为它的形状很典型。

我们的探针在枚举阶段老老实实把那 19 个格式打印了出来，然后在下一屏用写死的 XR24 去分配目标 buffer。结果 `TEST_ONLY` 被 `ENOTSUP` 拒绝。

危险的地方在于这个拒绝**看起来像**"这块硬件不支持 writeback 与显示共存"。差一点就把它记成一条硬件能力结论，而错误的能力结论会一路影响到第五步的验收方案。

两条推论。**约束一旦被读出来，就必须成为下一步的输入**，只打印不使用等于给了自己一个"我检查过了"的错觉。**把一个失败归因到"硬件不支持"之前，先确认请求本身是合法的**，`ENOTSUP` 说的是"这个请求我做不了"，不是"这类功能我没有"。

改掉格式之后，三个问题一次拿到答案：writeback connector 可以和显示 connector挂在同一个 CRTC 上（屏幕照常亮，同时抓到一份），翻页完成事件正常到达，回读的像素与写进去的**逐点精确相等**。第五步因此有了机器可判的验收判据。



## 故障注入：怎么验证判据本身有效

上一节建了一堆判据。这一节的问题是：怎么知道它们真的会拒绝该拒绝的东西？

一个从来没有被触发过的检查，和一段注释没有区别。

### 九条用例

我们在客户端里加了一个开关，让它按要求发出各种不合法的请求。每一条都必须满足同一组要求：服务端拒绝，给出能定位的错误，不崩溃，不上屏，不泄漏 fd。

| 用例 | 注入内容 | 预期在哪一层被挡住 |
| --- | --- | --- |
| bad-stride | 跨距报成实际的一半 | addfb2 的尺寸检查 |
| bad-offset | 偏移超出 buffer | addfb2 的尺寸检查 |
| missing-fd | 声明两个平面，只发一个 fd | 传输层的 fd 计数检查 |
| extra-fd | 声明一个平面，发两个 fd | 同上 |
| not-dmabuf | 发一个不是 dma_buf 的 fd | `PRIME_FD_TO_HANDLE` |
| tiny-buffer | 实际分配 64x64，声明成全屏 | addfb2 的尺寸检查 |
| bad-modifier | 编造一个私有 modifier | 我们自己的公告集合检查 |
| stale-header | 改掉协议版本号 | 消息头校验 |
| half-message | 消息体截断一半 | 消息头的 body_size 校验 |

`not-dmabuf` 这条挺有意思：随便打开一个字符设备，把那个 fd 当成 dma_buf 发过去。内核会拒绝，因为那个 `struct file` 上没有 dma_buf 的操作表。这条用例验证的是"服务端不会把一个来路不明的 fd 当成内存"。



### 沉默也是一种结果，而且是最重要的那种

我们第一版的故障注入模式是这样写的：发出不合法的请求，然后等服务端的ERROR 消息，收到就打印，退出。

`tiny-buffer` 这条跑起来挂住了。

原因是这条用例**从来没有被实现过**。枚举里有它，命令行里有它，注入函数里它落到了 `default: break`。于是它发出的是一条完全合法的请求，服务端收下、什么都不说，两边一起干等。

也就是说：**一个没有被发现的故障，表现成了一个挂住的程序。** 而"挂住"这个现象会把人引去查测试框架，不是查判据。

改法有两条。第一，把这条用例真的实现出来。第二，也是更重要的一条，故障模式的等待必须有超时；超时就打印一条明确的"故障未被发现"并以非零退出。

用例表必须有一个"未被发现"的显式结果，不能只有"被拒绝"和"崩溃"。



### 故障注入自己也会注入错

九条用例里有三条是错的，三种错法不一样。

第一种就是上面的 `tiny-buffer`，压根没实现。

第二种是 `extra-fd`。它和 `missing-fd` 共用了"把平面数改成 2"这一行代码，可多发一个 fd 之后数量反而对上了，于是拒绝理由变成了"平面 1 的 stride 是零"。拒是拒了，但打中的不是想打的那条判据。

**一个用例通过了，不等于它测了你以为的东西。** 只看退出码，这种错法永远不会暴露；必须人工核对每条用例的拒绝理由是不是预期的那一条。

第三种是 `bad-modifier`，那条是被测方的问题，上一节讲过了。



### 这一节的三条推论

- 每个用例都要人工核对拒绝理由，不能只看返回码
- 所有等待都要有超时，没有超时的等待会把测试失败伪装成工具故障
- 用例表里要有"未被发现"这个显式结果



## 记账：稳态每帧应该有几次 ioctl

内容判据回答"数据对不对"，记账回答"有没有多做事"。这两件事互相独立。



### 稳态预算

第二讲定下的稳态约束是：每帧一次 atomic commit，一次翻页事件，`add_fb` 和`prime_*` 的增量为 0。跨了进程之后这条不变。

不变的原因就是 CREATE_BUFFER 和 COMMIT 拆开了。所有的导入和 fb 注册都发生在握手之后的启动阶段，帧循环里只有提交和事件处理。

检查方式不是靠自觉。帧循环每秒核对一次计数增量，不为 0 就直接打 ERROR。

```
每秒:
    delta = 本秒的 ioctl 计数 - 上一秒的
    rebinds = delta.add_fb + delta.prime_fd_to_handle + delta.prime_handle_to_fd
    if rebinds != 0:
        LOG_ERROR("稳态里出现了 N 次 buffer 重绑定")
```

"每帧重新导入加 addfb2"是能跑的：画面正常，帧率正常，只是白白多三次 ioctl。不主动检查，没人会发现。



### 第一个统计窗口不算稳态

第一版这个检查每次运行都会报一条 ERROR。因为第一秒里包含着三块 buffer 的导入和 fb 注册，那是启动，不是稳态。

改法是把第一个窗口标记成启动窗口，打印它的实际数字，从第二个窗口开始才做稳态判定：

```
(启动窗口：3 块客户端 buffer，共 6 次导入/注册 ioctl，
 稳态预算从下一次报告开始生效)
```

这样既保留了信息，又不会污染告警。



### 退出时的配平

退出时要检查三组配对：

```
add_fb          对   rm_fb
prime_fd_to_handle  对   gem_close
create_dumb     对   destroy_dumb
```

外加导入表里的 handle 引用计数应该归零，两端 `/proc/self/fd` 的条目数应该回到启动时的水平。

关于配平表还有一条经验，第一讲学到的：**能进配平表的资源，必须有且只有一种获取方式、有且只有一种释放方式，两者一一对应。** DRM master 就不满足这个条件，它有隐式继承和显式 ioctl 两种获取方式，于是当年配平表报了一个假的"释放多于获取"。



### 帧率与丢帧

`FrameStats` 统计的是相邻两次翻页完成事件的间隔。60Hz 下期望是 16.666ms，超过 1.5 个周期算丢一帧。

跨进程之后有一个新的观察点：客户端的绘制时间现在不在合成器的控制之下。如果客户端画得慢，合成器手里就会没有 pending 的 buffer，这时候应该重复显示上一帧，而不是等。我们这一步的实现里，帧循环发现没有 pending 时就不提交，屏幕上停留的还是上一帧，帧率统计上也就不会出现翻页。

这是最简单的策略，也是正确的策略。第七步会在这上面做更细的事情：客户端慢了多少，是不是稳定地慢，要不要通知它降低目标帧率。



## 把一帧从头到尾走一遍

前面是分开讲的机制，这里把它们串成一条完整的时间线。两个进程，从启动到稳态，再到退出。

### 启动与握手

```
服务端                                   客户端
─────────────────────────────────────    ─────────────────────────────
open("/dev/dri/cardN")
枚举 connector / CRTC / plane
挑一条输出通路
分配一块自有的兜底 buffer 并注册 fb
取得 DRM master
完整 modeset，屏幕点亮，显示兜底帧
监听 socket
                                         connect
                                         发 HELLO（协议版本、我能怎么分配）
收到 HELLO
按本机探测结果决定推荐哪条分配路径
从 plane 的 IN_FORMATS 取候选 modifier
发 HELLO_ACK（尺寸、格式、推荐、候选）
                                         收到 HELLO_ACK
                                         按推荐打开设备
                                         分配 N 块 buffer
                                         每块导出一个 dmabuf fd
                                         为每块发一条 CREATE_BUFFER
收到 CREATE_BUFFER × N
校验 (format, modifier) 在公告集合里
PRIME_FD_TO_HANDLE
addfb2
记进 buffer id → fb id 的表
```

握手之后，服务端手里是 N 个可以随时挂到 plane 上的 fb，客户端手里是 N 块可以随时绘制的内存。**导入和注册到此为止，帧循环里不会再发生。**



### 稳态

```
客户端                                   服务端
─────────────────────────────           ────────────────────────────
挑一块空闲 buffer
（GBM 路径在这里 map）
画图案
写签名块（第 0 行前 32 个像素）
（GBM 路径在这里 unmap）
算签名的校验值
发 COMMIT(buffer id, 帧序号, 校验值)
标记这块 buffer 为占用
                                         收到 COMMIT
                                         记为 pending
                                         （前 N 帧：映射 dmabuf 回读比对）
阻塞等回向消息
                                         上一次翻页已完成，且有 pending：
                                           set_plane(pending 的 fb)
                                           atomic commit（非阻塞 + 翻页事件）
                                           submitted = pending
                                         poll(DRM fd, socket)
                                         收到翻页完成事件：
                                           released  = on_screen
                                           on_screen = submitted
                                           发 BUFFER_RELEASE(released)
                                           发 FRAME_DONE(帧序号, 翻页序号)
收到 BUFFER_RELEASE
把那块标记为空闲
收到 FRAME_DONE
帧计数加一，回到循环开头
```

这个循环里客户端和服务端各自阻塞在自己的等待上，没有轮询，没有睡眠固定时长。节拍完全由硬件的翻页事件驱动。



### 退出

```
客户端                                   服务端
────────────────────────────           ─────────────────────────────
达到帧数上限，或收到信号
关闭 socket，进程退出
（内核回收它的 fd 与 GEM 对象）
                                         socket 上读到 EOF
                                         提交兜底帧
                                         等这次翻页完成
                                         RmFB、归还 handle、关 fd
                                         打印内容判据结果
                                         打印计数与配平
                                         禁用 plane 与 CRTC
                                         释放 master
```

顺序不能反。上面讲过，在 on-screen 状态下 RmFB 会让内核去禁用 plane。



### 有几处值得停下来看

**服务端从头到尾没有碰过像素。** 除了打开 `--verify` 的前 8 帧回读之外，它做的全部事情是导入、注册、提交。零拷贝这个词的具体含义就是这个。

**客户端不知道 CRTC、plane、fb 的存在。** 它只知道自己要按某个尺寸和格式分配一块内存，画完发一条消息。下一讲换成真实的 wayland 客户端时，这个认知边界一模一样。

**两个进程的节拍靠 FRAME_DONE 同步。** 客户端画得快没用，它会卡在等空闲槽位上；画得慢也不会拖垮服务端，服务端会继续显示上一帧。这就是 wayland的 frame callback 在做的事情。



## 这一讲欠下的债：同步

第二讲结尾欠了一笔同步的债，这一讲让它变大了。

### 现在是怎么处理的

客户端画完之后，直接发 COMMIT。服务端收到之后，直接提交给内核。中间没有任何机制保证"画完了"这件事。

CPU 绘制的路径上，这没有问题。`memcpy` 返回的时候像素已经在内存里了，后面的 `DMA_BUF_IOCTL_SYNC` 结束访问也做了缓存刷新。

GPU 绘制的路径上就不一样了。GL 的绘制命令是异步的，`glDrawArrays` 返回只说明命令进了队列。第二讲的做法是在提交前调 `glFinish()`，让 CPU 阻塞到 GPU 干完为止。那是明知故犯，标了以后要删。

跨进程之后，这件事多了一层：**画的人和提交的人不是同一个进程。** 客户端的 `glFinish()` 只能保证它自己那边画完了，服务端无从验证。



### 隐式同步为什么不能依赖

有一种机制叫隐式同步：dma_buf 上挂着一个 reservation object，里面记着"谁在写这块内存"和"谁在读"。内核在提交显示时会去看这个对象，自动等待写操作完成。

这个机制在很多平台上确实工作。问题在于两点。

**不保证存在。** 挂不挂 fence 由驱动决定，跨设备路径上尤其没谱。

**不可观测。** 它成立的时候，效果和 `glFinish()` 一样；不成立的时候，症状是偶发的花屏。**分不出这两种情况的机制，不能作为正确性依据。**

蒙对了比错了更糟糕。错了会被立刻发现，蒙对了会在换一块板子的时候突然坏掉。



### 显式同步长什么样

第六步要做的事情，形状大致是这样：

```
客户端
    提交 GL 绘制命令
    导出一个 fence fd（EGL_ANDROID_native_fence_sync 或者 syncobj）
    发 COMMIT，把 fence fd 随消息一起发过去
    不等待，立刻开始画下一帧

服务端
    收到 COMMIT 和 fence fd
    把 fence fd 设成 plane 的 IN_FENCE_FD
    atomic commit
    内核会让显示硬件等这个 fence 触发之后再切换扫描地址
    CPU 全程不阻塞
```

反方向也一样。服务端向 CRTC 申请 `OUT_FENCE_FD`，拿到之后转成客户端的 release 信号。客户端等这个 fence 触发就能复用 buffer，不必等一条 BUFFER_RELEASE 消息。

这条路的收益是 CPU 不再需要在任何一侧阻塞等待 GPU。代价是要理解 fence 的生命周期和所有权，那是第六步的主题。

现在能做的是把位置留出来：COMMIT 和 BUFFER_RELEASE 的消息体里各有一个 flags 字段，其中一位留给"随消息携带 fence fd"。





## 这一步之后，wayland 会替换掉什么

这一讲自己造了一套协议。下一讲要把它换成真的。这一节把替换关系摆出来，顺带解释几个 wayland 的核心概念，因为它们的形状我们已经实现过一遍了。

### 对象与请求

wayland 是一套面向对象的协议。客户端连上之后先拿到 `wl_display`，从它拿到 `wl_registry`，registry 会广播服务端支持的全局对象。客户端 bind它需要的那些，之后所有的交互都在这些对象上进行。

我们的 HELLO 和 HELLO_ACK 做的就是这件事的极简版：交换版本，交换能力。换成真协议之后这两条消息消失，取而代之的是 registry 的广播和 bind。



### wl_surface 和 wl_buffer

`wl_surface` 是一块可见区域，一个窗口对应一个。`wl_buffer` 是一块具体的像素内存。

客户端的动作是 `attach` 一块 buffer 到 surface 上，标记 damage 区域，然后 `commit`。commit 之前的所有请求都只是记在待生效状态里，commit 那一刻一起生效。这个"待生效状态"和"当前状态"的双缓冲设计是 wayland 的核心原则，
它保证客户端永远不会显示出一个改到一半的状态。

我们的 COMMIT 消息就是 `wl_surface.attach` 加 `.commit` 的合并版。`wl_buffer` 对应我们的 buffer id 加那张导入表。

**`wl_buffer` 是长生命周期对象。** 客户端创建一次，反复 attach。这正是我们把 CREATE_BUFFER 和 COMMIT 拆开的原因，语义完全对得上，下一讲不需要改这里的模型。



### linux-dmabuf 与 feedback

`zwp_linux_dmabuf_v1` 是客户端把 dma_buf 变成 `wl_buffer` 的协议。流程是创建一个 params 对象，逐个平面 `add`（fd、平面索引、offset、stride、modifier 的 hi 和 lo），然后 `create` 或者 `create_immed`。

我们的 CREATE_BUFFER 就是这几个请求的合并版，字段一一对应。

`zwp_linux_dmabuf_feedback_v1` 是合成器告诉客户端该怎么分配的协议。它发一个格式表，再发若干个 tranche，每个 tranche 带一个设备标识和一组 (format, modifier) 索引，按优先级排列。客户端从最靠前的 tranche 里挑一个自己能做到的。

我们的 HELLO_ACK 是它的雏形。**决策发生在合成器侧**这一点已经在这一讲定下来了，下一讲换的是传输和数据结构。

有一件事这一讲刻意没做：**候选列表原样转发，不排序。** 排序是 tranche策略，属于下一讲。这一讲只负责把 plane 公告的那份集合完整传过去。



### frame callback 与 release

`wl_surface.frame` 请求注册一个回调，合成器在"现在适合画下一帧了"的时候触发它。我们的 FRAME_DONE 就是它。

`wl_buffer.release` 事件告诉客户端这块 buffer 可以复用了。我们的BUFFER_RELEASE 就是它，连"什么时候该发"的规则都一样。



### xdg-shell

这一讲完全没有涉及窗口的概念。`wl_surface` 只是一块像素，它有多大、放在哪里、是不是一个可以最小化的窗口，wayland 核心协议不管。这些交给 `xdg-shell`：`xdg_surface` 和 `xdg_toplevel` 描述一个桌面窗口，包括标题、最大化、全屏这些状态。

下一讲要实现的是最小的一套，够让标准客户端跑起来即可。



### 替换关系一览

| 这一讲 | 下一讲 |
| --- | --- |
| 自定义消息头加定长 body | wayland wire 格式，由 libwayland 处理 |
| SOCK_SEQPACKET | SOCK_STREAM（粘包交给库） |
| HELLO / HELLO_ACK | registry 与 `zwp_linux_dmabuf_feedback_v1` |
| CREATE_BUFFER | `zwp_linux_buffer_params_v1` |
| COMMIT | `wl_surface.attach` + `.commit` |
| BUFFER_RELEASE | `wl_buffer.release` |
| FRAME_DONE | `wl_surface.frame` |
| buffer id 到 fb id 的表 | 同样的表，key 换成 `wl_buffer` 指针 |
| 一个客户端一个 surface | 多客户端多 surface，加上场景图 |

传输层整个被替换掉，数据模型和生命周期规则原样保留。这是这一讲把接口按wayland 的形状设计的回报。



## 本讲小结

这一讲在链路中间切了一刀，把绘制和上屏拆到两个进程里。

机制上新增的东西不多：`SCM_RIGHTS` 传 fd，一套描述 buffer 的线格式，一条回向的 release 消息。PRIME 那一层第二讲已经压过了，这一讲没有再碰。真正的增量在别处。

**跨进程意味着跨信任边界。** 来自另一个进程的每一个字段都要当成可疑的，而内核只帮你挡住其中一部分。挡不住的那部分，判据得自己定，而最自然的判据就是"我公告过什么就接受什么"。

**跨进程意味着所有权要靠协议表达。** 同一个进程里靠调用顺序就能管住的生命周期，现在要变成消息。release 发早了会撕裂，发晚了会卡住，而两种症状都是间歇性的。

**跨进程意味着失败模式变多，而返回码一个都没变。** 四层 ioctl 校验没有一层碰过像素，所以内容判据必须自己造：画进像素里的签名，服务端侧的回读，以及显示侧的 writeback 回读。



下一讲把这套自造协议换成 wayland，让标准客户端连上来。那一讲的重点不在协议解析，而在多个 surface 同时存在之后，场景图和 plane 分配之间的关系。



## 自测题

答案在每题下面折叠段里，建议先自己想。

**1. 为什么不能把 GEM handle 直接发给另一个进程？**

GEM handle 的作用域是单个打开的设备文件。同一个数值在另一个 fd 上大概率指向别的对象，而且是一个真实存在的对象，所以不会报错，只会显示错误的内容。跨进程要传的是 dma_buf 的 fd。



**2. `sendmsg` 之后发送方应该关闭自己那份 fd 吗？什么时候关？**

应该关，在 `sendmsg` 成功返回之后。传输是复制一份引用而不是转移所有权，发送方不关的话引用计数永远不会降到能释放的程度。在 `sendmsg` 返回前就关则是另一个错误，那时内核还没为传输持有引用。



**3. 收到消息时发现平面数是 2 但只收到 1 个 fd，除了返回错误还要做什么？**

关掉已经收到的那个 fd。接收函数的契约是"要么返回持有全部 fd 的对象，要么一个都不留下"，任何一条提前返回的分支都要满足它。



**4. `MSG_CMSG_CLOEXEC` 不带会怎样？症状什么时候出现？**

收到的 fd 没有 close-on-exec，进程 fork 加 exec 时会带进子进程，那块显存永远不会被释放。症状是运行几小时之后显存耗尽，现场看不出原因。



**5. 为什么消息头里要放 `body_size` 和 `fd_count`，明明这两个数都能从别处
算出来？**

冗余就是判据。收发两侧对同一条消息理解不一致时这两个数会对不上，最常见的原因是两个二进制不是同一次构建的。不检查的话字段会读成垃圾值，而垃圾值落在合法区间时症状是画面不对而不是报错。



**6. 一块 NV12 的 buffer，两个平面在同一块 dma_buf 里，协议上应该发几个 fd？**

两个，同一个 dma_buf 的两个 fd，offset 不同。设计成"检测共享只发一个"会让所有权规则变成条件式的，出错方式从"忘了释放"变成"某种组合下忘了释放"。



**7. 客户端声明了一个编造的 modifier，`addfb2` 收下了。这说明什么？该怎么
处理？**

说明这一版驱动的 addfb2 路径没有校验 modifier。不能指望内核替你挡住跨信任边界进来的字段。合成器应当自己比对：客户端送来的 (format, modifier) 必须在自己公告过的集合里。



**8. 第 N 帧翻页完成时，应该释放哪一块 buffer？为什么？**

第 N-1 帧用的那块。一块 buffer 在被另一块换下来之前一直在被扫描。释放刚上屏的那块会让客户端在正在扫描的内存上作画，症状是间歇性撕裂。



**9. 客户端准备了 3 块 buffer，为什么它几乎每帧都要等一次 release？这是故障吗？**

服务端最多同时持有三块：on-screen、submitted、pending。三块的时候客户端空闲槽位恒为 0。这是预期行为，帧率不受影响，只是绘制和呈现无法重叠。想要重叠就给四块。



**10. 客户端没有空闲槽位时，为什么不能临时多分配一块？**

新分配会掩盖 release 时机写错的问题，把"卡住"这种明显的症状变成"内存慢慢涨"这种要跑很久才发现的症状。



**11. 服务端读到 socket EOF，客户端的 buffer 正在被扫描。释放顺序是什么？**

先提交一帧自有的兜底 buffer，等这次翻页完成，再 RmFB 和归还 handle。在 on-screen 状态下 RmFB 会让内核去禁用 plane 或 CRTC。



**12. `PRIME_FD_TO_HANDLE`、`addfb2`、`TEST_ONLY`、翻页事件四层都通过了，能证明客户端画的内容出现在屏幕上吗？**

不能。这四层没有一层碰过像素。要靠独立于返回码的内容判据。



**13. 帧签名为什么必须画在第 0 行第 0 列？**

放在中间的话，stride 算错时签名块的位置会跟着一起漂移，按错误的 stride去读反而能读到正确的签名。判据要放在错误会破坏它的位置上。



**14. 帧签名里的 run_nonce 有什么用？**

让上一次运行残留在显存里的内容无法冒充本次的正确结果。复用显存的板子上这类误判真实存在，而且第一次遇到会以为链路是通的。



**15. 服务端映射 dmabuf 回读之前必须做什么？不做会怎样？**

发 `DMA_BUF_IOCTL_SYNC` 的 START，读完发 END。不做的话在有缓存一致性问题的平台上会读到陈旧数据，而且是间歇性的。



**16. `mmap(dmabuf_fd)` 失败了，应该当成错误还是当成什么？**

当成一条能力判断。它需要导出方实现了 dma-buf 的 mmap 操作，有的驱动不实现，有的在策略上拒绝。正确的处理是降级并明确打印"这一层校验拿不到"，不要静默少一层。



**17. `WRITEBACK_FB_ID` 和 plane 的 `FB_ID` 在语义上有什么关键区别？**

前者是一次性属性，内核在一次 commit 完成后就消费掉，想抓下一帧必须重设。后者设了就一直生效。



**18. 一条故障注入用例跑完，程序挂住了。最可能是什么情况？**

注入的故障没有被发现，服务端收下了这条"不合法"的请求，什么都不说，两边一起等。用例表必须有"未被发现"这个显式结果，所有等待都要有超时。



**19. 稳态里每帧应该有几次 `add_fb`？为什么第一秒的统计不算数？**

零次。所有导入和注册都在握手阶段完成。第一秒里包含启动阶段的导入，把它计进稳态判定会导致每次运行都报一条假的告警，而每次都出现的告警等于没有告警。



**20. `gbm_bo_map()` 拿到的映射能不能一直持有反复写？dumb buffer 的 mmap 呢？**

GBM 的不能，实现可以给一块中转缓冲，真正的拷回发生在 `unmap`。dumb buffer的 mmap 给的就是 GEM 对象背后那块内存，可以一直用。两者类型长得一样，语义不同。

| 术语 | 含义 |
| --- | --- |
| SCM_RIGHTS | Unix domain socket 的辅助数据类型，用于在进程间传递 fd |
| 辅助数据 | `sendmsg` / `recvmsg` 里与数据载荷分开的控制信息，承载 fd 等内核对象引用 |
| SOCK_SEQPACKET | 保消息边界、保可靠、保顺序的 socket 类型 |
| dma_buf | 内核里代表一块可被多个设备共享的内存的对象，导出后表现为一个 fd |
| PRIME | DRM 里 dma_buf 的导出与导入接口 |
| GEM handle | 一个 GEM 对象在某个打开的设备文件里的编号，作用域仅限该 fd |
| modifier | 描述内存排布的 64 位值，线性或者某种平铺压缩格式 |
| fourcc | 四字符格式码，例如 `XR24` 表示 XRGB8888 |
| plane | KMS 里的图层，显示控制器扫描的最小单位 |
| framebuffer | KMS 里对一块内存加上格式描述之后的对象，plane 引用它 |
| writeback connector | 不连显示器的 connector，把 CRTC 的输出写回到一块 buffer |
| 一次性属性 | 内核消费一次之后自动清零的 KMS 属性，`WRITEBACK_FB_ID` 是其中之一 |
| out fence | 内核返回给用户态的同步对象 fd，触发表示某个操作完成 |
| 零拷贝 | 像素从被画出来到被扫描出光，没有被复制过 |
| 稳态 | 帧循环进入稳定状态之后的每帧行为，不含启动阶段 |

## 附录 D：几个容易混淆的点

**fd 数值在两个进程里不同，这正常吗？** 

正常，而且几乎必然不同。fd 是进程私有的索引，内核在接收方找一个空位装引用。两端数值相同只是巧合。



**dma_buf 传过去之后，发送方还能继续用吗？**

能。双方持有的是同一个内核对象的引用，谁都可以映射、可以导入。协议层面的"这块 buffer 现在归谁用"是我们自己定的规则，内核不管。



**`wl_shm` 和 `linux-dmabuf` 是替代关系吗？** 

不是替代，是分工。前者是保底通道，客户端没有可用的 GPU 时也能画出东西；后者是零拷贝主路。真实的合成器两条都要支持。



**writeback 抓到的内容和屏幕上完全一样吗？** 

取决于抓取点。写回可以发生在显示流水线的不同位置，有的驱动提供属性来选。抓取点在色彩转换之前的话，读回来的值和写进去的会不一样，那时候判据要换成结构比对而不是逐点相等。



**内容判据能替代肉眼吗？** 

不能完全替代。签名判据能证明像素落在了那块内存里，writeback 能证明显示控制器读到了它。"这个画面对不对"仍然要人看。判据的价值在于把那些人眼分辨不出来的错误变成一条明确的失败。
