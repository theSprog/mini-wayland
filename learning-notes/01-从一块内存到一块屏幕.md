## 一、先问一个问题：屏幕上的像素是从哪来的

在写任何代码之前，先把一个问题想清楚：

**当你在屏幕上看到一个红色的点，这个"红色"是以什么形式、经过哪些环节，从程序变成光的？**

一个粗略但方向正确的回答是：

```
程序写内存 → 显示控制器周期性地读这块内存 → 通过物理链路发给显示器 → 显示器点亮像素
```

这句话里藏着四个需要展开的问题：

1. **"内存"是哪块内存？** 普通的 `malloc` 出来的内存行吗？
2. **"周期性地读"是什么周期？** 谁决定的？
3. **"显示控制器"是什么？** 它和 GPU 是一个东西吗？
4. **程序怎么告诉硬件"读这块内存"？** 这个"告诉"是什么形式？

这四个问题的答案，构成了整个显示栈的骨架。本讲会把它们一一拆开。

先给出简短版本，后面细讲：

1. 必须是**显示控制器能直接访问的物理连续（或经过 IOMMU 映射）的内存**，由内核的图形内存管理器分配。普通 `malloc` 的内存不行。
2. 周期由**显示模式（display mode）**决定。1920x1080@60Hz 意味着每秒 60 次，每次从头到尾扫一遍整块内存。
3. 显示控制器（Display Controller / DPU / CRTC）和 GPU 是**两个不同的硬件单元**，虽然常常封装在同一颗芯片里。GPU 负责"算出像素"，显示控制器负责"把像素送出去"。
4. 通过 `ioctl` 向内核的 DRM 子系统下发命令。



## 二、显示的物理层：扫描、同步与消隐

要理解上层的软件抽象，必须先理解下层的物理约束。很多看起来奇怪的软件设计，根源都在物理层。

### 2.1 扫描：显示是一个流式过程

显示器**不是**"整屏一次性刷新"的。它是**逐行、逐像素**地被驱动的。

想象显示控制器内部有一个指针，它从帧缓冲区（framebuffer）的第一个像素开始，按固定的时钟频率往后走：

```
像素时钟每跳一次，输出一个像素
一行输出完，回到行首，输出下一行
一屏输出完，回到帧首，开始下一帧
```

这个过程叫**扫描（scanout）**。驱动这个过程的时钟叫**像素时钟（pixel clock）**。

对于 1920x1080@60Hz：

```
每帧像素数 ≈ 1920 × 1080 = 2,073,600
每秒帧数 = 60
每秒像素数 ≈ 124,416,000 ≈ 124 MHz
```

但实际的像素时钟是 **148.5 MHz**，比算出来的多了 19%。多出来的是什么？



### 2.2 消隐期：为什么 htotal > hdisplay

这个问题的答案来自 CRT（阴极射线管）时代。CRT 用电子束打在荧光屏上成像，电子束扫完一行要**回到行首**，这个"回扫"需要时间；扫完一屏要**回到左上角**，这个"垂直回扫"需要更多时间。回扫期间电子束必须关闭，否则会在屏幕上划出亮线。

这段"什么都不输出"的时间叫**消隐期（blanking period）**：

- **水平消隐（horizontal blanking）**：每行末尾的回扫时间
- **垂直消隐（vertical blanking）**：每帧末尾的回扫时间

于是一个显示模式的时序被描述成这样：

```
                    hdisplay        hsync_start   hsync_end        htotal
                       |                 |            |              |
     ┌─────────────────┤─────────────────|────────────|──────────────|
     │   可见像素区      │  前肩           │  同步脉冲    │  后肩        │
     │   1920 pixels   │  (front porch)  │  (hsync)   │ (back porch) │
     └─────────────────┴─────────────────┴────────────┴──────────────┘
     0              1920              2008         2052         2200
```

垂直方向同理：

```
vdisplay = 1080, vsync_start = 1084, vsync_end = 1089, vtotal = 1125
```

现在重新算像素时钟：

```
htotal × vtotal × 刷新率 = 2200 × 1125 × 60 = 148,500,000 = 148.5 MHz  ✓
```



**关键结论**：

> 帧率不是 `1 / (hdisplay × vdisplay)` 算出来的，
> 而是 `pixel_clock / (htotal × vtotal)`。

这就是为什么在代码里必须这样算刷新率：

```cpp
// clock 单位是 kHz，所以乘 1e6 得到 mHz（毫赫兹）
uint32_t refresh_mhz = (clock * 1000000ULL) / (htotal * vtotal);
```

而**不能**去读 `drmModeModeInfo::vrefresh` 字段。那个字段是四舍五入到整数 Hz 的（60 而不是 59.94），拿它算帧间隔会稳定偏差 0.1%，一分钟就差一帧。做帧节拍控制（frame pacing）时这个误差是致命的。



### 2.3 VBlank：一个至关重要的时间窗口

垂直消隐期（VBlank）是整个显示系统里最重要的一个时间概念。

**在 VBlank 期间，显示控制器不在读取可见像素。** 这意味着：

> 如果你要切换显示控制器读取的内存地址，VBlank 是唯一安全的时刻。

为什么？考虑不在 VBlank 切换会发生什么：

```
显示控制器正在扫描第 500 行，读的是 buffer A
                ↓
        此时把地址换成 buffer B
                ↓
第 501 行开始读的是 buffer B
```

结果：屏幕上半部分是 A 的内容，下半部分是 B 的内容。中间有一条明显的"接缝"。
这就是**画面撕裂（tearing）**。

```
    ┌─────────────────┐
    │                 │
    │   buffer A 的   │
    │   上半帧         │
    ├─────────────────┤  ← 撕裂线，在扫描到第 500 行时切换造成
    │   buffer B 的   │
    │   下半帧         │
    │                 │
    └─────────────────┘
```

所以：**所有的帧提交，本质上都是"请在下一个 VBlank 到来时切换地址"**。这个操作有个名字：**page flip（页翻转）**。

VBlank 还有一个衍生作用：它是一个**天然的时间基准**。显示硬件每 16.67ms 产生一次 VBlank 中断，内核记录下这个中断的精确时间戳。这个时间戳是"这一帧真正开始出光"的物理时刻，是所有帧节拍控制的锚点。



### 2.4 隔行扫描与其他历史包袱

顺带一提几个会在代码里遇到的 flag：

- **INTERLACE（隔行扫描）**：一帧分两场，先扫奇数行再扫偶数行。电视时代的带宽优化手段。算刷新率时要乘 2（因为一个刷新周期只扫一半的行）。
- **DBLSCAN（倍扫）**：每行扫两遍，用来在高频显示器上显示低分辨率内容。算刷新率时要除 2。
- **vscan**：每行重复 vscan 次。

这些在现代显示器上基本用不到，但 KMS 的 API 会暴露它们，所以刷新率的计算函数必须处理：

```cpp
uint64_t numerator = clock * 1000000ULL;
if (flags & DRM_MODE_FLAG_INTERLACE) numerator *= 2;
if (flags & DRM_MODE_FLAG_DBLSCAN)   numerator /= 2;
if (vscan > 1)                        numerator /= vscan;
return numerator / (htotal * vtotal);
```

写不写这几行的区别是：在一台接了老电视的设备上，你的帧节拍会全错。



### 2.5 物理链路：像素怎么从芯片走到显示器

CRTC 输出的是一串**并行的像素数据加上同步信号**。这个形式没法直接沿着一根线传几米远，需要 encoder 把它转换成某种串行的、抗干扰的、有时钟恢复能力的格式。主流的几种：

- **VGA（模拟）**

    > 已经基本淘汰，但概念上最直白：三根线分别传 R、G、B 的**模拟电压**，另外两根传 HSYNC 和 VSYNC 方波。显示器直接用电压驱动电子枪。没有任何编码，也没有任何数字协议——所以它无法传递色深、色域这类元信息，也无法做加密或音频。

- **TMDS（HDMI / DVI）**

    > TMDS = Transition Minimized Differential Signaling，最小化跳变差分信号。它是数字的：三对差分线传 R、G、B，第四对传时钟。"最小化跳变"是指编码时会把 8 位数据映射成 10 位，选择跳变次数最少的那种编码，以降低电磁辐射和码间干扰。多出来的 2 位还用来做直流平衡。同步信号和音频**塞进消隐期**传输——这是消隐期在数字时代的新用途。这也解释了为什么 HDMI 能一根线传音视频。

- **DisplayPort（分组化）**

    > DP 和前两者有本质区别：它是**基于分组（packet）**的，更像网络协议而不像视频线。像素数据被切成小包，和音频包、控制包一起在 1/2/4 条 lane 上传输。
    > 好处是：
    >
    > - **带宽可协商**。链路训练（link training）时两端商定用几条 lane、每条跑多快。
    >
    > - **可以做 MST**（Multi-Stream Transport）——一根线上挂多台显示器，
    >   每台一条独立的流。这在 KMS 里表现为 `DRM_MODE_ENCODER_DPMST`。
    >
    > - **DSC**（Display Stream Compression）可以在链路上做视觉无损压缩，
    >   让带宽不够的链路也能跑 8K。

- **MIPI DSI（嵌入式）**

    > 手机、平板、嵌入式设备的内屏几乎都用 DSI。特点是低功耗、引脚少，而且支持**命令模式**——显示控制器可以把一帧数据写进屏幕自带的显存（GRAM），然后屏幕自己刷新。这样静态画面时主控可以完全休眠。

- **eDP（embedded DisplayPort）**

    > 笔记本内屏。就是 DP，但省掉了热插拔相关的部分，加了 PSR（Panel Self Refresh）等省电特性。
    >
    > 在 KMS 里，这些差异体现为 `Encoder` 的 `type` 字段：
    >
    > ```c
    > DRM_MODE_ENCODER_DAC      // VGA
    > DRM_MODE_ENCODER_TMDS     // HDMI / DVI
    > DRM_MODE_ENCODER_LVDS
    > DRM_MODE_ENCODER_DSI      // MIPI DSI
    > DRM_MODE_ENCODER_DPMST    // DisplayPort MST
    > DRM_MODE_ENCODER_VIRTUAL  // 虚拟（writeback、虚拟显示器）
    > ```
    >
    > 以及 `Connector` 的 `type` 字段（`DRM_MODE_CONNECTOR_HDMIA`、
    > `_DisplayPort`、`_eDP`、`_DSI` 等）。



**对合成器的实际影响**：几乎没有。这正是 KMS 抽象的价值——用户的代码不需要知道输出是 HDMI 还是 DSI，差异被 encoder 和 driver 吸收了。唯一会有影响上来的是：

- **模式列表不同**。DSI 屏通常只有一个固定模式；HDMI 显示器有几十个。
- **热插拔行为不同**。内屏永远 connected；HDMI 会插拔。
- **链路带宽约束**。这会体现为某些高分辨率+高刷新率的组合在`TEST_ONLY` 时被拒绝。



### 2.6 EDID 与热插拔检测

显示器怎么告诉主机"我支持哪些模式"？

**DDC / EDID**

HDMI 和 DP 的接口里有两根线是 I2C 总线（叫 DDC，Display Data Channel）。显示器上挂着一颗小 EEPROM，里面存着 **EDID**——一块 128 字节（可以扩展到多个 128 字节块）的结构化数据，描述：

```
厂商 ID、产品码、序列号、生产日期
EDID 版本
基本显示参数：数字/模拟、色深、物理尺寸（cm）、gamma
色度坐标（色域）
已建立的时序（一组标准分辨率的位图）
标准时序（8 组）
详细时序描述符（最多 4 个，第一个通常是原生分辨率）
扩展块（CEA-861：音频能力、HDMI 特有功能、更多时序）
```

内核读到 EDID 之后，把它解析成 `drmModeModeInfo` 的列表，这就是你在 connector 上看到的模式列表。EDID 原始数据也作为一个 blob 属性暴露出来：

```bash
sudo cat /sys/class/drm/card0-HDMI-A-1/edid | edid-decode
```

**为什么"探测 connector 状态"会阻塞几十毫秒**，现在就清楚了：
它要走一遍 I2C 事务读 128+ 字节。I2C 是慢速总线（标准模式 100kHz），读一个 EDID 块就要毫秒级；如果显示器没接，还要等超时。

这就是 `drmModeGetConnector()`（强制探测）和`drmModeGetConnectorCurrent()`（读内核缓存）区别的物理来源。



**HPD（Hot Plug Detect）**

接口里还有一根 HPD 引脚。插上显示器时它被拉高，产生一个中断。内核收到中断后：

1. 重新探测 connector 状态
2. 重新读 EDID
3. 通过 **udev uevent** 通知用户态

用户态的显示服务器监听这个事件，然后重新枚举资源、重新配置输出。这就是"插上 HDMI 线，屏幕自动亮起来"的完整链路。

监听方法：

```
udev_monitor = udev_monitor_new_from_netlink(udev, "udev")
udev_monitor_filter_add_match_subsystem_devtype(udev_monitor, "drm", NULL)
udev_monitor_enable_receiving(udev_monitor)
fd = udev_monitor_get_fd(udev_monitor)
# 把 fd 加进事件循环，可读时重新枚举
```

**重要推论**：任何缓存下来的 KMS 资源快照，在热插拔后都可能失效。这是显示服务器里一类经典 bug 的来源——保存了一个 connector 指针，热插拔后对象已经被重建，指针悬垂。

我们的实现用一个**代号（generation）**来处理这件事：

```cpp
enum class Generation : uint64_t {};

// 每次 rescan() 递增
// 所有对外暴露的指针只在同一个 generation 内有效
// 计算出的"输出通路"记录自己是哪一代算的，用之前校验
```

不匹配就返回一个明确的错误，而不是悄悄地用一个悬垂指针。



### 2.7 从时序参数到一条 modeline

把前面的内容合起来，看一个真实的 modeline：

```
1920x1080 60.000 Hz  h: 1920 2008 2052 2200  v: 1080 1084 1089 1125
                     clock 148500 kHz  flags +hsync +vsync  type preferred
```

逐项解读：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `hdisplay` | 1920 | 可见宽度 |
| `hsync_start` | 2008 | 从第 1920 到 2008 是**前肩**（88 像素） |
| `hsync_end` | 2052 | 从 2008 到 2052 是**同步脉冲**（44 像素） |
| `htotal` | 2200 | 从 2052 到 2200 是**后肩**（148 像素） |
| `vdisplay` | 1080 | 可见高度 |
| `vsync_start` | 1084 | 垂直前肩 4 行 |
| `vsync_end` | 1089 | 垂直同步脉冲 5 行 |
| `vtotal` | 1125 | 垂直后肩 36 行 |
| `clock` | 148500 | 像素时钟，kHz |
| `+hsync/+vsync` | | 同步脉冲的极性是正的 |

验算：`2200 × 1125 × 60 = 148,500,000` ✓

**消隐开销**：`(2200×1125 - 1920×1080) / (2200×1125) = 16.2%`。
也就是说，有 16% 的时间和带宽是"浪费"在消隐上的。这在 CRT 时代是物理必需，在今天纯粹是兼容性包袱。所以 DisplayPort 之类的现代接口支持**减少消隐**（Reduced Blanking）的时序，把开销压到 5% 以下。

你会在模式列表里看到同一个分辨率有多个不同刷新率/不同时序的条目，区别就在这里。

**为什么这些细节对写合成器的人重要？**

1. 帧时长必须用 `htotal × vtotal / clock` 算，前面强调过。
2. 消隐期的长度决定了"从 VBlank 开始到下一帧第一个可见像素"有多少时间。这是**提交截止时间**的物理基础，如果你在 VBlank 开始后才提交，只要赶在可见区开始前完成就还来得及。
3. 做 VRR（可变刷新率）时，调整的正是 `vtotal`，拉长垂直消隐来延长帧时间。



## 三、显示控制器的内部结构

现在来看第三个问题：显示控制器是什么。

### 3.1 它和 GPU 不是一回事

在一颗现代 SoC 或显卡里，至少有两个独立的硬件单元：

| 单元 | 职责 | 别名 |
| --- | --- | --- |
| **GPU** | 执行着色器，把三角形和纹理算成像素，结果写进内存 | 3D engine, render engine |
| **显示控制器** | 周期性地从内存读像素，做合成/缩放/色彩转换，输出到物理链路 | DPU, Display Engine, CRTC, VOP |

它们**不共享执行流水线**。GPU 可以完全空闲，而显示控制器仍在以 60Hz 扫描；反过来，GPU 可以满负荷渲染，而显示控制器输出的还是上一帧。

两者通过**内存**耦合：GPU 写，显示控制器读。这也是为什么"同步"在这个系统里如此重要——你必须保证显示控制器不会读到 GPU 还没写完的内容。



### 3.2 显示控制器的数据通路

一个典型的现代显示控制器长这样：

```
   显存里的若干块 buffer
   ┌──────┐  ┌──────┐  ┌──────┐
   │ FB 1 │  │ FB 2 │  │ FB 3 │
   └───┬──┘  └───┬──┘  └───┬──┘
       │         │         │
       ▼         ▼         ▼
   ┌────────┐┌────────┐┌────────┐
   │ Plane 0││ Plane 1││ Plane 2│   ← 每个 plane 独立读取一块 buffer
   │Primary ││Overlay ││ Cursor │      可以裁剪、缩放、格式转换
   └────┬───┘└────┬───┘└────┬───┘
        │         │         │
        └─────────┼─────────┘
                  ▼
            ┌───────────┐
            │  Blender  │              ← 按 Z 序混合，处理透明度
            └─────┬─────┘
                  ▼
            ┌───────────┐
            │   CRTC    │              ← 产生时序（htotal/vtotal/pixel clock）
            │  时序发生器 │                 做 gamma 校正
            └─────┬─────┘
                  ▼
            ┌───────────┐
            │  Encoder  │              ← 把并行像素流编码成物理信号
            │           │                 (TMDS for HDMI, DP lanes, MIPI DSI...)
            └─────┬─────┘
                  ▼
            ┌───────────┐
            │ Connector │              ← 物理接口
            │           │                 (HDMI 口、DP 口、内置屏的排线)
            └─────┬─────┘
                  ▼
              显示器
```

这五个概念（Plane / CRTC / Encoder / Connector / Framebuffer）就是 KMS 的对象模型。它们不是软件抽象，它们直接对应硬件里的功能块。



### 3.3 名字的历史包袱

这些名字都有点古怪，因为它们来自更早的时代：

- **CRTC** = **C**athode **R**ay **T**ube **C**ontroller，阴极射线管控制器。现在早就没有阴极射线管了，但这个名字沿用下来指代"时序发生器"。你可以把它理解成 **一路显示输出的时序引擎**。一块显卡有几个 CRTC，就最多能同时驱动几个独立画面的显示器。
  
- **Plane**（平面）：也叫 layer、window、pipe（不同厂商叫法不同）。它是"一层图像"。硬件能同时读取多个 plane 并混合，这个能力叫硬件合成（hardware composition）。Plane 分三类：
  - **Primary**：主平面，通常是全屏的背景层。每个 CRTC 至少有一个。
  - **Overlay**：叠加层，可以放在主平面之上。视频播放常用它，硬件可以直接扫描 NV12 格式的 YUV 数据，省掉一次 CPU 或 GPU 的色彩转换。
  - **Cursor**：鼠标指针专用。硬件光标的好处是移动鼠标不需要重绘整个屏幕。
  
- **Encoder**（编码器）：把 CRTC 输出的并行像素流转换成物理传输格式。HDMI 用 TMDS 编码，DisplayPort 用自己的 lane 协议，内置屏可能用 MIPI DSI。
  
- **Connector**（接口）：物理连接器。它知道显示器插没插、显示器支持哪些模式（通过 EDID 读取）、物理尺寸多大。
  
- **Framebuffer**（帧缓冲）：注意这里指的是 **KMS 对象**，不是"一块内存"。它是"一块内存 + 宽高 + 像素格式 + 行跨距"的**打包描述**，是显示控制器能理解的形式。



### 3.4 拓扑不是全连接的

一个很容易的误解：**不是任意 Connector 都能接任意 CRTC**。

硬件内部的连线是固定的。可能的情况：

```
CRTC 0 ──┬── Encoder A ── Connector: eDP（内置屏）
         └── Encoder B ── Connector: DSI

CRTC 1 ──┬── Encoder C ── Connector: HDMI
         └── Encoder B ── Connector: DSI      ← DSI 两个 CRTC 都能挂
```

KMS 用一个**位图**来表达这个约束：每个 Encoder 有一个 `possible_crtcs` 字段，第 n 位为 1 表示"这个 encoder 可以接第 n 个 CRTC"。

注意这个 n 是 CRTC 在资源数组里的下标，不是 CRTC 的 ID。这是一个非常容易写错的地方。假设：

```
drmModeRes::crtcs[] = { 31, 84 }      // 两个 CRTC，ID 分别是 31 和 84
HDMI 的 encoder.possible_crtcs = 0x2  // 二进制 10，即第 1 位
```

`0x2` 的第 1 位为 1，对应 `crtcs[1]`，也就是 **CRTC ID 84**。如果你写了"取第一个 CRTC"，会拿到 ID 31，然后内核在提交时返回 `-EINVAL`，而且不会告诉你为什么。

所以在我们的实现里，`CrtcIndex`（下标）和 `CrtcId`（ID）是**两个不同的类型**，互相赋值编译不过：

```cpp
enum class CrtcId : uint32_t {};
enum class CrtcIndex : uint32_t {};

class PossibleCrtcs {
public:
    constexpr bool contains(CrtcIndex idx) const noexcept {
        const uint32_t bit = static_cast<uint32_t>(idx);
        return bit < 32u && ((mask_ >> bit) & 1u) != 0u;
    }
private:
    uint32_t mask_ = 0;
};
```

`contains()` 只接受 `CrtcIndex`，把 `CrtcId` 传进去是编译错误。类型系统在这里替我们挡住了一整类难查的 bug。



### 3.5 合成到底是什么

"合成（composition）"这个词在图形领域用得很多，先把它定义清楚。

**合成 = 把多个图层按某种规则叠成一张图。**

最基本的规则是 **alpha 混合（alpha blending）**。给定上层颜色 $C_s$（source，源）和下层颜色 $C_d$（destination，目标），以及上层的不透明度
$\alpha$：

```
结果 = α × C_s + (1 - α) × C_d
```

这叫 **source-over** 运算，是最常用的一种。α = 1 时完全遮挡，α = 0 时完全透明。

一个典型的桌面画面需要合成的图层：

```
┌────────────────────────────────┐
│  鼠标光标                       │  最上层
├────────────────────────────────┤
│  下拉菜单（带阴影，半透明）        │
├────────────────────────────────┤
│  前台窗口                       │
├────────────────────────────────┤
│  后台窗口（被部分遮挡）           │
├────────────────────────────────┤
│  桌面壁纸                       │  最下层
└────────────────────────────────┘
```

**谁来做这个合成？** 有三种可能：

- **方式一：CPU 合成。** 

    遍历每个像素做混合。1080p 有 200 万像素，每个像素几次乘加，还要跨图层读内存。现代 CPU 能做，但功耗高、延迟大，而且会挤占应用的 CPU 时间。1990 年代的做法。

- **方式二：GPU 合成。**

    把每个图层作为纹理，画成一个个带纹理的矩形，让 GPU 的混合单元做 alpha 混合，结果渲染到一张输出纹理，再把这张纹理交给显示控制器扫描。

    这是今天绝大多数合成器的默认路径。优点是**万能**——任意变换、任意特效、任意数量的图层都能做。缺点是要唤醒 GPU、要额外一次全屏的读写。

- **方式三：硬件平面合成（hardware overlay）。**
    把图层直接交给显示控制器的多个 plane，让**扫描输出的过程本身**完成混合。前面画过的那张图就是这个：

    ```
    Plane 0 ─┐
    Plane 1 ─┼→ Blender → CRTC → 输出
    Plane 2 ─┘
    ```

    - 优点巨大：
        1. **零额外内存带宽**。像素只被读一次（扫描时），没有中间结果。
        2. **GPU 可以完全休眠**。播放视频时这能省下大量功耗。
        3. **延迟更低**。少一次"渲染到中间纹理再扫描"的往返。
    - 缺点是**约束多**：
        1. plane 数量有限（通常每个 CRTC 2~8 个）
        2. 缩放能力有限（可能只支持整数倍，或有最大缩放比）
        3. 格式支持有限（cursor plane 通常只支持 ARGB8888）
        4. 有总带宽上限（同时开太多 plane 会超）
        5. Z 序可能固定（不是所有硬件都有 `zpos` 属性）



### 3.6 为什么硬件平面调度是合成器的核心

合成器面对的问题是一个**在线的资源分配问题**：

> 给定当前屏幕上的 N 个图层，以及硬件的 M 个 plane 和一堆约束，决定哪些图层直接走硬件 plane、哪些交给 GPU 合成。

而且要求：**每帧都可能重算**（窗口在移动、视频在播放、有窗口被关掉）。

典型的启发式策略：

```
优先级排序：
  1. 全屏且不透明的顶层窗口     → Primary plane（直接扫描，零拷贝）
  2. 视频层（YUV 格式）         → Overlay plane（省掉色彩转换）
  3. 鼠标光标                  → Cursor plane（移动时不重绘全屏）
  4. 剩下的所有图层             → GPU 合成到一张纹理，再走一个 plane

然后：
  构造 atomic 请求
  TEST_ONLY 试探
  如果被拒 → 把最不划算的那个图层挪回 GPU 合成，重试
```

这个"试探—降级"的循环，正是 `TEST_ONLY` 存在的意义。**硬件的约束太复杂，用户态没法准确建模，只能问内核。**

举个具体的例子说明收益。全屏播放 1080p60 视频：

| 方案 | 每帧的内存访问 |
| --- | --- |
| GPU 合成 | 读 YUV 3MB + 写 RGB 8MB + 扫描读 8MB = **19MB** |
| Overlay 直出 | 扫描读 YUV 3MB = **3MB** |

每秒 60 帧，差距是 1.14 GB/s vs 0.18 GB/s。在移动设备上，这个差别直接反映为续航。



### 3.7 一个容易混淆的点：Framebuffer 的三种含义

"framebuffer" 这个词在不同语境下指三个不同的东西，很容易搞混：

1. **概念上的帧缓冲**：存放一帧像素的那块内存。
2. **KMS 的 framebuffer 对象**：`fb_id`，是"内存 + 格式描述"的打包。本文里说 framebuffer 默认指这个。
3. **Linux 的 fbdev 子系统**：`/dev/fb0`，一个古老的、比 DRM 更早的显示接口。它只支持单缓冲、不支持多平面、不支持模式设置的细粒度控制。

> fbdev 现在基本只作为 DRM 的一个兼容层存在（`CONFIG_DRM_FBDEV_EMULATION`），用来让老程序和内核控制台能工作。新代码不应该用 fbdev。
>
> 如果你在网上搜"Linux 显示编程"，很可能搜到大量 fbdev 的教程。那些内容对理解现代显示栈没有帮助，甚至有害，fbdev 没有 plane、没有 atomic、没有显式同步的概念。
>



## 四、Linux 图形栈全景

有了硬件模型，现在看软件是怎么组织的。

### 4.1 X11 的模型和它的问题

在 Wayland 之前，Linux 桌面用的是 **X Window System（X11）**。它的架构是：

```
应用程序 ──(X 协议)──> X Server ──> 硬件
```

X Server 是一个独立进程，它：
- 拥有显示硬件
- 接收所有输入事件并分发
- 为应用程序提供绘图 API（画线、画矩形、贴图……）
- 管理窗口

问题在于，X11 设计于 1984 年，那时候的假设和今天完全不同：

1. **网络透明**：X 协议设计成可以跨网络。今天几乎没人用这个功能，但它导致了一大堆间接层。
2. **服务端绘图**：X Server 提供绘图原语。今天所有应用都用自己的渲染引擎（Cairo、Skia、GPU 渲染），只把最终位图交给 X。X 的绘图 API 成了死代码。
3. **合成是后加的**：X 最初没有窗口合成的概念。现代的窗口特效靠一个叫 **Compositing Window Manager** 的外挂进程实现，它作为 X 的客户端，把所有窗口的内容重新合成一遍再交回给 X 显示。这意味着**至少多一次拷贝和一次进程往返**。
4. **没有真正的输入隔离**：任何 X 客户端都能监听全局键盘事件。这是设计缺陷，不是配置问题。

架构上的结果是这样一条冗长的路径：

```
应用渲染 → 交给 X Server → X 交给合成器 → 合成器合成 → 交回 X → X 交给硬件
```



### 4.2 Wayland 的思路

Wayland 的核心洞察是：

> 既然实际上是"合成器"在做所有的合成工作，那就让**合成器直接拥有硬件**，去掉中间的 X Server。

于是架构变成：

```
应用程序 ──(Wayland 协议)──> 合成器（同时也是显示服务器）──> 硬件
```

在 Wayland 模型里：

- **应用自己渲染**。合成器不提供绘图 API，只接收"一块画好的 buffer"。
- **合成器直接操作 KMS**。它就是显示服务器。
- **传递的是 buffer 的引用（文件描述符），不是像素数据**。零拷贝。
- **协议只负责"窗口管理"语义**：这块 buffer 是哪个窗口的、放在哪、焦点给谁、输入事件发给谁。



### 4.3 UMD 与 KMD

图形驱动被切成两半，这是理解整个栈的关键：

```
┌──────────────────────────────────────────────┐
│  应用程序 (OpenGL / Vulkan 调用)               │
├──────────────────────────────────────────────┤
│  UMD  User-Mode Driver                       │  用户态驱动
│  - Mesa 的 Gallium 驱动 / 厂商闭源驱动          │  在应用进程内，是一个 .so
│  - 编译着色器、构造 GPU 命令流                   │
│  - 管理 buffer 的分配和布局                     │
├──────────────────────────────────────────────┤
│  libdrm  （不是驱动，是 ioctl 的薄封装）         │
├──────────────────────────────────────────────┤
│  ═══════ 用户态 / 内核态边界 ═══════            │
├──────────────────────────────────────────────┤
│  KMD  Kernel-Mode Driver                     │  内核态驱动
│  - DRM 子系统 + 厂商驱动                       │
│  - 显存分配、地址映射、命令提交、中断处理          │
│  - 显示模式设置                                │
├──────────────────────────────────────────────┤
│  硬件                                         │
└──────────────────────────────────────────────┘
```

为什么这么切？

- **性能**：编译着色器、构造命令流是重活，放在内核里会拖慢整个系统，而且崩了就是内核崩溃。
- **安全**：KMD 必须验证 UMD 提交的一切（不能让一个进程读另一个进程的显存），所以 KMD 要尽可能小、尽可能好审计。
- **多 API 支持**：OpenGL、Vulkan、OpenCL 各有各的 UMD，共享同一个 KMD。

**本系列的合成器，站在这个分层的一个特殊位置**：它既是 UMD 的使用者（用 EGL/GLES 做兜底合成），又是 KMD 的直接调用者（做 KMS 提交），还是其他进程的 UMD 的服务对象（接收客户端提交的 buffer）。

所以这条链路是：

```
客户端 UMD 分配 buffer、渲染
   ↓ (Wayland 协议 + DMA-BUF fd)
合成器 决定这块 buffer 怎么显示
   ↓ (KMS ioctl)
KMD 配置硬件
   ↓ (VBlank 中断)
KMD 回报"已上屏"和精确时间戳
   ↓ (Wayland 协议)
客户端 UMD 知道可以复用 buffer、知道该什么时候画下一帧
```

这就是所谓的 **UMD ↔ KMD ↔ UMD 全链路**。



### 4.4 Mesa 在哪

Mesa 是 Linux 上最主要的开源图形驱动集合。需要澄清一点：

**Mesa 主要是 UMD。** 当你调用 `glDrawArrays()`，执行的是 Mesa 的代码；Mesa 把它翻译成 GPU 命令，然后通过 `ioctl` 交给内核里的 KMD。

Mesa 里还包含：
- **EGL**：窗口系统和 OpenGL 之间的胶水层。负责创建渲染上下文、管理 surface、和窗口系统（X11 / Wayland / GBM）对接。
- **GBM**（Generic Buffer Management）：一个"不依赖任何窗口系统"的buffer 分配接口。合成器用它来分配可以被 GPU 渲染、又能被显示控制器扫描的显存



### 4.5 Wayland 的对象模型

Wayland 协议是**面向对象**的：客户端和合成器之间维护一组共享的对象，每个对象有一个 ID，有一组**请求**（客户端 → 合成器）和
**事件**（合成器 → 客户端）。

最核心的几个：

```
wl_display          连接本身。所有对象的根。
  └── wl_registry   服务发现：合成器在这里广播它支持哪些接口
        ├── wl_compositor   用来创建 surface
        ├── wl_shm          共享内存 buffer（慢速路径）
        ├── zwp_linux_dmabuf_v1   DMA-BUF buffer（零拷贝路径）
        ├── xdg_wm_base     窗口管理语义（标题栏、最大化、关闭）
        ├── wl_seat         输入设备组（键盘 + 鼠标 + 触摸）
        └── wp_presentation 精确的呈现时间反馈
```

**`wl_surface`** 是最重要的对象。它代表"一块可以显示的矩形区域"。注意它**不是窗口**——它只是一块内容。要变成一个有标题栏、能最大化的窗口，需要给它套一个 `xdg_toplevel` 角色。

一个 surface 的更新流程：

```
attach(buffer)        # 把一块 buffer 关联到 surface
damage(x,y,w,h)       # 声明哪些区域变了
set_opaque_region(..) # 声明哪些区域是完全不透明的
frame(callback)       # 请求"下次适合画的时候通知我"
commit()              # 把上面这些 pending 状态**原子地**变成 current 状态
```



### 4.6 双缓冲状态：Wayland 协议里的 atomic

注意上面最后那个 `commit()`。这是 Wayland 设计里一个很漂亮的地方：

> **所有对 surface 的修改都是"暂存（pending）"的，直到 `commit()` 才一次性生效。**

这意味着客户端可以在一次 commit 里同时改变 buffer、位置、缩放、输入区域——合成器看到的要么是全部旧状态，要么是全部新状态，不会看到"buffer 换了但尺寸还没改"的中间态。

**这和 KMS 的 atomic 提交是同一个思想**，只是发生在不同的层：

```
客户端 → 合成器：  wl_surface.commit()      原子地更新一个 surface 的状态
合成器 → 内核：    drmModeAtomicCommit()    原子地更新整个显示配置
```

理解这一点，就理解了为什么 Wayland 被称为 "every frame is perfect"（每一帧都是完美的）。在 X11 下，窗口 resize 时经常能看到内容和边框尺寸不一致的闪烁，根源就是缺少这种原子性。



### 4.7 frame callback：Wayland 的节流机制

`wl_surface.frame(callback)` 是一个容易被忽略但极其重要的机制。

客户端请求一个 frame callback，合成器在"适合画下一帧的时候"触发它。客户端收到回调后才画下一帧。

这解决了两个问题：

- **问题一：不可见的窗口不该消耗资源。

    > 如果一个窗口被完全遮挡或最小化了，合成器**根本不触发它的 frame callback**，客户端就自然停下来了，不需要任何额外的协议。

- **问题二：客户端不该画得比屏幕快。**

    > 如果客户端以 1000fps 渲染而屏幕只有 60Hz，多出来的 940 帧全是浪费。frame callback 天然地把客户端节流到刷新率。

对比 X11：客户端可以随便画，节流靠 `glXSwapBuffers` 阻塞，而这个阻塞行为是驱动实现细节，不同驱动不一样。

**对合成器实现的含义**：frame callback 应该在**收到 page flip 完成事件之后**触发，而不是提交之后。因为只有那时才知道"上一帧真的上屏了，现在开始画下一帧刚好赶得上下一个 VBlank"。

这条链路是：

```
KMS page flip 事件 → 合成器知道一帧上屏了
                  → 触发所有可见 surface 的 frame callback
                  → 客户端开始画下一帧
                  → 客户端 commit
                  → 合成器合成
                  → 提交给 KMS
                  → 下一个 VBlank
```



### 4.8 damage：只重画变化的部分

`wl_surface.damage()` 让客户端声明"这次只有这块区域变了"。

合成器可以据此：

- 只重新合成变化的区域（GPU 合成时能省不少带宽）
- 如果变化区域为空，干脆跳过这一帧的提交

在 KMS 层面也有对应的机制：`FB_DAMAGE_CLIPS` 属性可以告诉内核"这个 framebuffer 只有这些矩形变了"。对于支持部分更新的面板（比如 DSI 命令模式的屏幕），这能大幅省电。

不过 damage 优化的收益高度依赖场景：全屏视频或游戏时每帧全变，damage 没用；而文本编辑器打字时可能只有几十像素变化，收益巨大。



## 五、DRM 子系统与设备节点

### 5.1 DRM 是什么

**DRM = Direct Rendering Manager**。它是 Linux 内核的图形子系统，提供两大类功能：

1. **渲染相关**：显存分配（GEM）、地址映射、GPU 命令提交、同步原语
2. **显示相关**：模式设置（KMS）、平面配置、页翻转

这两类功能是**正交**的。一个设备可以只有渲染功能（比如独立的计算卡），也可以只有显示功能（比如某些 SoC 的独立显示控制器）。



### 5.2 设备节点

DRM 通过 `/dev/dri/` 下的设备节点暴露给用户态：

```
/dev/dri/card0        primary node   —— 完整功能，包括 KMS
/dev/dri/card1
/dev/dri/renderD128   render node    —— 只有渲染功能，没有 KMS
/dev/dri/renderD129
```

**primary node（`cardN`）**：
- 可以做模式设置（需要 DRM master 权限，后面讲）
- 可以做渲染
- 通常需要特权或属于 `video` 组

**render node（`renderDN`）**：
- **不能**做模式设置
- 可以分配显存、提交 GPU 命令
- 权限宽松（`0666`），任何进程都能打开

为什么要分开？因为**渲染不需要特权，显示需要**。一个只想用 GPU 做计算的程序不应该有能力把你的屏幕关掉。render node 就是为这个场景设计的。

**关键坑**：`cardN` 和 `renderDN` 的编号**不对应**，而且**同一个物理设备可能有多个 primary node，其中只有一个带 KMS 资源**。

在实际硬件上遇到过这样的拓扑：

```
/dev/dri/card0       同一个物理设备，但没有 KMS 资源
/dev/dri/card1       同一个物理设备，有 KMS 资源        ← 显示要用这个
/dev/dri/renderD128  同一个物理设备的 render node      ← 渲染要用这个
```

所以代码里必须做两件事：

1. **枚举所有 `cardN`，逐个检查有没有 KMS 资源**，而不是假设 `card0`
2. **KMS fd 和 render fd 分开持有**，不能假设是同一个节点

```cpp
// 伪码：找到有 KMS 资源且有已连接显示器的节点
for (path in glob("/dev/dri/card*")) {
    fd = open(path, O_RDWR);
    if (fd < 0) continue;                    // 权限不足是常态，跳过

    res = drmModeGetResources(fd);
    if (res == NULL) continue;               // 没有 KMS，可能是纯渲染节点

    for (connector in res->connectors) {
        if (connector.status == CONNECTED) {
            return path;                     // 找到了
        }
    }
}
```



### 5.3 驱动名字的两套体系

还有一个容易混淆的地方：**同一个设备有两个"驱动名"**。

```bash
# PCI/platform 驱动名（内核设备模型里的绑定关系）
$ basename $(readlink -f /sys/class/drm/card0/device/driver)
i915          # 或 amdgpu / nouveau / rockchip-drm / <厂商私有名>

# DRM 驱动名（DRM 子系统内部的标识）
$ # 由 drmGetVersion() 返回
i915          # 这个例子里两者恰好相同，很多平台上不同
```



`modetest -M <name>` 要的是**后者**。用前者会打开错误的节点或者失败。在代码里，DRM 驱动名通过这个接口拿：

```cpp
drmVersionPtr version = drmGetVersion(fd);
// version->name    → "i915" / "amdgpu" / "rockchip" / ...
// version->desc    → 人类可读的描述
drmFreeVersion(version);
```



### 5.4 libdrm 是什么

**libdrm 不是驱动。** 它是一个很薄的用户态库，把 DRM 的 `ioctl` 包装成 C 函数，顺便处理一些结构体填充的样板代码。

比如这个调用：

```c
drmModeAddFB2(fd, width, height, format, handles, pitches, offsets, &fb_id, 0);
```

内部大致就是：

```c
struct drm_mode_fb_cmd2 cmd = {0};
cmd.width = width;
cmd.height = height;
cmd.pixel_format = format;
memcpy(cmd.handles, handles, sizeof(cmd.handles));
memcpy(cmd.pitches, pitches, sizeof(cmd.pitches));
memcpy(cmd.offsets, offsets, sizeof(cmd.offsets));
cmd.flags = flags;

int ret = drmIoctl(fd, DRM_IOCTL_MODE_ADDFB2, &cmd);
*fb_id = cmd.fb_id;
return ret;
```

理解这一点很重要：**libdrm 没有任何"智能"**。它不缓存、不重试、不做策略决定。所有的策略都在你的代码里。所以出问题时，不要去怀疑 libdrm，直接看你传进去的参数和内核回的 errno。

libdrm 还有一个特点：**大量的 `drmModeGetXxx()` 返回堆分配的结构体，必须配对调用 `drmModeFreeXxx()`**。



这类 C 风格 API 在 C++ 里应该无条件包成 RAII：

```cpp
struct ResDeleter {
    void operator()(drmModeRes* p) const noexcept { drmModeFreeResources(p); }
};
using UniqueRes = std::unique_ptr<drmModeRes, ResDeleter>;

// 使用
UniqueRes res(drmModeGetResources(fd));
if (!res) { /* 错误处理，无需手动 free */ }
// 离开作用域自动释放，即使中途 return 或抛异常
```



### 5.5 会话、seat 与 VT：显示服务器的权限模型

前面说"要停掉显示管理器才能拿 DRM master"。这一节讲清楚背后的机制，因为一个真正可用的合成器必须处理这些。

**VT（Virtual Terminal）**

Linux 内核提供多个虚拟终端，Ctrl+Alt+F1~F12 切换。每个 VT 是一个独立的"控制台会话"，同一时刻只有一个是**前台**的。

图形界面通常占用一个 VT（比如 tty7）。切换 VT 时，内核需要通知当前的图形程序"你要交出显示控制权了"。

这个通知机制是 `ioctl(tty_fd, VT_SETMODE, ...)` 配合信号：

```
1. 程序声明自己接管 VT 切换：
   VT_SETMODE with mode = VT_PROCESS
   指定两个信号：relsig（要求释放）和 acqsig（获得控制）

2. 用户按 Ctrl+Alt+F3
   内核给程序发 relsig
   程序收到后：drmDropMaster()，然后 VT_RELDISP 确认
   内核完成切换

3. 用户切回来
   内核发 acqsig
   程序收到后：drmSetMaster()，**重新做一次完整 modeset**
```

注意第 3 步的"重新完整 modeset"。切走期间，别的程序（比如内核控制台）可能改过显示配置，不能假设切回来时状态还是你留下的那个。

另外还要设置 `KDSETMODE`：

```c
ioctl(tty_fd, KDSETMODE, KD_GRAPHICS);  // 接管时，禁止内核往屏幕上画文字
ioctl(tty_fd, KDSETMODE, KD_TEXT);      // 退出时恢复
```

不设的话，内核控制台的光标和内核日志会画到你的画面上。



**logind 与 seat**

上面那套直接操作 VT 的做法要求 root 权限。现代发行版用 **systemd-logind**（或独立的 **seatd**）来解耦：

- **seat（座位）**：一组物理上属于同一个人的输入输出设备。单人电脑只有一个 `seat0`；多头工作站可以配多个 seat。
- **session（会话）**：一个用户在一个 seat 上的登录实例。

logind 作为特权守护进程，负责：

1. **代替程序打开设备节点**，通过 D-Bus 把 fd 传给非特权进程（用 `SCM_RIGHTS` 传 fd，和后面 DMA-BUF 共享是同一个机制）
2. **管理 VT 切换**，通过 D-Bus 信号 `PauseDevice` / `ResumeDevice` 通知会话
3. **判断谁是 active session**，只有 active 的能拿到设备

所以一个规范的 Wayland 合成器的启动流程是：

```
1. 连接 D-Bus，向 logind 声明自己是一个 graphical session
2. 通过 logind 的 TakeDevice 拿到 /dev/dri/cardN 的 fd
   （不需要自己是 root）
3. 监听 PauseDevice / ResumeDevice 信号处理 VT 切换
4. 输入设备也通过 logind 拿（libinput 支持这个模式）
```

这样合成器可以**完全不需要 root 权限**运行。

**这对我们意味着什么？**

本系列的早期阶段直接用 `sudo` 跑，是为了绕开这一整套机制专注于显示本身。但要注意这是**临时的简化**，不是最终形态。一个能日常用的合成器必须：

- 通过 logind/seatd 拿设备，不用 root
- 处理 VT 切换（drop/acquire master + 重新 modeset）
- 处理设备被 pause/resume

这些会在后面的阶段补上。现在知道有这么回事就够了。



**为什么这个模型是必要的？**

想象没有它会怎样：任何一个用户程序都能调 `drmSetMaster()` 抢走显示控制权，在你输密码时截屏，或者画一个假的登录界面。

seat / session 模型确保**只有当前活跃会话的程序**能碰显示和输入设备。这是 Wayland 相比 X11 在安全性上改进的一部分——
X11 时代任何客户端都能监听全局键盘。



### 5.6 DRM lease：把一个输出借出去

顺带提一个后来加入的机制，因为它体现了 KMS 设计的可扩展性。

**DRM lease** 允许 master 把**一部分资源**（某个 connector + CRTC + plane）"租借"给另一个进程，那个进程在这些资源上拥有 master 权限，但碰不到其他资源。

```c
int lessee_fd = drmModeCreateLease(fd, object_ids, count, flags, &lessee_id);
// 把 lessee_fd 通过 socket 传给另一个进程
```

主要用途是 **VR 头显**：合成器把头显那个 connector 租给 VR 运行时，让它独占地以极低延迟直接提交，同时桌面继续在别的显示器上正常工作。

这个机制说明了一件事：**KMS 的对象模型足够正交，以至于可以按对象粒度做权限切分。** 这在 legacy 接口时代是做不到的。



## 六、KMS 对象模型

KMS = **K**ernel **M**ode **S**etting，内核模式设置。"模式设置"指的就是"配置显示输出"这件事：分辨率多少、刷新率多少、从哪块内存读像素。

### 6.1 五类对象

前面讲硬件时已经见过了，这里正式定义：

| 对象 | 硬件对应 | 主要属性 |
| --- | --- | --- |
| **Connector** | 物理接口 | 连接状态、支持的模式列表、EDID、物理尺寸 |
| **Encoder** | 信号编码器 | 类型（TMDS/DSI/…）、`possible_crtcs` |
| **CRTC** | 时序发生器 | 当前模式、是否激活、gamma 表 |
| **Plane** | 图层读取单元 | 绑定的 FB、源矩形、目标矩形、支持的格式 |
| **Framebuffer** | （无，是软件描述） | 宽高、格式、GEM handle、行跨距 |

每个对象有一个**全局唯一的 32 位 ID**（在同一个 DRM 设备内唯一）。所有的 KMS 操作都是"对某个 ID 的对象做某件事"。

### 6.2 Connector 的状态

Connector 有三种状态：

```c
DRM_MODE_CONNECTED       // 接了显示器
DRM_MODE_DISCONNECTED    // 没接
DRM_MODE_UNKNOWNCONNECTION  // 探测不出来（某些 VGA 接口）
```

查询连接状态有两个接口，区别很重要：

```c
drmModeGetConnector(fd, id)         // 强制重新探测：发起 DDC/AUX 通信
drmModeGetConnectorCurrent(fd, id)  // 只读内核缓存的状态
```

**强制探测会阻塞几十毫秒**（要通过 I2C 读 EDID）。如果你要扫描系统里所有设备的所有 connector，用前者会卡顿明显。

我们的做法是：

- 快速扫描（找"哪个节点有显示器"）用 `Current` 版本
- 正式枚举（要拿准确的模式列表）用强制探测版本



### 6.3 Writeback Connector：一个特殊的存在

有一类 connector 叫 **writeback connector**。它不连接任何显示器，而是**把 CRTC 合成后的结果写回到一块内存**。

用途：
- 无显示器的自动化测试（合成一帧，读回来算 CRC 校验）
- 屏幕录制、远程桌面的硬件加速路径

坑在于：**writeback connector 永远报告 `CONNECTED`，而且有完整的模式列表**。如果你的"找一个可用输出"的逻辑写成"取第一个 connected 的 connector"，很可能会选中它，然后在一个不产生任何实际显示输出的通路上做 modeset，屏幕依然是黑的，而所有 ioctl 都返回成功。

所以必须显式跳过：

```cpp
if (connector.type == DRM_MODE_CONNECTOR_WRITEBACK) {
    continue;  // 这不是显示输出
}
```

另外，writeback connector 默认是**隐藏**的，必须显式声明能力才能看到：

```c
drmSetClientCap(fd, DRM_CLIENT_CAP_WRITEBACK_CONNECTORS, 1);
```

这也解释了一个现象：同一台机器，用不同工具枚举出的 connector 数量可能不同，取决于工具有没有开这个 cap。



### 6.4 显示模式（Mode）

Connector 会报告一个**模式列表**，每个模式就是前面讲的那套时序参数：

```c
struct drmModeModeInfo {
    uint32_t clock;         // 像素时钟，kHz

    uint16_t hdisplay;      // 可见宽度
    uint16_t hsync_start;   // 水平同步脉冲起点
    uint16_t hsync_end;     // 水平同步脉冲终点
    uint16_t htotal;        // 一行的总长度（含消隐）
    uint16_t hskew;

    uint16_t vdisplay;      // 可见高度
    uint16_t vsync_start;
    uint16_t vsync_end;
    uint16_t vtotal;        // 一帧的总行数（含消隐）
    uint16_t vscan;

    uint32_t vrefresh;      // 刷新率，整数 Hz（有精度损失，别用）
    uint32_t flags;         // INTERLACE / DBLSCAN / 同步极性
    uint32_t type;          // PREFERRED / DRIVER / USERDEF
    char name[32];
};
```

模式列表是从显示器的 **EDID**（Extended Display Identification Data）里解析出来的。EDID 是一小块存在显示器里的 ROM，通过 I2C 读取，
描述了显示器的能力。

其中标记了 `DRM_MODE_TYPE_PREFERRED` 的是显示器推荐的模式，通常是它的物理原生分辨率。**没有特殊理由就应该用 preferred 模式**——用非原生分辨率会让显示器做缩放，画质变差还增加延迟。



### 6.5 一个重要的实现决定：ModeInfo 不要自己重新定义

在实现里，我们直接持有 `drmModeModeInfo` 原始结构：

```cpp
struct ModeInfo {
    drmModeModeInfo raw{};
    // ... 各种便捷方法
};
```

而不是定义一个"更漂亮的"自己的结构再做转换。原因是：

> 设置模式时，这个结构体要**逐字节**交给内核（作为一个 blob 属性）。自己定义一份再转换，只会引入转换 bug，没有任何收益。

代价是 `mw/drm` 这一层的头文件必须 `#include <xf86drmMode.h>`。我们把这条写进了分层约定：**这一层的职责就是包装 libdrm，
所以允许引 libdrm 的头；再往上的层不许**。



### 6.6 像素格式：fourcc 到底在说什么

前面提到过 fourcc，这一节展开讲，因为它是后面几讲反复出现的概念。

**fourcc** 是把四个 ASCII 字符打包成一个 32 位整数：

```c
#define fourcc_code(a, b, c, d) \
    ((uint32_t)(a) | ((uint32_t)(b) << 8) | ((uint32_t)(c) << 16) | ((uint32_t)(d) << 24))

#define DRM_FORMAT_XRGB8888  fourcc_code('X', 'R', '2', '4')  // "XR24"
```

注意是**小端打包**：第一个字符在最低字节。所以把这个 `uint32_t` 当成字符数组打印，得到的就是 `"XR24"`。

**RGB 格式的命名规则**

`XR24` 拆开是 `XR` + `24`：

- 字母部分从**最高有效位到最低有效位**列出通道：`XRGB`（但为了凑四个字符，只写前两个字母 + 位数）
- 数字部分是**每通道的位数 × 通道数**的简写

完整列表的规律：

| fourcc | 全名 | 内存布局（小端，逐字节） |
| --- | --- | --- |
| `XR24` | XRGB8888 | B, G, R, X |
| `AR24` | ARGB8888 | B, G, R, A |
| `XB24` | XBGR8888 | R, G, B, X |
| `RG16` | RGB565 | 两字节，`RRRRRGGG GGGBBBBB` |
| `AR30` | ARGB2101010 | 30 位色 + 2 位 alpha |

> **这里有一个经典的困惑点。** `XRGB8888` 这个名字描述的是"把这 32 位当成一个整数看时，从高位到低位是 X、R、G、B"。
>
> 但在小端机器上，这个整数存进内存后，**字节顺序是反的**：最低字节（B）在最前面。所以：
>
> ```c
> uint32_t* pixel = ...;
> *pixel = 0x00FF0000;   // X=0, R=0xFF, G=0, B=0  →  纯红
> ```
>
> 写成 `uint32_t` 时按名字的顺序，存进内存后自动变成 B, G, R, X。**只要你始终用 `uint32_t` 读写，就不用关心字节序。**只有在按字节操作时才需要小心。
>
> 验证方法很简单：画一组彩条，看颜色顺序对不对。如果 R 和 B 反了，说明搞混了 `XRGB` 和 `XBGR`。
>

**YUV 格式：为什么视频不用 RGB**

人眼对**亮度**的敏感度远高于对**色度**的敏感度。YUV（更严格地说是 Y'CbCr）把颜色分成：

- **Y**：亮度（luma）
- **U / Cb**：蓝色色度差
- **V / Cr**：红色色度差

然后对色度做**降采样**。常见的采样模式：

```
4:4:4   每个像素都有完整的 Y、U、V        无压缩
4:2:2   水平方向色度减半                 省 33%
4:2:0   水平和垂直方向色度都减半          省 50%
```

`4:2:0` 是视频编码的绝对主流。1920×1080 的一帧：

```
RGB8888:  1920 × 1080 × 4 = 8,294,400 字节
NV12:     Y  平面 1920 × 1080     = 2,073,600
          UV 平面 960 × 540 × 2   = 1,036,800
          合计                     = 3,110,400 字节  （省 62%）
```

**平面（plane）与打包（packed）**

注意"plane"这个词在这里又有了第三个含义（前面有 KMS plane 和图层）。在像素格式的语境下，plane 指"一块独立的内存区域"：

```
打包格式（packed）：所有通道交错在一块内存里
    YUYV:  Y0 U0 Y1 V0 Y2 U2 Y3 V2 ...

半平面（semi-planar）：亮度一块，色度一块（交错）
    NV12:  [Y Y Y Y ...] [U V U V ...]

全平面（planar）：三块独立内存
    YU12:  [Y Y Y ...] [U U U ...] [V V V ...]
```

这解释了为什么 `drmModeAddFB2` 的 `handles` / `pitches` / `offsets` 都是**长度为 4 的数组**——多平面格式需要多个 GEM object（或者同一个 object 的不同偏移）。

**色彩空间与范围**

同样是 YUV 数据，转换成 RGB 的系数取决于**色彩空间标准**：

```
BT.601   标清视频
BT.709   高清视频（最常见）
BT.2020  超高清 / HDR
```

用错系数，颜色会有肉眼可见的偏差（尤其是绿色和肤色）。

另外还有**范围（range）**：

```
Limited / TV range:  Y ∈ [16, 235], UV ∈ [16, 240]
Full / PC range:     Y ∈ [0, 255],  UV ∈ [0, 255]
```

用错范围，画面会**发灰**（把 limited 当 full 解释）或者 **过黑过白丢细节**（把 full 当 limited）。

KMS 把这两个参数暴露为 plane 的属性：

```
COLOR_ENCODING  →  ITU-R BT.601 YCbCr / BT.709 YCbCr / BT.2020 YCbCr
COLOR_RANGE     →  YCbCr limited range / YCbCr full range
```

所以合成器把一个 YUV buffer 交给 overlay plane 时，**必须同时设置这两个属性**，否则颜色会错。这是 overlay 直出路径上一个非常容易漏掉的细节。

**alpha 预乘**

带 alpha 的格式还有一个隐藏参数：alpha 是否**预乘（premultiplied）**。

```
非预乘：  存储 (R, G, B, A)，混合时算 α×C_s + (1-α)×C_d
预乘：    存储 (R×A, G×A, B×A, A)，混合时算 C_s + (1-α)×C_d
```

预乘的好处是混合时少一次乘法，而且在做缩放/滤波时数学上更正确（非预乘的边缘会出现"黑边"或"白边"）。

KMS 用 plane 的 `pixel blend mode` 属性表达：

```
"None"              忽略 alpha，当不透明处理
"Pre-multiplied"    预乘（大多数图形栈的默认）
"Coverage"          非预乘
```

搞错了的症状是半透明区域的颜色偏暗或偏亮。



### 6.7 格式支持是分层的

一个容易踩的坑：**"设备支持某个格式"这句话在不同层有不同含义。**

```
GPU 能渲染的格式        ← Mesa / 厂商 UMD 决定
GPU 能采样（读纹理）的格式 ← 通常比能渲染的多
显示控制器能扫描的格式    ← KMS plane 的格式列表
视频解码器能输出的格式    ← 另一套完全独立的能力
```

这四个集合往往不同。做零拷贝视频管线时，你需要找一个四者交集里的格式（通常是 NV12 或 P010）。

而且**每个 plane 的格式列表可能不同**：cursor plane 通常只支持 ARGB8888；某些 overlay plane 支持 YUV 而 primary plane 不支持。所以格式查询必须是 per-plane 的，不能"查一个 plane 然后假设全设备都一样"。



## 七、属性系统：现代 KMS 的核心抽象

这一节是理解 atomic KMS 的关键。

### 7.1 一切都是属性

现代 KMS 里，几乎所有可配置的东西都表达成**属性（property）**：

```
Connector 的属性：CRTC_ID, EDID, DPMS, link-status, max bpc, vrr_capable, ...
CRTC 的属性：     MODE_ID, ACTIVE, OUT_FENCE_PTR, VRR_ENABLED, GAMMA_LUT, ...
Plane 的属性：    type, FB_ID, CRTC_ID, SRC_X/Y/W/H, CRTC_X/Y/W/H, IN_FORMATS, IN_FENCE_FD, rotation, zpos, alpha, ...
```

属性有名字（字符串）和 ID（整数），值是 64 位无符号整数。

配置显示输出，本质上就是**给一堆 (对象, 属性, 值) 三元组赋值**。

这个设计的好处是**可扩展**：驱动可以定义新属性而不改 UAPI，用户态通过名字查找，找不到就说明这个驱动/内核不支持该功能。这就是"运行时能力探测"的基础。



### 7.2 属性的种类

```c
DRM_MODE_PROP_RANGE          // 无符号区间，如 alpha ∈ [0, 65535]
DRM_MODE_PROP_SIGNED_RANGE   // 有符号区间，如 CRTC_X 可以是负数
DRM_MODE_PROP_ENUM           // 枚举，如 type ∈ {Primary, Overlay, Cursor}
DRM_MODE_PROP_BITMASK        // 位掩码，如 rotation
DRM_MODE_PROP_BLOB           // 大块数据，值是一个 blob 对象的 ID
DRM_MODE_PROP_OBJECT         // 值是另一个 KMS 对象的 ID，如 CRTC_ID
```

这里有个**实现陷阱**：判断属性种类时，legacy 类型和扩展类型用的是 **不同的掩码**：

```c
#define DRM_MODE_PROP_LEGACY_TYPE    (DRM_MODE_PROP_RANGE | DRM_MODE_PROP_ENUM | \
                                      DRM_MODE_PROP_BLOB  | DRM_MODE_PROP_BITMASK)
#define DRM_MODE_PROP_EXTENDED_TYPE  0x0000ffc0
```

这是 UAPI 的历史包袱：老的四种类型挤在 flags 的低位里，后加的 OBJECT 和 SIGNED_RANGE 用了另一段位。用一个掩码去判所有类型，会把 OBJECT 误判成 RANGE。

正确的写法：

```cpp
PropKind classify(uint32_t flags) {
    uint32_t extended = flags & DRM_MODE_PROP_EXTENDED_TYPE;
    if (extended != 0) {
        switch (extended) {
            case DRM_MODE_PROP_OBJECT:       return PropKind::Object;
            case DRM_MODE_PROP_SIGNED_RANGE: return PropKind::SignedRange;
            default:                          return PropKind::Unknown;
        }
    }
    switch (flags & DRM_MODE_PROP_LEGACY_TYPE) {
        case DRM_MODE_PROP_RANGE:   return PropKind::Range;
        case DRM_MODE_PROP_ENUM:    return PropKind::Enum;
        case DRM_MODE_PROP_BLOB:    return PropKind::Blob;
        case DRM_MODE_PROP_BITMASK: return PropKind::Bitmask;
        default:                     return PropKind::Unknown;
    }
}
```



### 7.3 属性定义是设备全局的，属性值是每对象一份

这是一个容易忽略但很重要的事实。

驱动在初始化时创建一批 property 对象（每个有自己的 ID），然后把它们**附加**到多个 connector / crtc / plane 上。

所以：

- `drmModeGetProperty(fd, prop_id)` 返回的元数据（名字、类型、flags）和"你从哪个对象查到这个 ID"**完全无关**
- 同一个 `CRTC_ID` 属性，在 6 个 connector 上是**同一个 prop_id**

不理解这一点，就会写出这样的代码：

```cpp
// 对每个对象
for (object in objects) {
    props = drmModeObjectGetProperties(fd, object.id, object.type);
    for (prop_id in props) {
        // 每次都重新查询定义 —— 大量重复
        prop = drmModeGetProperty(fd, prop_id);
        ...
    }
}
```

在一个有 6 个 connector、2 个 CRTC、8 个 plane 的设备上，这会产生 **230 次** `drmModeGetProperty` 调用，而实际不同的属性定义只有 **100 个**。

加一个设备级的缓存，130 次多余的 ioctl 就消失了：

```cpp
class PropertyDefCache {
public:
    const Definition* get(BorrowedFd fd, uint32_t property_id) {
        auto it = binary_search(defs_, property_id);
        if (found) { ++hits_; return &it->second; }

        ++misses_;
        auto* prop = drmModeGetProperty(fd.get(), property_id);
        if (!prop) return nullptr;
        // ... 填充 Definition，插入到有序位置
    }
private:
    std::vector<std::pair<uint32_t, Definition>> defs_;  // 按 id 排序
};
```

注意缓存必须是**每设备**的，不能做成全局静态——property ID 只在单个 DRM fd 内唯一。



### 7.4 属性 ID 的查询必须只做一次

这是一条硬性工程约束：

> **`drmModeObjectGetProperties` 只在初始化 / 模式设置阶段调用，渲染热路径禁止调用。**

原因很直接：那是一次 `ioctl`，会陷入内核。每帧调用是纯粹的浪费。

正确的模式是：初始化时把需要的属性 ID 解析到一个结构体里，热路径只读结构体字段：

```cpp
struct PlanePropIds {
    PropertyId type      = kNoProperty;  // 必选
    PropertyId fb_id     = kNoProperty;  // 必选
    PropertyId crtc_id   = kNoProperty;  // 必选
    PropertyId src_x     = kNoProperty;  // 必选
    // ...
    PropertyId in_formats      = kNoProperty;  // 可选
    PropertyId in_fence_fd     = kNoProperty;  // 可选
    PropertyId zpos            = kNoProperty;  // 可选

    static Result<PlanePropIds> resolve(const PropertyMap& props);
};
```

**必选属性缺失就直接报错退出**——atomic 驱动必须注册这些，缺了说明这个驱动根本没实现 atomic modeset，继续往下走只会在提交时得到一个没头没尾的 `EINVAL`。

**可选属性缺失就留 `kNoProperty`，运行时分支跳过**。这就是"运行时能力探测"落到属性粒度上的样子，不需要任何 `#ifdef`。



### 7.5 怎么保证这条约束不被违反

光靠代码审查是不够的。某个看起来无害的辅助函数里调了一次属性查询，每帧就多一次 ioctl，而且**完全不影响画面**——你根本不会发现。

所以我们的做法是**给每类 ioctl 记数**，并提供一个"密封"机制：

```cpp
// 模式设置完成后调一次
void seal_init_phase();

// 帧循环里每帧调一次
void check_sealed(const char* where);
```

`seal_init_phase()` 记录当前计数，`check_sealed()` 检查那些"初始化后不该再增长"的计数器有没有增长。增长了就打一条醒目的错误：

```
ERR  hot-path violation at 'frame loop': get_properties grew from 16 to 17
     after the init phase was sealed
ERR    this is an ioctl per frame that should have been cached at modeset time
```

**故意不 abort**——学习阶段更想看到它继续跑，好体会"性能 bug 的隐蔽性"。多一次 ioctl 通常只是掉帧，不会黑屏。

配套地，demo 每秒打印一次 ioctl 增量：

```
INFO frames=61 fps=60.00 interval=16.667ms [16.486, 16.847] dropped=0
INFO   last second: 61 frames, ioctls: commit=61 flip=61
```

稳态下 `commit` 数应该恰好等于帧数，其他计数器应该是 0。这一行就是"热路径零 ioctl"的运行时证据，不是口号。



### 7.6 Blob 属性与生命周期

有些数据太大，塞不进一个 64 位整数——比如显示模式（68 字节）、EDID（128 字节起）、格式列表（几百字节）。

KMS 用 **blob** 解决：blob 是一个独立的内核对象，有自己的 ID；property 的 value 就是这个 ID。

```c
// 创建一个 blob（比如把模式提交给内核）
uint32_t blob_id;
drmModeCreatePropertyBlob(fd, &mode, sizeof(mode), &blob_id);

// 用完销毁
drmModeDestroyPropertyBlob(fd, blob_id);
```

blob 不销毁就会一直挂在内核的 DRM 文件私有数据上。每次模式设置泄漏一个，热插拔场景下很快就能观察到资源耗尽。

所以 blob 必须 RAII 包装。同时要注意一个时序细节：

> **blob 不能在 commit 返回之前销毁**——内核是在 commit 处理过程中才去取 blob 内容的。

在我们的 demo 里，模式 blob 的生命周期覆盖整个程序运行：

```cpp
// 在 run() 的作用域里创建，活到函数返回
const PropertyBlob mode_blob = TRY(
    PropertyBlob::create(device.fd(), &path.mode.raw, sizeof(path.mode.raw)));
```



### 7.7 IN_FORMATS：格式与 modifier 的协商基础

`IN_FORMATS` 是一个 blob 属性，描述"这个 plane 支持哪些 (格式, 排布) 组合"。

先解释两个概念：

**像素格式（format）** 用 **fourcc** 表示——四个 ASCII 字符打包成 32 位整数：

```
XR24 = XRGB8888   32 位，无 alpha
AR24 = ARGB8888   32 位，带 alpha
NV12 = YUV 4:2:0  两平面，视频常用
P010 = 10 bit YUV 4:2:0
```

**修饰符（modifier）** 是一个 64 位的不透明值，描述**内存里的排布方式**。

同样是 XRGB8888，像素在内存里可以：
- **线性排布（LINEAR）**：一行接一行，简单直接
- **平铺（tiled）**：按 16x16 或 32x32 的小块重排，提高 GPU 的缓存命中率
- **压缩（compressed）**：带元数据的无损压缩，省带宽

不同厂商的平铺/压缩方案完全不同，所以 modifier 的高 8 位是 vendor 号，低 56 位是 vendor 自定义的编码。

**关键设计原则：合成器永远不解码 modifier 的语义。**

合成器只做三件事：

```
1. 从 plane 的 IN_FORMATS blob 读出 (format, modifier) 集合      ← 不解析
2. 按优先级发给客户端，让客户端据此分配 buffer                    ← 原样转发
3. 客户端回传 buffer，原样交给 addfb2；失败就降级                 ← 不判断
```

代码里体现为：

```cpp
// 正确：不透明 token
enum class Modifier : uint64_t {};

// 禁止出现：
// bool is_vendor_tiled(uint64_t mod) { return (mod >> 56) == VENDOR_FOO; }
```

唯一允许做 vendor 判断的地方是**日志格式化**，而且必须隔离在调试模块里，主逻辑不得依赖它的返回值。

**IN_FORMATS 的 blob 结构**长这样：

```c
struct drm_format_modifier_blob {
    __u32 version;            // 必须是 1
    __u32 flags;
    __u32 count_formats;      // 格式个数
    __u32 formats_offset;     // 格式数组的偏移
    __u32 count_modifiers;    // modifier 记录数
    __u32 modifiers_offset;   // modifier 数组的偏移
};

struct drm_format_modifier {
    __u64 formats;   // 位图：相对 offset 的 64 个格式里哪些支持本 modifier
    __u32 offset;    // 位图第 0 位对应 formats[] 里的下标
    __u32 pad;
    __u64 modifier;
};
```

位图 + offset 这个设计是为了压缩：格式多于 64 个时用多条记录，每条覆盖一个 64 格式的窗口。

解析伪码：

```
for each modifier_record:
    for bit in 0..63:
        if bitmask has bit set:
            index = record.offset + bit
            if index < count_formats:
                emit (formats[index], record.modifier)
```

**自校验的重要性**：这类二进制解析很容易写错，而且错了不会立刻崩，只会给出一份"看起来合理但是错的"格式列表。

由于某些版本的 `modetest` 根本不打印 IN_FORMATS，没法交叉验证，我们的做法是让**数据自己证明自己**：把 blob 的头部字段和每条记录原样打出来，再验证几条应该成立的等式：

```
✓ version == 1
✓ formats_offset + count_formats*4 <= blob 长度
✓ modifiers_offset + count_modifiers*24 <= blob 长度
✓ 每条记录的 offset < count_formats
✓ sum over records of popcount(bitmask) == 解析出的 pair 数
```

最后一条最关键。实测输出：

```
count_formats     = 32
count_modifiers   = 17
[0 ] modifier=0x0000000000000000 offset=0 bitmask=0x00000000ffffffff bits=32 LINEAR
[1 ] modifier=0x9200000000000027 offset=0 bitmask=0x0000000060000fff bits=14 ...
[2 ] modifier=0x9200000000000022 offset=0 bitmask=0x000000000004c000 bits=3  ...
...
OK    popcount over all bitmasks (403) equals the parsed pair count (403)
```

`0xffffffff` 有 32 个 1，对应 32 个格式全支持 LINEAR；`0x60000fff` 有 14 个 1，说明这个 modifier 只适用于 14 种格式。总和 403 和解析出的 pair 数一致，说明位图和 offset 的语义理解是对的。

数据自洽就是最好的证明，不需要外部工具背书。这是一种在缺乏参考实现时非常有用的验证思路。



## 八、Legacy KMS 与 Atomic KMS

### 8.0 一点历史：为什么会有三代接口

**第一代：UMS（User-mode Mode Setting），2007 年以前**

模式设置在**用户态**做。X Server 里的驱动直接 `mmap` 显卡寄存器，自己写时钟分频器、自己配 CRTC。

问题：

- **内核控制台和 X 会打架**。Ctrl+Alt+F1 切到 tty 经常花屏或黑屏，因为两边都在改同一组寄存器，谁也不知道对方改了什么。
- **suspend/resume 无法恢复**。内核不知道显示状态是什么，恢复不了。
- **panic 时看不到 oops**。内核崩溃时没法接管显示输出。
- **每个驱动一套私有寄存器接口**，完全不通用。

**第二代：KMS，2008 年起**

把模式设置搬进内核。内核成为唯一的显示状态所有者，提供统一的 UAPI：`drmModeSetCrtc` / `drmModeSetPlane` / `drmModePageFlip`。解决了上面所有问题。但引入了新问题，就是下一节要讲的"无法原子、无法预验证、无法扩展"。

**第三代：Atomic KMS，2015 年起（内核 4.0 左右开始稳定）**

把所有状态统一成属性，把所有修改统一成一次提交。这一代还带来了两个重要的附加能力：

- **Universal Planes**：在此之前，primary plane 和 cursor plane是隐藏的，只能通过 `drmModeSetCrtc` / `drmModeSetCursor` 这些专用接口操作。universal planes 把它们统一成普通 plane。
- **可扩展的能力协商**：新功能通过新属性引入，老程序看不到就自动降级，不需要改 UAPI。

> **本系列只用第三代。** 项目里有一条硬约束：`drmModeSetCrtc` / `drmModePageFlip` / `drmModeSetPlane` 一律禁止出现。
>
> 理由不只是"新的更好"，而是：**混用两代接口的行为是未定义的**。legacy 接口在内核里被实现成"构造一个 atomic 请求然后提交"，但它会隐式设置很多你没意识到的状态。混着用会让状态管理变成噩梦。
>



### 8.1 Legacy 接口的问题

早期的 KMS 提供的是一组"命令式"的接口：

```c
drmModeSetCrtc(fd, crtc_id, fb_id, x, y, connectors, count, mode);
drmModeSetPlane(fd, plane_id, crtc_id, fb_id, flags,
                crtc_x, crtc_y, crtc_w, crtc_h,
                src_x, src_y, src_w, src_h);
drmModePageFlip(fd, crtc_id, fb_id, flags, user_data);
```

每个调用改变硬件状态的一部分。问题有三个：

**1. 无法原子地改变多个东西**

假设你要同时移动一个 overlay 并切换主平面的 buffer。用 legacy 接口只能一个一个调，中间有一帧的时间窗口，用户会看到"主平面已经换了但 overlay 还没动"的中间状态。

**2. 无法预先验证**

你不知道一组配置硬件能不能接受，只能真的下发下去看它返回什么。如果失败了，硬件可能已经处于半配置状态。

**3. 无法表达新功能**

每加一个功能就要加一个新的 ioctl，或者往老的 ioctl 里塞参数。`drmModeSetPlane` 的参数已经多到无法阅读了。

### 8.2 Atomic 接口

Atomic KMS 把模型换成了"声明式"：

> **你构造一张 (对象, 属性, 值) 三元组的表，一次性交给内核。内核要么全部应用，要么全部拒绝。**

API 只有四个函数：

```c
drmModeAtomicReq* drmModeAtomicAlloc(void);
int  drmModeAtomicAddProperty(req, object_id, property_id, value);
int  drmModeAtomicCommit(fd, req, flags, user_data);
void drmModeAtomicFree(req);
```

就这些。所有的配置都通过 `AddProperty` 表达。

一次完整的模式设置长这样（伪码）：

```
req = AtomicAlloc()

# 把 connector 接到 CRTC 上
AddProperty(req, connector_id, PROP_CRTC_ID, crtc_id)

# 配置 CRTC：设置模式、激活
mode_blob = CreatePropertyBlob(&mode, sizeof(mode))
AddProperty(req, crtc_id, PROP_MODE_ID, mode_blob)
AddProperty(req, crtc_id, PROP_ACTIVE,  1)

# 配置 primary plane：绑定 framebuffer、设置几何
AddProperty(req, plane_id, PROP_FB_ID,   fb_id)
AddProperty(req, plane_id, PROP_CRTC_ID, crtc_id)
AddProperty(req, plane_id, PROP_SRC_X,   0)
AddProperty(req, plane_id, PROP_SRC_Y,   0)
AddProperty(req, plane_id, PROP_SRC_W,   width  << 16)   # 注意
AddProperty(req, plane_id, PROP_SRC_H,   height << 16)   # 注意
AddProperty(req, plane_id, PROP_CRTC_X,  0)
AddProperty(req, plane_id, PROP_CRTC_Y,  0)
AddProperty(req, plane_id, PROP_CRTC_W,  width)
AddProperty(req, plane_id, PROP_CRTC_H,  height)

AtomicCommit(fd, req, DRM_MODE_ATOMIC_ALLOW_MODESET, NULL)
AtomicFree(req)
```

一共 13 个属性。实测输出：

```
INFO atomic request modeset: 13 properties
INFO   object 142:
INFO     CRTC_ID    (prop 20) = 84 (0x54)
INFO   object 84:
INFO     MODE_ID    (prop 23) = 154 (0x9a)
INFO     ACTIVE     (prop 22) = 1 (0x1)
INFO   object 87:
INFO     FB_ID      (prop 17) = 156 (0x9c)
INFO     CRTC_ID    (prop 20) = 84 (0x54)
INFO     SRC_X      (prop 9) = 0 (0x0)
INFO     SRC_Y      (prop 10) = 0 (0x0)
INFO     SRC_W      (prop 11) = 125829120 (0x7800000)
INFO     SRC_H      (prop 12) = 70778880 (0x4380000)
INFO     CRTC_X     (prop 13) = 0 (0x0)
INFO     CRTC_Y     (prop 14) = 0 (0x0)
INFO     CRTC_W     (prop 15) = 1920 (0x780)
INFO     CRTC_H     (prop 16) = 1080 (0x438)
```

看这张表就能理解 atomic 的本质了：**它就是一张表**，没有别的魔法。



### 8.3 16.16 定点数：新手第一大坑

注意上面 `SRC_W = 125829120 (0x7800000)` 而 `CRTC_W = 1920 (0x780)`。

**`SRC_*` 属性是 16.16 定点数**：高 16 位是整数部分，低 16 位是小数部分。所以 1920 要写成 `1920 << 16 = 0x7800000`。

**`CRTC_*` 属性是普通整数**。1920 就写 1920。

为什么源矩形要用定点？因为**缩放**。当 plane 做缩放时，源矩形的边界可能落在非整数像素上。目标矩形在屏幕上，必然是整数像素。

这个不对称非常容易搞错，而且症状很恶心：内核返回 `-EINVAL`，**不告诉你是哪个属性错了**。少移位 16 位意味着源矩形只有 1/65536 大小，内核判定为非法。

我们的解决方案是**用类型系统堵死**：

```cpp
class Fixed16 {
public:
    static constexpr Fixed16 from_int(uint32_t v) noexcept {
        return Fixed16(static_cast<uint64_t>(v) << 16);
    }
    static constexpr Fixed16 from_raw(uint64_t raw) noexcept {
        return Fixed16(raw);
    }
    constexpr uint64_t raw() const noexcept { return raw_; }
private:
    constexpr explicit Fixed16(uint64_t r) noexcept : raw_(r) {}
    uint64_t raw_ = 0;
};

// 源矩形：16.16 定点
struct SrcRect  { Fixed16 x, y, width, height; };

// 目标矩形：普通整数
struct CrtcRect { int32_t x, y; uint32_t width, height; };
```

`Fixed16` 只能通过 `from_int()` / `from_raw()` 构造，外面拿不到"没移位的裸数"。`SrcRect` 和 `CrtcRect` 是两个不同的类型，互相传参编译不过。

**全工程唯一读 `Fixed16::raw()` 的地方**，是那个负责下发几何属性的函数：

```cpp
Status AtomicRequest::set_plane_geometry(const Plane& plane,
                                         const SrcRect& src,
                                         const CrtcRect& crtc_rect) {
    TRY(add(plane.id, plane.prop_ids.src_x, src.x.raw(),      "SRC_X"));
    TRY(add(plane.id, plane.prop_ids.src_y, src.y.raw(),      "SRC_Y"));
    TRY(add(plane.id, plane.prop_ids.src_w, src.width.raw(),  "SRC_W"));
    TRY(add(plane.id, plane.prop_ids.src_h, src.height.raw(), "SRC_H"));

    // CRTC_X/Y 是有符号的（plane 可以部分移出屏幕），
    // 要走 int32 -> uint32 的位模式转换，不能符号扩展成 64 位
    TRY(add(plane.id, plane.prop_ids.crtc_x, static_cast<uint32_t>(crtc_rect.x), "CRTC_X"));
    TRY(add(plane.id, plane.prop_ids.crtc_y, static_cast<uint32_t>(crtc_rect.y), "CRTC_Y"));
    TRY(add(plane.id, plane.prop_ids.crtc_w, crtc_rect.width,  "CRTC_W"));
    TRY(add(plane.id, plane.prop_ids.crtc_h, crtc_rect.height, "CRTC_H"));
    return Ok();
}
```

工程里不允许出现任何一处手写的 `<< 16`。

### 8.4 TEST_ONLY：先问再做

Atomic 接口最有价值的能力之一：

```c
drmModeAtomicCommit(fd, req, DRM_MODE_ATOMIC_TEST_ONLY, NULL);
```

带这个 flag，内核会**完整走一遍校验流程但不真的应用**。校验包括：

- 属性值是否在合法范围内
- 平面组合硬件能不能支持（层数、缩放比例）
- 显存带宽够不够
- 时钟能不能配出来

返回 0 表示"这个配置可行"，返回错误表示"不可行"。

这个能力是**硬件平面调度器**的基础：合成器可以先试探"能不能把这三个窗口分别放到三个硬件平面上"，不行就退回到 GPU 合成。

对于我们现在，它有一个更朴素的用途：**在真的改变屏幕状态之前，先确认配置是对的**。



### 8.5 提交的几个 flag

```c
DRM_MODE_ATOMIC_TEST_ONLY      // 只校验不应用
DRM_MODE_ATOMIC_NONBLOCK       // 不等 vblank 就返回
DRM_MODE_ATOMIC_ALLOW_MODESET  // 允许做完整模式设置
DRM_MODE_PAGE_FLIP_EVENT       // 完成时投递一个事件
```

**`ALLOW_MODESET` 的语义值得单独说。**

模式设置是重操作：可能要重新配置时钟、重新训练链路、甚至让屏幕黑一下。所以内核要求你显式声明"我知道这次提交可能触发模式设置"。

如果你的提交会改变模式但没带这个 flag，内核直接返回 `EINVAL`。反过来，**稳态的帧提交不应该带这个 flag**。带上它反而会掩盖问题——
如果某次提交意外地触发了模式设置（说明你的状态管理出了 bug），不带 flag 会让它立刻暴露成一个错误，带了就静默地黑一下屏幕过去了。

所以：

```
模式设置：  ALLOW_MODESET
帧提交：    NONBLOCK | PAGE_FLIP_EVENT
```



### 8.6 当提交被拒绝时：属性级定位

Atomic 提交失败时，内核只回一个 `errno`。它**不告诉你**：

- 是哪个对象的问题
- 是哪个属性的问题
- 是不是根本不是单个属性的问题

这在调试时非常痛苦。我们的应对是两步：

**第一步：把请求完整打出来。** 前面展示的那张 13 行的表就是。配合内核的 `drm.debug` 日志（后面讲），可以逐条对照。

**第二步：属性级定位。** 反复用属性子集重试 `TEST_ONLY`，找出"去掉它就能过"的那一条：

```
输入：一个被拒绝的请求，包含 N 条属性
过程：
    for i in 0..N-1:
        构造一个新请求，包含除第 i 条之外的所有属性
        TEST_ONLY
        if 通过:
            报告"第 i 条属性可疑"
            return
    报告"没有单条属性能解释这个拒绝"
```

代价是 O(N) 次额外 ioctl。N 通常是几十，一次 TEST_ONLY 是微秒级，在**出错路径**上完全可以接受。

**必须说清楚这个结果的局限性**：KMS 的约束是**整体性**的——显存带宽、平面层叠数量、缩放比例上限，都不是单条属性能表达的。所以"去掉它就能过"是**强线索**，不是判决书。

但对于"某个属性值超出硬件范围"这类问题，它非常有效。而如果**一条都定位不出来**，那本身就是信息：说明拒绝来自全局约束。



## 九、显存：GEM、dumb buffer 与 framebuffer

回到最开始的第一个问题：那块内存是哪来的。

### 9.1 GEM：图形执行管理器

**GEM**（Graphics Execution Manager）是 DRM 的内存管理层。它管理的对象叫 **GEM object**，每个有一个 32 位的 **handle**。

关键性质：

- **handle 是每个文件描述符私有的**。同一块显存，在进程 A 的 fd 上 handle 可能是 1，在进程 B 的 fd 上可能是 7。
- **handle 不能跨进程传递**。传过去也没用，因为它是 fd-local 的。
- 跨进程共享要用 **PRIME**，把 GEM object 导出成一个 **DMA-BUF 文件描述符**。fd 可以通过 UNIX socket 的辅助数据（`SCM_RIGHTS`）传给别的进程。



### 9.2 dumb buffer：最笨但最通用的分配方式

GEM 的分配接口是**厂商特定**的——Intel 有 `i915_gem_create`，AMD 有 `amdgpu_gem_create`，各不相同。

但 KMS 提供了一个**通用**的分配接口，叫 **dumb buffer**：

```c
// 1. 分配
struct drm_mode_create_dumb create = {
    .width  = 1920,
    .height = 1080,
    .bpp    = 32,
};
ioctl(fd, DRM_IOCTL_MODE_CREATE_DUMB, &create);
// 返回：create.handle, create.pitch, create.size

// 2. 获取 mmap 偏移
struct drm_mode_map_dumb map = { .handle = create.handle };
ioctl(fd, DRM_IOCTL_MODE_MAP_DUMB, &map);
// 返回：map.offset

// 3. 映射到用户态
void* pixels = mmap(NULL, create.size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, map.offset);

// 4. 用完释放
struct drm_mode_destroy_dumb destroy = { .handle = create.handle };
ioctl(fd, DRM_IOCTL_MODE_DESTROY_DUMB, &destroy);
```

"dumb"（笨）这个名字是自嘲。它笨在三点：

1. **只能线性排布**，GPU 读它很慢
2. **不保证能跨进程共享**（没有 PRIME 语义保证）
3. **CPU 写入很慢**（后面解释）

但它有一个巨大的优点：**通用**。任何支持 KMS 的驱动都必须实现它。所以它是"验证显示通路是否打通"的最短路径，非常适合作为第一步。



### 9.3 pitch：不要用 width × 4

注意 `CREATE_DUMB` 返回的是 `pitch`，而不是让你指定。

**pitch（行跨距）是一行占用的字节数**，驱动会按硬件对齐要求向上取整。

虽然 1920 × 4 = 7680，但硬件可能要求 128 字节对齐，那 pitch 可能是 7680（正好对齐）或者更大的值。

**用 `width * 4` 做行偏移是最常见的花屏原因。** 正确的写法：

```cpp
uint32_t* row(uint32_t y) {
    return reinterpret_cast<uint32_t*>(pixels + y * pitch);
    //                                              ^^^^^ 不是 width * 4
}
```

同理，`size` 也可能大于 `pitch * height`，要用驱动给的值去 mmap。



### 9.4 write-combining 内存：为什么 CPU 写显存很慢

dumb buffer 映射出来的内存，通常是 **write-combining（WC）** 属性的。

WC 内存的特点：

- **顺序宽写很快**：CPU 有一个写合并缓冲区，会把连续的写攒成一次总线事务
- **随机读极慢**：不走缓存，每次读都是一次总线往返
- **随机写也慢**：破坏写合并

> 为什么要这样？
>
> 因为这块内存是给显示控制器读的。
>
> 如果走正常的缓存策略，CPU 写完之后数据可能还在 cache 里，显示控制器读到的是旧数据。
>
> WC 是"不缓存但允许写合并"的折中。

**实践含义**：画图时**只顺序写，绝不读回**。

我们的 demo 里，绘制函数是这样组织的：

```cpp
void draw_frame(DumbBuffer& buffer, uint64_t frame) {
    // 先在普通内存（有缓存）里拼好一整行
    static std::vector<uint32_t> normal_row;
    static std::vector<uint32_t> band_row;
    normal_row.resize(size.width);
    band_row.resize(size.width);

    for (uint32_t x = 0; x < size.width; ++x) {
        // ... 计算这个 x 位置的颜色，写进普通内存
    }

    // 然后一次 memcpy 到 WC 内存，一整行一整行地写
    for (uint32_t y = 0; y < size.height; ++y) {
        const uint32_t* source = in_band ? band_row.data() : normal_row.data();
        std::memcpy(buffer.row(y), source, row_bytes);
    }
}
```

复杂的逐像素计算在有缓存的普通内存里做，只有最终的顺序写穿过 WC 内存。1080p 每帧 8 MiB，在弱一点的板子上大约几毫秒。



### 9.5 Framebuffer：显示控制器认识的形式

有了 GEM handle 还不够。显示控制器还需要知道：宽多少、高多少、什么格式、行跨距多少、（可选）什么 modifier。

把这些打包成一个 KMS 对象，就是 **framebuffer**，有自己的 `fb_id`：

```c
uint32_t handles[4] = { gem_handle, 0, 0, 0 };
uint32_t pitches[4] = { pitch, 0, 0, 0 };
uint32_t offsets[4] = { 0, 0, 0, 0 };
uint32_t fb_id;

drmModeAddFB2(fd, width, height, DRM_FORMAT_XRGB8888, handles, pitches, offsets, &fb_id, 0);
```

数组是 4 个，因为多平面格式（如 NV12 的 Y 平面和 UV 平面）需要多个 handle。

**销毁**用 `drmModeRmFB(fd, fb_id)`。

**这里有一个非常重要的区分**，涉及两个不同的 API：

```c
// 路径 A：不传 modifier，内核按驱动默认推断排布
drmModeAddFB2(fd, w, h, format, handles, pitches, offsets, &fb_id, 0);

// 路径 B：显式传 modifier
drmModeAddFB2WithModifiers(fd, w, h, format, handles, pitches, offsets,
                           modifiers, &fb_id, DRM_MODE_FB_MODIFIERS);
```

**路径 A + 线性内存 ≠ 路径 B + `DRM_FORMAT_MOD_LINEAR`。**

它们在内核里走的是不同的代码分支。路径 B 需要 `DRM_CAP_ADDFB2_MODIFIERS` 能力，而且某些驱动对显式传 LINEAR 的处理和默认推断不一样。

所以在数据结构上，"没有 modifier 信息"必须和"确定是线性排布"区分开：

```cpp
inline constexpr Modifier kModifierLinear{0};
inline constexpr Modifier kModifierInvalid{0x00ffffffffffffffULL};  // 表示"未知"
```

当驱动没有 `IN_FORMATS` 属性时，我们只能拿到裸的格式列表，这时候记 `kModifierInvalid` 而**不是** `kModifierLinear`，后续走路径 A。



### 9.6 三层对象的销毁顺序

`GEM object` → `framebuffer` → `plane 绑定`，是一条引用链。销毁必须逆序：

```cpp
DumbBuffer::~DumbBuffer() {
    // 1. 先撤 framebuffer（它引用着 GEM 对象）
    fb_.reset();

    // 2. 再解除 mmap
    if (pixels_ != nullptr) {
        munmap(pixels_, byte_size_);
    }

    // 3. 最后销毁 GEM 对象
    if (handle_ != GemHandle{0}) {
        drm_mode_destroy_dumb destroy{ .handle = handle_ };
        ioctl(fd_, DRM_IOCTL_MODE_DESTROY_DUMB, &destroy);
    }
}
```

顺序反了，内核会拒绝销毁一个还被引用的对象，导致泄漏。

而在更上层，**退出时必须先解除 plane 对 framebuffer 的绑定**，否则 framebuffer 还被 KMS 状态引用着：

```
teardown 提交（一次 atomic commit 完成）：
    for each plane on this CRTC:
        FB_ID   = 0
        CRTC_ID = 0
    CRTC.ACTIVE  = 0
    CRTC.MODE_ID = 0
    connector.CRTC_ID = 0
```

注意 `FB_ID` 和 `CRTC_ID` 必须**同时置 0**。只置一个内核会拒绝——"plane 有 fb 但没 crtc"和"有 crtc 但没 fb"都是非法状态。



### 9.7 算一笔带宽账

显示系统里，**内存带宽往往比算力更早成为瓶颈**。学会估算它很重要。

扫描输出本身的带宽需求：

```
1920 × 1080 × 4 字节 × 60 Hz = 497 MB/s
3840 × 2160 × 4 字节 × 60 Hz = 1.99 GB/s
3840 × 2160 × 4 字节 × 120 Hz = 3.98 GB/s
```

**这是显示控制器必须持续、无中断地读到的量。** 一旦跟不上，FIFO 欠载（underrun），屏幕上出现闪烁或横条。内核日志里会看到类似 `underrun` 或 `FIFO underflow` 的错误。

现在加上合成：如果用 GPU 把三个图层合成到一张输出：

```
读三个图层：   3 × 497 MB/s = 1.49 GB/s
写输出：             497 MB/s
扫描读输出：         497 MB/s
                  ─────────────
合计：              2.48 GB/s
```

而如果三个图层各走一个硬件 plane：

```
扫描时读三个图层：   1.49 GB/s
```

省掉了 1 GB/s。这就是硬件平面调度的价值所在，也是为什么内核会用 `TEST_ONLY` 拒绝"看起来合法但带宽超标"的配置。

**这也解释了为什么 tiling 和压缩有意义**——见下一节。



### 9.8 tiling 与压缩：modifier 背后的真实动机

前面说 modifier 是"不透明的排布描述符"。现在讲讲它描述的到底是什么，以及为什么值得存在。

**线性排布的问题**

线性排布下，第 (x, y) 个像素的地址是 `base + y * pitch + x * 4`。

现在考虑 GPU 渲染一个三角形。三角形是二维的，GPU 通常按**2×2 或 4×4 的小块**并行处理片元。这些相邻的片元在屏幕上是上下左右相邻的，但在线性内存里：

```
(0,0) 和 (1,0) 相邻    → 内存地址差 4 字节，同一条 cache line ✓
(0,0) 和 (0,1) 相邻    → 内存地址差 7680 字节，不同的 cache line ✗
                          甚至可能在不同的 DRAM page
```

DRAM 有一个特性：**访问同一个 row（页）内的数据很快，跨 row 要先 precharge 再 activate，代价高**。线性排布下垂直方向的访问几乎必然跨 row。

**tiling（平铺）的解法**

把图像切成小块（tile），比如 16×16 像素，**块内连续存储**：

```
线性：
  行 0: [ 0][ 1][ 2][ 3][ 4][ 5][ 6][ 7] ...
  行 1: [ 8][ 9][10][11][12][13][14][15] ...

4×2 tile：
  tile 0 存放: 行0的0~3, 行1的0~3   → 连续 8 个像素
  tile 1 存放: 行0的4~7, 行1的4~7
```

这样一个 2D 的小区域落在连续的内存里，cache 命中率和 DRAM 行命中率都大幅提高。实测能带来 20%~50% 的带宽收益，视访问模式而定。

代价是**寻址变复杂**，而且每家的 tile 尺寸、排列顺序、交织方式都不一样。这就是为什么 modifier 是厂商私有的。

**压缩**

更进一步，有些硬件支持**帧缓冲压缩**：

- 每个 tile 附带一小块元数据，记录这个 tile 用了几个字节
- 纯色或渐变区域压缩率很高，噪声区域压缩率低
- **无损**，所以对画质没有影响

厂商各有名字：Intel 叫 CCS（Color Control Surface），AMD 叫 DCC（Delta Color Compression），ARM 叫 AFBC。

压缩的收益在 4K 以上尤其明显——省下来的带宽直接转化为功耗和散热。



> **为什么合成器不该理解 modifier 的语义**
>
> 看完上面你可能会想："既然知道 tiling 更快，合成器就该优先选带 tiling 的 modifier 啊。"
>
> 这个想法是错的，理由有三：
>
> 1. **合成器无法判断哪个更快。** "更快"取决于生产者是谁、消费者是谁。某个 modifier 可能 GPU 写得快但显示控制器读得慢。只有驱动知道。
>    
> 2. **modifier 的编码是私有且会变的。** 今天 `0x...0021` 表示某种 tiling，下一代硬件可能换个含义。任何 `(mod >> 56) == VENDOR_FOO` 的判断都是在给未来埋雷。
>    
> 3. **正确的机制已经存在。** `linux-dmabuf` 协议有一个**feedback + tranche** 机制：合成器把 modifier 列表按优先级分组（tranche）发给客户端，客户端的 UMD 从中挑一个它也支持的。两边的驱动各自知道自己那边的性能特性，交集就是最优解。
>
> 
>
> 所以合成器的职责只有三条：
>
> 1. 从 plane 的 IN_FORMATS 读出 (format, modifier) 集合    ← 不解析
> 2. 按优先级分组转发给客户端                                ← 原样转发
> 3. 客户端回传 buffer，原样交给 addfb2，失败就降级           ← 不判断
>
> 这是一条**架构原则**，不是代码风格偏好。违反它的代码在换一代硬件时必然出问题。



### 9.9 显存从哪来：物理连续、IOMMU 与 CMA

最后一个显存相关的话题：显示控制器对内存有什么要求？

**要求：显示控制器必须能持续、低延迟地访问这块内存。**

具体表现取决于系统架构：

**独立显卡（有专用显存）**

显存是显卡上的 GDDR/HBM，通过 PCIe BAR 映射。分配就是在显存里划一块，天然满足所有要求。
CPU 访问要走 PCIe，所以很慢——这是为什么独显上CPU 直接写显存是个坏主意。

**集成显卡 / SoC（统一内存）**

显存就是系统 DRAM 的一部分。这时候有两种情况：

- 有 IOMMU（或 SMMU）：显示控制器通过 IOMMU 访问内存，IOMMU 做虚拟地址到物理地址的翻译。这样内存**不需要物理连续**，分散的页面可以被映射成连续的设备地址空间。现代 SoC 基本都有。
- 没有 IOMMU：显示控制器只能用物理地址，所以那块内存必须**物理连续**。

> 物理连续的大块内存在系统跑久了之后很难分配到（内存碎片化）。
>
> Linux 的解法是 **CMA**（Contiguous Memory Allocator）：启动时预留一块连续区域，平时可以被可移动页面借用，需要时把那些页面迁走腾出连续空间。
>
> 内核启动参数里的 `cma=256M` 就是在配这个。如果一个嵌入式设备报"分配 framebuffer 失败"，八成是 CMA 区域太小。
>

**为什么这对我们重要？**

因为它解释了 dumb buffer 的一个行为：

`DRM_IOCTL_MODE_CREATE_DUMB` 返回的 `size` 可能大于 `pitch × height`，而且 `pitch` 会被对齐到某个值。这些都是硬件对齐要求（比如 DMA 引擎要求 64 或 256 字节对齐）的体现。

也解释了为什么 dumb buffer 的内存是 write-combining 而不是 cached：如果是 cached，CPU 写完之后数据可能还在 cache 里，显示控制器（不经过 CPU cache）读到的是旧数据。要么每次写完 flush cache（慢且容易漏），要么干脆不缓存。

**一致性（coherency）**是这个领域一个反复出现的主题。后面讲 DMA-BUF 时会再遇到：跨设备共享一块内存时，谁负责保证 cache 一致性，是一个需要显式处理的问题。



## 十、一帧的完整生命周期

现在把所有东西串起来。

### 10.1 双缓冲

单缓冲一定会撕裂：你在写的同时显示控制器在读。

双缓冲的思路：

```
buffer A ← 显示控制器正在扫描
buffer B ← CPU/GPU 正在画

画完 B 之后，请求"下一个 VBlank 时切换到 B"

VBlank 到来，硬件切换：
buffer B ← 显示控制器正在扫描
buffer A ← 现在可以安全地画了
```

关键点：

提交之后不能立刻去写另一个 buffer。必须等到"切换完成"的确认，才知道上一个 buffer 空出来了。

这个确认就是 **page flip 完成事件**。



### 10.2 帧循环的骨架

```
初始化：
    分配 N 个 buffer（N ≥ 2）
    做一次完整的模式设置
    in_flight = 0

每一帧：
    1. buffer = 取一个当前没在扫描的
    2. 在 buffer 上绘制
    3. 构造 atomic request：plane.FB_ID = buffer.fb_id
    4. commit(NONBLOCK | PAGE_FLIP_EVENT, user_data = frame_number)
       in_flight += 1
    5. poll(drm_fd) 等待可读
    6. read(drm_fd) 读出事件，解析
       in_flight -= 1
       记录 vblank 时间戳和序号
```

用文字描述这个时序：

```
时刻 t0   ：CPU 在 buffer B 上绘制，硬件在扫描 buffer A
时刻 t1   ：CPU 提交 "下个 VBlank 切到 B"，立即返回（NONBLOCK）
时刻 t1~t2：CPU 空闲（在 poll），硬件继续扫描 A
时刻 t2   ：VBlank 到来，硬件切换到 B，内核投递事件
时刻 t2+  ：CPU 被 poll 唤醒，读到事件，知道 A 空出来了
           开始在 A 上绘制下一帧
```



### 10.3 DRM 事件的格式

内核通过**读 DRM fd** 来投递事件。这不是 `ioctl`，是普通的 `read(2)`。

事件格式：

```c
struct drm_event {
    __u32 type;      // DRM_EVENT_VBLANK 或 DRM_EVENT_FLIP_COMPLETE
    __u32 length;    // 整个事件的字节数
};

struct drm_event_vblank {
    struct drm_event base;
    __u64 user_data;   // 你提交时传的值，原样返回
    __u32 tv_sec;      // 时间戳（秒）
    __u32 tv_usec;     // 时间戳（微秒）
    __u32 sequence;    // vblank 序号
    __u32 crtc_id;     // 哪个 CRTC（需要 DRM_CAP_CRTC_IN_VBLANK_EVENT）
};
```

**一次 `read` 可能返回多个事件**，必须循环解析：

```
读一个缓冲区
offset = 0
while offset + sizeof(drm_event) <= 已读字节数:
    读出 header（type, length）
    校验 length 合法且不越界
    switch header.type:
        case FLIP_COMPLETE / VBLANK:
            解析 drm_event_vblank
            处理
        default:
            跳过（内核以后可能加新类型）
    offset += header.length
```

libdrm 提供了 `drmHandleEvent()` 帮你做这件事（回调式）。


### 10.4 时间戳的时钟域

`tv_sec` / `tv_usec` 用的是哪个时钟？取决于一个能力位：

```c
uint64_t value;
drmGetCap(fd, DRM_CAP_TIMESTAMP_MONOTONIC, &value);
// value == 1 → CLOCK_MONOTONIC
// value == 0 → CLOCK_REALTIME（老驱动）
```

**这个区别很要命。** `CLOCK_REALTIME` 是墙钟，会被 NTP 调整、会被手动改、会跳变。拿它算帧间隔，某次 NTP 同步就能让你的帧节拍算法疯掉。

所以代码里必须探测，不能假设：

```cpp
if (timestamp_is_monotonic) {
    event.timestamp_ns = raw_ns;
} else {
    // 只能采样一次偏移做转换，本身就是有损的
    uint64_t offset = sample_realtime_to_monotonic_offset();
    event.timestamp_ns = raw_ns - offset;
    LOG_WARN("vblank timestamps are CLOCK_REALTIME; frame pacing will drift "
             "if the wall clock is adjusted");
}
```



### 10.5 用 sequence 检测丢帧

`sequence` 是 **vblank 计数**，不是帧计数。它随硬件的每一次垂直消隐递增，和你有没有提交无关。

所以：

```
相邻两次事件的 sequence 差 == 1  → 每个刷新周期都上屏了一帧
相邻两次事件的 sequence 差 >  1  → 中间漏掉了 (差 - 1) 个刷新周期
```

这是**丢帧最直接、最可靠的证据**，比测墙钟时间准确得多。

```cpp
void FrameStats::record(const FlipEvent& event) noexcept {
    if (frames > 0) {
        if (event.sequence > last_sequence) {
            uint64_t gap = event.sequence - last_sequence;
            if (gap > 1) {
                dropped += gap - 1;
            }
        }
        // ... 统计间隔的 min/max/平均
    }
    last_sequence = event.sequence;
    last_timestamp_ns = event.timestamp_ns;
    ++frames;
}
```

实测输出：

```
VKMS：  frames=300 fps=60.00 interval=16.666ms [16.665, 16.666] dropped=0
真硬件：frames=600 fps=60.00 interval=16.667ms [16.387, 16.948] dropped=0
```

VKMS 是软件定时器，间隔规整到 0.001ms 以内。真实硬件有 ±0.3ms 的抖动，这是 PLL 频率偏差加上时间戳测量误差的正常范围。



### 10.6 同步：这个系统里最难的部分

这一节值得多花点篇幅，因为它是整个显示栈里概念最绕、也最容易出微妙 bug 的地方。

**问题的根源：一切都是异步的**

回顾一下这个系统里有几个独立运行的执行单元：

```
CPU（应用进程）      构造渲染命令
GPU                 执行渲染命令
显示控制器           扫描输出
视频解码器           解码出 YUV 帧
CPU（合成器进程）    决定怎么合成
```

它们通过内存耦合，但各自的进度**互不知晓**。

当你调用 `glFlush()` 或 `vkQueueSubmit()` 返回时，GPU 可能一条命令都还没执行。命令只是被放进了队列。

如果这时候直接把 buffer 提交给 KMS，显示控制器可能扫描到一张**半成品**——上半部分是新内容，下半部分还是旧内容或者垃圾数据。

所以必须有某种机制表达："这块 buffer 在某个操作完成之前不能读。"

**dma_fence：内核的同步原语**

`dma_fence` 是 Linux 内核里表达"一个异步操作的完成"的对象。它的状态机极其简单：

```
创建 → 未 signal → signal（一次性，不可逆）
```

可以：
- 查询是否已 signal
- 阻塞等待它 signal
- 注册回调，signal 时被调用

GPU 驱动在提交一批命令时创建一个 fence，GPU 执行完这批命令后（通过中断）signal 它。

**隐式同步（implicit sync）**

传统做法是把 fence **挂在 buffer 上**。

每个 DMA-BUF（或 GEM object）内部有一个 `dma_resv` 结构，里面存着两类 fence：

```
exclusive fence   写操作的 fence。要读或写这个 buffer，必须等它。
shared fences     读操作的 fence 列表。要写这个 buffer，必须等所有的。
```

规则就是经典的读写锁语义：

```
提交一个"写 buffer X"的操作 → 等 X 的 exclusive + 所有 shared
                            → 完成后设置 X 的新 exclusive

提交一个"读 buffer X"的操作 → 只等 X 的 exclusive
                            → 完成后把自己加进 X 的 shared 列表
```

**好处**：完全透明。应用什么都不用做，内核自动串起依赖。一个 buffer 从 GPU 渲染到 KMS 扫描，中间的等待是自动的。

**坏处**：

1. **粒度太粗。** 内核只知道"这个 buffer 被写过"，不知道你的实际依赖。它只能保守地等。
   
2. **无法表达跨设备的复杂依赖。** 比如"等 GPU 的第 3 个 pass" 这种细粒度需求表达不了。
   
3. **对现代 GPU API 不友好。** Vulkan 的模型是显式同步的，把它硬套进隐式模型会引入不必要的等待。
   
4. **调试困难。** 一个莫名其妙的卡顿，可能是某个你没意识到的隐式依赖造成的。

**显式同步（explicit sync）**

思路是把 fence 从 buffer 里**剥离出来**，变成独立传递的对象。

Linux 提供两种表示：

**`sync_file`** —— 一个文件描述符，代表一个（或一组）fence。可以通过 `poll()` 等待，可以通过 UNIX socket 传给别的进程。

```c
// 从 EGL 拿一个 fence fd
EGLSyncKHR sync = eglCreateSyncKHR(dpy, EGL_SYNC_NATIVE_FENCE_ANDROID, NULL);
int fence_fd = eglDupNativeFenceFDANDROID(dpy, sync);
```

**`drm_syncobj`** —— 一个容器，里面可以放 fence。
分两种：

```
binary syncobj    容器里放一个 fence，signal 一次就完了
timeline syncobj  容器里是一条时间线，用 uint64 的点标记进度
                  "等到第 42 个点" / "signal 第 43 个点"
```

timeline syncobj 是 Vulkan timeline semaphore 的内核实现，它比 binary 更灵活：可以先等一个还没被 signal 的点（生产者还没提交），不会死锁。

**KMS 侧的显式同步**

KMS 通过两个属性支持显式同步：

```
plane 的 IN_FENCE_FD 属性
    提交时挂一个 sync_file fd 上去
    硬件会等这个 fence signal 之后才切换扫描地址
    ← 这样 CPU 完全不用阻塞

CRTC 的 OUT_FENCE_PTR 属性
    提交时传一个指向 int 的指针
    内核会在这里写回一个新的 fence fd
    它在这一帧真正上屏后 signal
    ← 用来通知客户端"你的 buffer 已经被扫描完了，可以复用"
```

有了这两个，合成器的帧循环变成：

```
收到客户端的 (buffer, acquire_fence)
    ↓
构造 atomic 请求：
    plane.FB_ID       = buffer 的 fb
    plane.IN_FENCE_FD = acquire_fence      ← 硬件自己去等
    crtc.OUT_FENCE_PTR = &release_fence
    ↓
提交（不阻塞！CPU 立刻返回）
    ↓
把 release_fence 发回客户端
    ↓
客户端拿到后知道：这个 fence signal 时，我的 buffer 就空出来了
```

**整条链路里 CPU 一次都没有阻塞等待 GPU。**这是显式同步最大的价值。



**一个重要的实践细节**

`DRM_CAP_SYNCOBJ` 是**渲染侧**的能力。在某些平台上，KMS 节点报告不支持 syncobj，而对应的 render node 支持。

这不矛盾：它们是同一个物理设备的两个不同 DRM 节点，能力集不同。KMS 侧的显式同步只需要 `sync_file` fd（`IN_FENCE_FD` / `OUT_FENCE_PTR` 属性），和 syncobj 无关。

不理解这一点，很容易在探测到 `syncobj=0` 时误判"这个平台不支持显式同步"而放弃整条路径。

**正确的探测方式**是分开看：

```
KMS 提交侧能不能做显式同步？
    → 看 plane 有没有 IN_FENCE_FD 属性
    → 看 CRTC 有没有 OUT_FENCE_PTR 属性

协议侧（linux-drm-syncobj-v1）能不能做？
    → 看 render node 的 DRM_CAP_SYNCOBJ_TIMELINE
```

这也是"运行时能力探测"这条原则的一个具体体现：不要用一个笼统的"支不支持"来概括，而要按你实际依赖的具体机制去探测。

**这一节的内容会在后面的阶段展开实现。** 现在需要记住的是：

1. 一切都是异步的，同步是显式设计出来的，不是天然存在的
2. 隐式同步透明但粗粒度，显式同步精确但要自己管理
3. fence 的传递用 fd，所有权管理必须严格（这就是为什么前面那么强调 `UniqueFd`）



### 10.6.1 回到双缓冲：为什么这一讲可以不管 fence

讲了这么多同步，回头看我们这一讲的帧循环，会发现它一个 fence 都没用。为什么可以？

因为**我们用的是 CPU 绘制**。

```
CPU 用 memcpy 写完 buffer   ← 这是同步的，返回时数据已经在内存里
    ↓
提交给 KMS
    ↓
硬件扫描
```

`memcpy` 返回时，写操作已经完成（write-combining 缓冲区会在后续的内存屏障或缓冲区满时刷出，而 `ioctl` 本身就是一个屏障）。没有任何异步操作需要等待。

而"上一帧的 buffer 什么时候空出来"这个问题，我们是用 **page flip 完成事件**来回答的——那本身就是一种同步机制，只不过是通过事件而不是 fence 表达的。

**从下一讲开始就不行了。** 一旦引入 GPU 渲染，`glFlush()` 返回不代表画完，就必须处理同步。届时有两条路：

- **靠隐式同步**：什么都不做，内核自动串起依赖。能工作，但不够精确。
- **走显式同步**：从 EGL 拿 fence fd，挂到 plane 的 `IN_FENCE_FD` 上。

我们会先用前者跑通，再换成后者，这样能亲眼看到两者的差异。



### 10.7 延迟是怎么构成的

"从我动鼠标到屏幕上光标移动"这段时间由哪些部分组成？这个问题对做交互式系统的人很重要。

```
输入设备采样        1 ~ 8 ms    （USB 鼠标 125Hz ~ 1000Hz）
内核处理 + 唤醒     < 1 ms
应用渲染           1 ~ 16 ms
合成器合成          1 ~ 5 ms
等待下一个 VBlank   0 ~ 16.7 ms  ← 平均 8.3 ms
扫描输出到该像素    0 ~ 16.7 ms  ← 取决于像素在屏幕上的位置
显示器内部处理      5 ~ 40 ms    ← 面板响应 + 内部图像处理
```

几个值得注意的点：

**"等待下一个 VBlank"是纯粹的等待。** 如果你的合成在 VBlank 刚过去之后完成，就要白等 16.7ms。这是**帧节拍控制（frame pacing）**要优化的核心——理想情况是"刚好在 VBlank 之前完成提交"。

**缓冲深度直接影响延迟。** 每多一层缓冲，就多一帧的延迟：

```
双缓冲：  画 → 等 VBlank → 显示            延迟 ~1 帧
三缓冲：  画 → 排队 → 等 VBlank → 显示      延迟 ~2 帧
```

三缓冲的好处是**抗抖动**：某一帧画得慢了，还有一帧库存顶着，不会掉帧。代价是多一帧延迟。

游戏和交互式应用倾向双缓冲（低延迟），视频播放倾向三缓冲（平滑优先）。合成器应该让这个可配。

**扫描输出的位置也影响延迟。** 屏幕顶部的像素在 VBlank 结束后立刻被扫描，底部的像素要等 16ms 之后。所以同一帧里，
屏幕底部的内容比顶部"旧" 16ms。这在 VR 里是个大问题，解决方案叫 "beam racing" 或 "racing the beam"——在扫描线后面紧跟着渲染。

**显示器内部处理往往是最大的一块。** 很多显示器有"游戏模式"，就是关掉内部的各种图像增强处理，把这一段从 40ms 压到 5ms。



### 10.8 撕裂、垂直同步与 VRR

前面讲过撕裂的成因。现在把几种应对策略摆在一起对比。

**策略一：不同步（允许撕裂）**

```
画完就立刻切换地址，不等 VBlank
```

延迟最低，帧率不受刷新率限制。代价是撕裂。竞技游戏玩家有时会选这个。

在 KMS 里对应 `DRM_MODE_PAGE_FLIP_ASYNC` 标志（atomic 版本是内核 6.8+ 才有的 `DRM_MODE_ATOMIC_ASYNC`）。

**策略二：垂直同步（VSync）**

```
画完之后等下一个 VBlank 再切换
```

无撕裂。但如果渲染时间超过一个刷新周期，会掉到刷新率的一半：

```
刷新率 60Hz（16.7ms 一帧）
渲染耗时 18ms  →  错过第一个 VBlank，只能等第二个
                →  实际帧率变成 30fps，而不是 55fps
```

这个"帧率断崖"是 VSync 最被诟病的地方。

**策略三：三缓冲 + VSync**

多一层缓冲吸收抖动，避免断崖。代价是延迟。

**策略四：VRR（可变刷新率）**

Adaptive-Sync / FreeSync / G-Sync 的统称。思路是：**让显示器等应用，而不是应用等显示器。**

实现方式是**动态拉长垂直消隐期**。前面讲过帧时长是`htotal × vtotal / clock`；VRR 就是在运行时调整 `vtotal`：

```
渲染快（10ms）→ vtotal 小 → 刷新率高
渲染慢（20ms）→ vtotal 大 → 刷新率低
```

这样每一帧都是"画完就显示"，既无撕裂又无断崖。

约束是显示器有一个**支持的刷新率范围**（比如 48~144Hz）。低于下限时要用 LFC（Low Framerate Compensation），把同一帧显示两次。

KMS 里的接口：

```
connector 的 vrr_capable 属性   （只读）→ 这个显示器支不支持
CRTC 的 VRR_ENABLED 属性        （可写）→ 开不开
```

开启后，提交的时机就直接决定了刷新时机。这是 Step 7 的内容。



### 10.9 帧节拍：为什么需要精确的时间戳

假设你要平滑地播放一段 24fps 的电影，屏幕是 60Hz。24 和 60 不整除，所以必须做 **3:2 pulldown**：

```
电影帧 1 → 显示 3 个刷新周期
电影帧 2 → 显示 2 个刷新周期
电影帧 3 → 显示 3 个
...
```

要做对这件事，播放器需要知道：

1. **上一帧是什么时候真正出光的**（不是什么时候提交的）
2. **刷新周期有多长**（精确到微秒，不能用取整的 vrefresh）
3. **下一帧的预期出光时刻**

这三个信息，KMS 通过 page flip 完成事件提供：

```c
struct drm_event_vblank {
    __u64 user_data;   // 哪一帧
    __u32 tv_sec;      // 什么时候出光
    __u32 tv_usec;
    __u32 sequence;    // 第几个刷新周期
    __u32 crtc_id;
};
```

Wayland 侧通过 `wp_presentation_feedback` 协议把这些信息转发给客户端。

**为什么"提交时间"不能替代"出光时间"？**

因为提交是异步的。你在 t=0 提交，实际生效可能是 t=5ms 的那个 VBlank，也可能因为提交晚了而落到 t=21.7ms 的下一个。只看提交时间，你无法区分这两种情况。

而 `sequence` 让这件事变得可判定：

```
上一帧 sequence = 100
这一帧 sequence = 101  →  连续，没丢帧
这一帧 sequence = 103  →  丢了 2 个刷新周期
```

这是**丢帧检测的黄金标准**。任何基于墙钟时间的判断都不如它可靠，因为墙钟测量本身有误差，而 sequence 是硬件计数器。



### 10.10 提交时机：一个常见的错误模式

新手写帧循环容易写成这样：

```
while (running) {
    draw();
    commit();
    sleep(16ms);      // ← 错
}
```

问题：

1. `sleep` 的精度不够，而且会漂移
2. 没有任何机制知道上一帧是否真的上屏了
3. 不知道自己是不是提交晚了

正确的模式是**事件驱动**：

```
while (running) {
    draw(buffer);
    commit(buffer, NONBLOCK | PAGE_FLIP_EVENT);

    poll(drm_fd);              // 阻塞在这里，直到 flip 完成
    read_and_parse_events();   // 拿到精确的出光时间和 sequence
}
```

这个循环**自然地被硬件节流**到刷新率，不需要任何 sleep。而且每一轮都能拿到准确的时序反馈。

更高级的做法（Step 7 会讲）是**预测 + 提前提交**：

```
根据历史数据估算：渲染耗时 R，合成耗时 C
下一个 VBlank 在 T
则应该在 T - R - C - 安全余量 时开始画这一帧
```

这样能把延迟压到最低，同时不掉帧。



## 十一、环境探查：那些命令到底在做什么

这一节解释在动手写代码之前，怎么摸清一个陌生平台的显示能力。

### 11.1 `/sys/class/drm/` 的结构

sysfs 暴露了 DRM 的设备树：

```bash
$ ls /sys/class/drm/
card0  card0-HDMI-A-1  card0-eDP-1  card1  renderD128  version
```

- `cardN` —— 一个 DRM 设备
- `cardN-<connector名>` —— 该设备下的一个 connector

每个 connector 目录下有：

```bash
$ cat /sys/class/drm/card0-HDMI-A-1/status
connected

$ cat /sys/class/drm/card0-HDMI-A-1/modes
1920x1080
1680x1050
...

$ xxd /sys/class/drm/card0-HDMI-A-1/edid | head
```

**注意**：读 `status` 可能触发一次强制探测（阻塞几十毫秒）。

查设备到驱动的绑定：

```bash
$ for d in /sys/class/drm/card[0-9]; do
    echo "$d driver=$(basename $(readlink -f $d/device/driver))"
  done
/sys/class/drm/card0 driver=i915
/sys/class/drm/card1 driver=i915
```

这里 `device/driver` 是一个符号链接，指向内核设备模型里绑定的驱动。**注意这是 PCI/platform 驱动名，不是 DRM 驱动名。**

| **维度**       | **总线驱动（PCI / Platform Driver）**                        | **DRM 子系统驱动（DRM Driver）**                             |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **内核结构体** | `struct pci_driver` 或 `struct platform_driver`              | `struct drm_driver`                                          |
| **关注职责**   | 硬件接入与总线交互（PCI ID 匹配、`probe`、BAR 空间映射、中断分配、PCI 电源管理） | 图形与显示抽象（GEM/TTM 内存管理、KMS 管道、Plane/CRTC 调度、向用户态提供 IOCTL） |
| **注册入口**   | `pci_register_driver()`                                      | `drm_dev_register()`                                         |
| **名称来源**   | `pci_driver.name`（体现在 `/sys/bus/pci/drivers/`）          | `drm_driver.name`（由 `DRM_IOCTL_VERSION` 返回）             |

用户态图形栈（如 Mesa、libGL、GBM）在查找并加载 `<xx>_dri.so`DRI 驱动时，依靠的是 **DRM 驱动名（`drm_driver.name`）** 以及 **硬件 PCI ID**，与总线驱动名（`pci_driver.name`）无关。



### 11.2 `modetest`

`modetest` 是 libdrm 自带的测试工具，是探查 KMS 资源的标准手段。

```bash
# 列出 connector 和它们支持的模式
sudo modetest -M <driver> -c

# 列出 CRTC、plane 和格式
sudo modetest -M <driver> -p

# 实际点屏测试
sudo modetest -M <driver> -s <connector_id>:<mode>

#例如, vsdrm 是驱动名称, 142 是 connector_id, 1920x1080 是所支持的一个 mode
sudo modetest -M vsdrm -s 142:1920x1080
```

**`-M` 参数要的是 DRM 驱动名**（`drmGetVersion()` 返回的那个），不是 PCI 驱动名，也不是设备节点名。

这一点非常容易搞错：用错了名字，modetest 会打开另一个节点，输出一张空的资源表，让你以为"这个设备没有显示能力"。

怎么知道 DRM 驱动名？两个办法：

办法一：逐个试

```shell
# 如果有 debugfs, 用 sudo 执行
for n in /sys/kernel/debug/dri/[0-9]*; do 
	[ -d "$n" ] && echo "Node $(basename "$n"): $(cat "$n/name" 2>/dev/null)"; 
done
```

办法二：写个小程序调 `drmGetVersion()`

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <xf86drm.h>

int main(int argc, char *argv[]) {
    int fd = open("/dev/dri/card2", O_RDWR | O_CLOEXEC);
    if (fd < 0) return 1;

    drmVersionPtr ver = drmGetVersion(fd);
    if (ver) {
        printf("DRM Driver Name: %s\n", ver->name);
        drmFreeVersion(ver);
    }
    close(fd);
    return 0;
}
```



我们的 `probe_kms -l` 就是办法二：

```
INFO   /dev/dri/card0 driver=<a>   kms=no  connected=no
INFO   /dev/dri/card1 driver=<b>   kms=yes connected=yes
INFO   /dev/dri/card2 driver=vkms  kms=yes connected=yes
```

一眼就能看出该用哪个节点、`-M` 该传什么。

**modetest 的局限**：不同版本的功能差异很大。比如某些版本根本不打印 `IN_FORMATS`，你会看到格式列表但看不到 modifier。
这时候用 `grep -c modifier` 得到 0，并不能说明设备没有 modifier，只能说明这版工具不打印。

**方法论上的教训**：当外部工具不能给你答案时，让**数据自己证明自己**——把原始结构打出来，验证内部一致性。



### 11.3 DRM master：为什么要停显示管理器

**DRM master** 是一个权限概念：**同一时刻，一个 DRM 设备只能有一个 master，只有 master 能做模式设置。**

这是必要的：如果两个进程同时改显示配置，结果是未定义的。

获取和释放：

```c
drmSetMaster(fd);   // 成为 master
drmDropMaster(fd);  // 放弃
drmIsMaster(fd);    // 查询（无副作用）
```

打开设备节点时，如果当前没有 master，你会自动成为 master。所以从裸 tty 直接启动的程序通常不需要显式调用 `drmSetMaster`。

而当 X11 或另一个 Wayland 合成器在跑时，master 被它占着，`drmSetMaster` 会返回 `EBUSY` 或 `EACCES`。

这就是为什么跑这类程序前要先停掉显示管理器（`systemctl stop gdm` / `lightdm` / `sddm`，取决于发行版），或者切到一个没有图形界面的 tty。

需要强调一个边界：

> **枚举资源、读属性不需要 master。任何修改状态的操作需要。**

所以在 X11 跑着的时候，你完全可以打开节点、枚举 connector、打印完整的拓扑和属性表。只有真正要点屏时才会失败。



### 11.4 `lsof`：谁占着设备

```bash
sudo lsof /dev/dri/cardN

# 例如
fan@fan-pc:~$ sudo lsof /dev/dri/card2
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
X       34711 root  mem    CHR  226,2           528 /dev/dri/card2
X       34711 root   13u   CHR  226,2      0t0  528 /dev/dri/card2
X       34711 root   18u   CHR  226,2      0t0  528 /dev/dri/card2
```

列出所有打开这个节点的进程。排查"为什么拿不到 master"时的第一步。`COMMAND` 就是正在独占 master 的进程（`X` 是 `Xorg`）

注意：**打开了不等于是 master**。很多进程会打开 DRM 节点做查询而不抢 master。

> 常见后缀对比：`r` = 只读 Read-only，`w` = 只写 Write-only，`u` = 读写 Read and Write



### 11.5 内核的 DRM 调试日志

DRM 子系统有一个位掩码控制的调试开关：

```bash
# 打开（输出量极大，谨慎）
echo 0x1ff | sudo tee /sys/module/drm/parameters/debug
# 某些厂商可以自定义 flag bit, 例如
echo 0x5ff | sudo tee /sys/module/drm/parameters/debug

# 关闭
echo 0 | sudo tee /sys/module/drm/parameters/debug

# 看输出
sudo dmesg -w
```

位的含义：

| **位值（Hex）** | **内核宏定义**  | **打印的调试内容**                                           |
| --------------- | --------------- | ------------------------------------------------------------ |
| **`0x01`**      | `DRM_UT_CORE`   | DRM 核心层基础操作（设备分配、注销、IOCTL 基础逻辑）         |
| **`0x02`**      | `DRM_UT_DRIVER` | 具体 GPU/显示驱动内部的私有调试日志                          |
| **`0x04`**      | `DRM_UT_KMS`    | 模式设置（Kernel Mode Setting，KMS）时序、连接器（Connector）探测、EDID 解析 |
| **`0x08`**      | `DRM_UT_PRIME`  | 跨设备内存共享与 DMA 缓冲区（DMA-BUF / PRIME）导出与导入     |
| **`0x10`**      | `DRM_UT_ATOMIC` | 原子状态提交（Atomic Commit）、`.atomic_check()` 校验与硬件配置流程 |
| **`0x20`**      | `DRM_UT_VBL`    | 垂直空白期（Vertical Blanking Interval，VBlank）中断与调度时间戳 |
| **`0x40`**      | `DRM_UT_STATE`  | 原子管道状态（Atomic State）详细转储与对象引用计数追踪       |
| **`0x80`**      | `DRM_UT_LEASE`  | DRM 租约管理（DRM Lease，常用于 VR 设备独占渲染管道）        |
| **`0x100`**     | `DRM_UT_DP`     | DisplayPort（DP）链路训练（Link Training）、AUX 读写与多流传输（Multi-Stream Transport，MST） |

排查 atomic 提交被拒时，`0x14`（KMS | ATOMIC）通常就够了，输出量比 `0x1ff` 小很多。

内核会打出它收到的每一个属性和校验失败的原因，和我们自己 dump 的请求逐条对照，很快能定位。

**注意**：这个日志的输出量确实很大，1080p@60 跑起来会刷满 dmesg 缓冲区。只在需要时短暂打开。



### 11.6 debugfs 与 CRC 校验

如果内核开了 `CONFIG_DEBUG_FS`，会有：

```bash
/sys/kernel/debug/dri/<设备号>/
    ├── crtc-0/crc/          ← 可以读出每帧的 CRC 校验值
    ├── state                ← 当前的完整 atomic 状态
    └── ...
```

`crc` 那个接口非常有用：它让你能**自动化验证画面内容是否正确**，不需要人眼看屏幕。这是 KMS 驱动测试套件（IGT）的主要手段之一。

`state` 可以直接看到内核当前的完整 atomic 状态，和你以为你设置的对照。

如果内核没开 `CONFIG_DEBUG_FS`，这个目录不存在，这条路走不通。



### 11.7 VKMS：虚拟 KMS 设备

```bash
sudo modprobe vkms
```

**VKMS**（Virtual KMS）是内核里的一个虚拟显示驱动。它没有真实硬件，用软件定时器模拟 VBlank，把"扫描输出"写到内存里。

它的价值在于：

- **不需要真实硬件**就能开发和测试 KMS 代码
- **能力极其有限**：通常只有 1 个 CRTC、1 个 primary plane、只支持 XR24、没有 modifier、没有 cursor plane

第二点看起来是缺点，其实是最大的优点：

> **VKMS 是通用性的试金石。**
>
> 如果你的代码能在"只有 1 个 primary plane / 只有 XR24 / 无 modifier"的设备上跑通，就证明它没有硬编码任何厂商假设。

我们的验收标准是**双环境通过**：

```
VKMS 通过、真硬件不通过  →  大概率是驱动问题
VKMS 不通过、真硬件通过  →  代码有 vendor 假设
```

两边对照，能把"我的代码错了"和"驱动没实现"分开。这在对接一个还在开发中的驱动时特别重要。否则每个问题都要花大量时间才能定位到底是谁的锅。



### 11.8 EDID 的解析

想知道显示器到底报告了什么：

```bash
# 读原始 EDID
sudo cat /sys/class/drm/card0-HDMI-A-1/edid > /tmp/edid.bin

# 解析（需要 edid-decode 工具）
edid-decode /tmp/edid.bin
```

输出包括厂商、型号、物理尺寸、支持的所有时序、色域信息等。

排查"为什么这个分辨率不可用"时会用到。



### 11.9 常见故障现象与排查方向

把前面所有内容组织成一张对照表。遇到问题时从这里开始。

| 现象 | 可能原因 | 验证方法 |
| --- | --- | --- |
| 屏幕全黑，但所有 ioctl 都成功 | 选中了 writeback connector | 检查 connector 的 type，跳过 `DRM_MODE_CONNECTOR_WRITEBACK` |
| 屏幕全黑，`ACTIVE=1` 已设置 | 没设 `MODE_ID`，或 blob 已被销毁 | dump 请求确认 `MODE_ID != 0`；确认 blob 生命周期覆盖 commit |
| 提交返回 `EINVAL`，找不到原因 | 属性值非法 / plane 不属于该 CRTC | dump 请求 + 属性级定位；打开 `drm.debug=0x14` 看内核日志 |
| 提交返回 `EINVAL`，只在改 mode 时 | 忘了 `ALLOW_MODESET` | 检查 commit flags |
| 提交返回 `EACCES` / `EPERM` | 不是 DRM master | `drmIsMaster()`；`lsof /dev/dri/cardN` |
| 提交返回 `EBUSY` | 上一次提交还没完成，或 CRTC 状态残留 | 确认收到了上一帧的 flip 事件；改用无条件完整 modeset |
| 提交返回 `ENOSPC` | 超出硬件资源（带宽、plane 数） | 减少 plane 数量或降低分辨率再试 |
| 画面花屏、斜纹 | 用 `width*4` 而不是 `pitch` 做行偏移 | 打印驱动返回的 pitch，对比 `width*4` |
| 颜色 R/B 互换 | 混淆了 `XRGB` 和 `XBGR` | 画彩条测试，检查 fourcc |
| 画面偏灰 / 对比度不对 | YUV range 设错（limited vs full） | 检查 plane 的 `COLOR_RANGE` 属性 |
| 视频颜色偏绿/偏紫 | YUV 色彩空间设错（601 vs 709） | 检查 `COLOR_ENCODING` 属性 |
| 半透明区域颜色不对 | alpha 预乘模式设错 | 检查 `pixel blend mode` 属性 |
| 撕裂 | 单缓冲，或用了 async page flip | 确认至少双缓冲，确认没带 ASYNC 标志 |
| 帧率是刷新率的一半 | 渲染超时错过了 VBlank | 看 `sequence` 的跳变；缩短渲染时间或加缓冲 |
| 帧间隔忽长忽短 | 时间戳是 `CLOCK_REALTIME` 被 NTP 调整 | 检查 `DRM_CAP_TIMESTAMP_MONOTONIC` |
| 屏幕闪烁 / 出现横条 | 显示带宽不够，FIFO 欠载 | `dmesg` 找 `underrun`；降低分辨率或减少 plane |
| `addfb2` 返回 `EINVAL` | modifier 不被支持，或走错了 API 路径 | 降级到不带 modifier 的 `AddFB2` 试试 |
| 只看到 overlay plane，没有 primary | 忘了设 `UNIVERSAL_PLANES` | 检查 `drmSetClientCap` 的返回值 |
| 找不到 writeback connector | 忘了设 `WRITEBACK_CONNECTORS` | 同上 |
| 枚举很慢（几百毫秒） | 用了强制探测版本的 connector 查询 | 快速扫描改用 `drmModeGetConnectorCurrent` |
| 程序退出后屏幕黑掉不恢复 | 没有正确 teardown | 退出时显式 disable 所有 plane 和 CRTC |
| 热插拔后崩溃 | 用了失效的资源快照指针 | 引入 generation 校验 |

**一个通用的排查顺序**：

```
1. 现象是"完全没反应"还是"有反应但不对"？
     完全没反应 → 检查 master、检查 commit 返回值
     有反应但不对 → 检查格式、几何、颜色属性

2. ioctl 返回什么 errno？
     EACCES/EPERM → 权限 / master
     EINVAL       → 参数问题，用属性级定位
     EBUSY        → 时序 / 状态残留
     ENOSPC       → 硬件资源不足

3. 打开内核日志对照
     echo 0x14 > /sys/module/drm/parameters/debug
     内核会打出它收到的每个属性和拒绝的原因

4. 用最小配置二分
     只开一个 plane、用最低分辨率、用 LINEAR modifier
     能过就往上加，直到复现
```



### 11.10 为什么要有一个"虚拟设备"做对照

前面提过 VKMS，这里强调一下方法论上的价值。

在只有一个环境的情况下，遇到问题你无法区分：

- 是我的代码写错了？
- 还是这个驱动没实现 / 实现有 bug？

有了第二个**已知正确的参考环境**，这个问题就变得可判定：

```
参考环境通过、目标环境不通过  →  指向驱动
参考环境不通过、目标环境通过  →  指向代码里的平台假设
两边都不通过                →  指向代码里的通用逻辑
两边都通过                  →  可以往下走了
```

VKMS 特别适合当参考环境，因为它**能力极其贫瘠**：通常只有 1 个 CRTC、1 个 primary plane、只支持 XR24、没有 modifier、没有 cursor plane。

这个"贫瘠"就是它的价值：能在 VKMS 上跑通，说明代码没有硬编码任何厂商假设、没有假设 plane 数量、没有假设格式可用。

**推广一下这个思路**：任何做硬件对接的项目，都应该尽早找到一个"最小能力"的参考实现。它不能验证功能，但能验证通用性。



## 十二、动手：最小点屏程序的骨架

现在把所有概念串成代码。以下是完整流程的伪码，每一步都对应前面讲过的概念。

### 12.1 阶段一：打开设备并声明能力

```python
# 1. 找到有 KMS 资源的节点
for path in sorted(glob("/dev/dri/card*")):
    fd = open(path, O_RDWR | O_CLOEXEC)
    if fd < 0: continue                 # 权限不足是常态

    version = drmGetVersion(fd)         # 拿 DRM 驱动名，用于日志和匹配

    res = drmModeGetResources(fd)
    if res == NULL: continue            # 没有 KMS，跳过

    # 用 GetConnectorCurrent（读缓存）而不是 GetConnector（强制探测），
    # 扫全系统时前者快几个数量级
    for connector_id in res.connectors:
        conn = drmModeGetConnectorCurrent(fd, connector_id)
        if conn.status == CONNECTED:
            found = path
            break

# 2. 声明客户端能力
#
# 顺序有讲究：先 UNIVERSAL_PLANES 再 ATOMIC。
# 没设 UNIVERSAL_PLANES 之前，drmModeGetPlaneResources 只返回 overlay plane，
# primary 和 cursor 是隐藏的（legacy 行为）。
drmSetClientCap(fd, DRM_CLIENT_CAP_UNIVERSAL_PLANES, 1)
drmSetClientCap(fd, DRM_CLIENT_CAP_ATOMIC, 1)
drmSetClientCap(fd, DRM_CLIENT_CAP_WRITEBACK_CONNECTORS, 1)   # 可选

# 3. 探测内核能力
for cap in [DUMB_BUFFER, PRIME, ADDFB2_MODIFIERS, TIMESTAMP_MONOTONIC,
            SYNCOBJ, SYNCOBJ_TIMELINE, CURSOR_WIDTH, CURSOR_HEIGHT, ...]:
    drmGetCap(fd, cap, &value)
    记录结果
```

关于 `drmGetCap` 有个细节：**返回非 0 不代表"不支持"，而是"内核不认识这个 cap"**。老内核对新加的 cap 返回 `EINVAL`。

两种情况都当 false，但日志要区分开，"驱动说不支持"和"内核太老不认识"的排查方向完全不同。



### 12.2 阶段二：枚举资源

```python
res = drmModeGetResources(fd)

# CRTC —— 注意这里建立 index 到 id 的映射
for i, crtc_id in enumerate(res.crtcs):
    crtc.id    = crtc_id
    crtc.index = i                       # ← possible_crtcs 位图用的是这个 i
    crtc.props = query_properties(fd, crtc_id, DRM_MODE_OBJECT_CRTC)
    crtc.prop_ids = resolve(crtc.props)  # 解析出 MODE_ID / ACTIVE / ... 的 id

# Encoder
for encoder_id in res.encoders:
    enc = drmModeGetEncoder(fd, encoder_id)
    encoder.possible_crtcs = enc.possible_crtcs   # 位图，存原值

# Connector —— 这里用强制探测版本，要拿准确的模式列表
for connector_id in res.connectors:
    conn = drmModeGetConnector(fd, connector_id)   # 会阻塞，慢
    connector.name = f"{type_name(conn.type)}-{conn.type_id}"   # "HDMI-A-1"
    connector.modes = conn.modes                  # 逐个拷贝 drmModeModeInfo
    connector.encoders = conn.encoders
    connector.props = query_properties(...)

# Plane —— 注意要在设了 UNIVERSAL_PLANES 之后
plane_res = drmModeGetPlaneResources(fd)
for plane_id in plane_res.planes:
    plane = drmModeGetPlane(fd, plane_id)
    p.possible_crtcs = plane.possible_crtcs
    p.props = query_properties(...)
    p.type  = p.props["type"]              # Primary / Overlay / Cursor

    # 格式列表：优先 IN_FORMATS（带 modifier）
    if p.props has "IN_FORMATS":
        blob = drmModeGetPropertyBlob(fd, p.props["IN_FORMATS"])
        p.formats = parse_in_formats(blob)
    else:
        # 退回裸格式列表，modifier 记 INVALID（不是 LINEAR！）
        for fmt in plane.formats:
            p.formats.append((fmt, MODIFIER_INVALID))
```



### 12.3 阶段三：拓扑匹配

这是最容易写错的一步。

```python
# 1. 选 connector
for conn in connectors:
    if not conn.connected:          continue
    if conn.is_writeback:           continue    # ← 必须跳过
    if conn.modes.empty():          continue
    chosen_connector = conn
    break

# 2. 选 mode
mode = chosen_connector.preferred_mode()   # 有 PREFERRED 标记的那个
if mode == NULL:
    mode = chosen_connector.modes[0]       # 内核按偏好降序排列

# 3. 选 CRTC —— 真正遍历 possible_crtcs 位图
chosen_crtc = NONE
for encoder_id in chosen_connector.encoders:
    enc = lookup_encoder(encoder_id)

    for crtc in crtcs:
        # 用 index 而不是 id 去测试位图！
        if not (enc.possible_crtcs & (1 << crtc.index)):
            continue

        # 检查有没有被别的 connector 占用
        if any(other.current_crtc == crtc.id for other in connectors
               if other != chosen_connector and other.connected):
            continue

        chosen_crtc = crtc
        break
    if chosen_crtc != NONE: break

# 4. 选 primary plane
for plane in planes:
    if plane.type != PRIMARY: continue
    if not (plane.possible_crtcs & (1 << chosen_crtc.index)): continue
    chosen_plane = plane
    break
```

每一步失败都应该给出**说清楚原因**的错误，而不是一个笼统的"找不到输出"。比如：

```
no CRTC in the possible_crtcs bitmask of HDMI-A-1's 1 encoder(s) is available
```

而且每个被跳过的候选都应该有 DEBUG 级别的日志说明为什么跳过：

```
DBG skip conn#77 (Writeback-1): writeback connector
DBG skip conn#135 (eDP-1): disconnected
```

这样出问题时不用猜。



### 12.4 阶段四：分配 buffer 并做模式设置

```python
# 分配 N 个 dumb buffer（N >= 2）
for i in 0..N-1:
    buffers[i] = create_dumb_buffer(fd, mode.width, mode.height, XR24)
    # 内部：CREATE_DUMB -> MAP_DUMB -> mmap -> AddFB2

# 先画第一帧，否则模式设置后会闪一下未初始化的显存
draw_frame(buffers[0], frame=0)

# 创建模式 blob（必须活到 commit 返回之后）
mode_blob = CreatePropertyBlob(fd, &mode, sizeof(mode))

# 构造 atomic 请求
req = AtomicAlloc()
AddProperty(req, connector.id, connector.prop_ids.crtc_id, crtc.id)
AddProperty(req, crtc.id,      crtc.prop_ids.mode_id,      mode_blob)
AddProperty(req, crtc.id,      crtc.prop_ids.active,       1)
AddProperty(req, plane.id,     plane.prop_ids.fb_id,       buffers[0].fb_id)
AddProperty(req, plane.id,     plane.prop_ids.crtc_id,     crtc.id)
AddProperty(req, plane.id,     plane.prop_ids.src_x,       0)
AddProperty(req, plane.id,     plane.prop_ids.src_y,       0)
AddProperty(req, plane.id,     plane.prop_ids.src_w,       width  << 16)
AddProperty(req, plane.id,     plane.prop_ids.src_h,       height << 16)
AddProperty(req, plane.id,     plane.prop_ids.crtc_x,      0)
AddProperty(req, plane.id,     plane.prop_ids.crtc_y,      0)
AddProperty(req, plane.id,     plane.prop_ids.crtc_w,      width)
AddProperty(req, plane.id,     plane.prop_ids.crtc_h,      height)

# 先试探
if AtomicCommit(fd, req, TEST_ONLY | ALLOW_MODESET, NULL) != 0:
    dump(req)                        # 打印完整请求
    bisect_rejection(req)            # 逐条剔除定位
    fail

# 真提交
AtomicCommit(fd, req, ALLOW_MODESET, NULL)
```

**关于"无条件完整模式设置"这个策略**，值得单独说明。

你可能会想：能不能先读一下当前状态，只改需要改的部分？答案是**不要这么做**。

接管一个别人（X11、上一个合成器、bootloader 的 splash 画面）留下的 KMS 状态时，增量修改的行为是不可预测的：你不知道对方留下了什么，也不知道驱动内部的状态机处于什么位置。

**正确的做法是无条件下发一次完整配置**，显式设置所有属性，不读当前状态、不做增量、不假设 CRTC 是干净的。

这条策略在实践中反复被验证：接管一个不干净的 KMS 状态时，完整 modeset 能过而增量修改失败的情况并不罕见。

legacy 的 `drmModeSetCrtc` 之所以在很多场景下"看起来更稳"，正是因为它内部强制重设整个 CRTC 状态。用 atomic 时，这份责任要由我们自己承担。



### 12.5 阶段五：帧循环

```python
seal_init_phase()      # 从这里开始，属性查询类 ioctl 不该再增长

frame = 0
while not should_stop:
    buffer = chain.acquire()
    draw_frame(buffer, frame)

    req.reset()                        # 复用，不重新分配
    AddProperty(req, plane.id, plane.prop_ids.fb_id,   buffer.fb_id)
    AddProperty(req, plane.id, plane.prop_ids.crtc_id, crtc.id)
    AddProperty(req, plane.id, ... 几何 ...)

    # 注意：不带 ALLOW_MODESET。稳态下不该发生模式设置，
    # 带上反而会掩盖"配置意外变了"这种问题。
    AtomicCommit(fd, req, NONBLOCK | PAGE_FLIP_EVENT, user_data=frame)
    chain.mark_submitted()

    # 等完成事件。超时给 5 个标称帧时长——正常远用不到，
    # 超了说明内核那边卡住了。
    if poll(fd, timeout_ms) has POLLIN:
        events = read_and_parse(fd)
        for e in events:
            chain.on_flip_complete()
            frame_stats.record(e)
        frame += 1

    check_sealed("frame loop")         # 验证没有热路径 ioctl
```

**`AtomicRequest` 的复用**值得说明。每帧 `AtomicAlloc` 一个新请求是浪费。

libdrm 提供了 `drmModeAtomicSetCursor(req, 0)`，把内部游标退回开头，底层数组容量保留：

```cpp
void AtomicRequest::reset() noexcept {
    if (req_ != nullptr) {
        drmModeAtomicSetCursor(req_, 0);   // 容量保留，不重新分配
    }
    entries_.clear();                       // 只归零 size
}
```

这样整个帧循环只有启动时那一次分配。



### 12.6 阶段六：退出清理

```python
# 一次 atomic 提交完成所有清理
req.reset()

# 关掉这个 CRTC 上的所有 plane，不只是我们用的那个。
# 别的 plane 可能是前一个程序留下的（比如硬件光标），
# 不关掉会挡着后面的进程。
for plane in planes_on(crtc):
    AddProperty(req, plane.id, plane.prop_ids.fb_id,   0)
    AddProperty(req, plane.id, plane.prop_ids.crtc_id, 0)

AddProperty(req, crtc.id, crtc.prop_ids.active,  0)
AddProperty(req, crtc.id, crtc.prop_ids.mode_id, 0)
AddProperty(req, connector.id, connector.prop_ids.crtc_id, 0)

AtomicCommit(fd, req, ALLOW_MODESET, NULL)

# 然后才释放资源，顺序由 RAII 保证：
# request -> framebuffer -> GEM object -> blob -> master -> fd
```



### 12.7 端到端追踪：一次鼠标移动的完整旅程

把这一讲的所有概念串成一条线。假设一个完整的 Wayland 桌面，用户移动了鼠标。

**阶段一：输入**

```
USB 鼠标以 125Hz 上报位移
    ↓
内核 USB HID 驱动解析成 input event
    ↓
写进 /dev/input/eventN
    ↓
合成器的事件循环被 epoll 唤醒
    ↓
libinput 把原始事件转换成带加速曲线的逻辑位移
    ↓
合成器更新光标位置，判断焦点窗口是否变化
```

**阶段二：分发**

```
合成器通过 wl_pointer.motion 事件把坐标发给焦点窗口的客户端
    ↓
（如果光标移出了当前窗口）
    wl_pointer.leave 给旧窗口
    wl_pointer.enter 给新窗口
```

注意合成器**只把事件发给焦点窗口**。这是和 X11 的一个重要区别：X11 下任何客户端都能监听全局输入。

**阶段三：客户端渲染（如果内容需要变）**

```
客户端收到 motion 事件，决定要重绘（比如按钮 hover 高亮）
    ↓
在自己的 buffer 上渲染（GPU 或 CPU）
    ↓
wl_surface.attach(new_buffer)
wl_surface.damage(变化区域)
wl_surface.frame(callback)     ← 请求下一帧的通知
wl_surface.commit()            ← 原子生效
```

**阶段四：合成器决策**

```
合成器收到 commit，更新场景图
    ↓
遍历所有可见 surface，构建这一帧的图层列表
    ↓
【硬件平面调度】
    光标 surface        → 尝试 cursor plane
    全屏不透明的顶层窗口  → 尝试 primary plane 直出
    其余图层            → 标记为需要 GPU 合成
    ↓
构造 atomic 请求
    ↓
TEST_ONLY 试探
    ↓
如果被拒 → 把某个图层挪回 GPU 合成，重试
    ↓
如果需要 GPU 合成 → 用 GLES/Vulkan 把那些图层画到一张纹理
```

**阶段五：提交**

```
drmModeAtomicCommit(fd, req, NONBLOCK | PAGE_FLIP_EVENT, frame_id)
    ↓
内核校验整组配置
    ↓
写硬件寄存器（但硬件会在下一个 VBlank 才真正生效——双缓冲的寄存器组）
    ↓
ioctl 立刻返回（NONBLOCK）
```

**阶段六：硬件**

```
下一个 VBlank 到来
    ↓
显示控制器切换到新的扫描地址
    ↓
产生 VBlank 中断
    ↓
KMD 中断处理程序记录精确时间戳和 sequence
    ↓
投递一个 drm_event 到 DRM fd
```

**阶段七：回环**

```
合成器 poll 到 DRM fd 可读
    ↓
read() 解析出 FlipEvent（时间戳、sequence、user_data）
    ↓
知道：上一帧的 buffer 空出来了
    ↓
通过 wp_presentation_feedback 把精确的出光时间告诉客户端
    ↓
触发所有可见 surface 的 frame callback
    ↓
客户端开始画下一帧
```

**这一整圈就是 UMD ↔ KMD ↔ UMD 的全链路。**



## 十三、工程方法：如何让底层代码可观测

这一节讲的不是显示技术，而是写这类代码的方法论。

### 13.1 底层代码的调试困境

图形底层代码有几个特点，让它比一般代码难调：

1. **失败信息极少**。内核只回一个 `errno`，不说是哪个属性、哪个对象。
2. **失败不一定可见**。多一次 ioctl 只是慢一点；格式解析错了可能只是某些格式用不了；很多 bug 不会崩。
3. **反馈周期长**。要停显示管理器、切 tty、跑程序、看屏幕。
4. **难以单元测试**。依赖真实硬件状态。

所以**可观测性必须是一等公民**，而不是"出问题了再加日志"。



### 13.2 日志：分级 + 结构 + 零成本

三条要求：

**等级过滤必须发生在格式化之前。** 这决定了日志接口必须是宏，不能是函数：

```cpp
#define MW_LOG_AT(level_, ...)                                                \
    do {                                                                      \
        if (static_cast<int>(log_level()) >= static_cast<int>(level_)) {      \
            log_write((level_), __FILE__, __LINE__, fmt(__VA_ARGS__));        \
        }                                                                     \
    } while (0)
```

Trace 级别下每帧会打几十条日志，函数接口做不到"关掉时零开销"——参数求值躲不掉。

**结构化：缩进作用域。** 资源枚举是树形的，平铺的日志读起来很痛苦：

```cpp
class LogIndent {
public:
    LogIndent()  noexcept { ++g_indent; }
    ~LogIndent() noexcept { --g_indent; }
    // 禁止拷贝和移动
};

#define LOG_SCOPE() LogIndent MW_CAT(mw_log_indent_, __LINE__)
```

用起来：

```cpp
LOG_INFO("connector {} '{}'", conn.id, conn.name);
{
    LOG_SCOPE();
    for (const auto& mode : conn.modes) {
        LOG_INFO("{}", describe_mode(mode));
    }
}
```

**一个隐蔽的坑：日志宏会破坏 `errno`。**

考虑这段代码：

```cpp
if (opendir("/dev/dri") == nullptr) {
    LOG_ERROR("cannot open /dev/dri: {}", errno_name(errno));
}
```

看起来没问题，实际打出来的是 `E?`（未知错误码），而 `ENOENT` 明明在表里。

原因：宏展开后，`if` 条件先调 `log_level()`，它首次调用要走 `getenv` / `clock_gettime` 做初始化，**这些调用会改 `errno`**。而日志参数是在 `if` 之后才求值的。

修法有两种：要求每个调用点都先 `const int err = errno;`（不现实），或者让宏保证 `errno` 透明：

```cpp
#define MW_LOG_AT(level_, ...)                                                \
    do {                                                                      \
        const int mw_saved_errno_ = errno;                                    \
        if (static_cast<int>(log_level()) >= static_cast<int>(level_)) {      \
            errno = mw_saved_errno_;          /* 求值参数前还原 */             \
            log_write((level_), __FILE__, __LINE__, fmt(__VA_ARGS__));        \
        }                                                                     \
        errno = mw_saved_errno_;              /* 出宏后还原 */                 \
    } while (0)
```

这类"底层设施本身有副作用"的问题，在写系统编程代码时会反复出现。值得建立一个习惯：**任何可能被放在错误处理路径上的工具，
都要保证不破坏 `errno`。**



### 13.3 ioctl 记账

给每一类 ioctl 记数，用一个宏统一包装：

```cpp
#define MW_DRM_CALL(counter_, call_, ...)                                     \
    ([&]() -> int {                                                           \
        LOG_TRACE("ioctl " #counter_ " <- " __VA_ARGS__);                     \
        const int mw_ret_ = (call_);                                          \
        const int mw_errno_ = errno;                                          \
        ++stats().counter_;                                                   \
        if (mw_ret_ != 0) {                                                   \
            LOG_DEBUG("ioctl " #counter_ " -> ret={} errno={} ({})",          \
                      mw_ret_, mw_errno_, errno_name(mw_errno_));             \
        }                                                                     \
        errno = mw_errno_;      /* 日志不污染调用方看到的 errno */             \
        return mw_ret_;                                                       \
    }())
```

用起来：

```cpp
int ret = MW_DRM_CALL(atomic_commit,
                      drmModeAtomicCommit(fd, req, flags, user_data),
                      "flags={} props={}", to_string(flags), entries_.size());
```

这一个宏同时给了：Trace 级别的入参日志、Debug 级别的失败日志、自动记数、`errno` 保护。

计数器的用途有三个：

**用途一：验证热路径干净。** 前面讲过的密封机制。

**用途二：验证资源配平。** 成对的计数（create/destroy、addfb/rmfb、setmaster/dropmaster）在程序退出时应该相等：

```cpp
void report_leaks_on_exit() noexcept {
    for (const auto& pair : kPairs) {
        uint64_t acquired = stats().*(pair.acquire);
        uint64_t released = stats().*(pair.release);
        if (acquired != released) {
            LOG_WARN("resource leak: {} acquired={} released={} (delta={})",
                     pair.name, acquired, released, acquired - released);
        }
    }
}
```

实测输出：

```
final ioctl counts:
  create_dumb = 2
  destroy_dumb = 2      ← 配平
  add_fb = 2
  rm_fb = 2             ← 配平
  atomic_commit = 602
  read_events = 600
  page_flip_events = 600
all paired kernel resources released cleanly
```

**这个机制自己抓到过一个 bug**：最初它报告 property blob 泄漏了一个。排查发现不是真泄漏——统计函数是在 `main` 调用的辅助函数内部执行的，而 blob 是那个函数的局部变量，此时还没析构。

修法是把统计挪到所有局部对象都析构之后：

```cpp
int main(int argc, char** argv) {
    const int exit_code = run(options);
    // run() 已返回，它的所有局部对象都析构完了。
    // 这时候 create 与 destroy 的计数才应该配平。
    report_leaks_on_exit();
    return exit_code;
}
```

值得注意的是：**误报本身也是有价值的信号**。它逼着我把"资源什么时候真正释放"想清楚了一遍。

**用途三：量化理解系统。** 一次完整的资源枚举花了多少次内核往返？

```
ioctl cost of one full enumeration:
  get_cap=11 set_client_cap=4 get_resources=6 get_plane_resources=1
  get_connector=9 get_encoder=6 get_plane=8 get_properties=16
  get_property=100 get_blob=16 TOTAL=177
```

177 次。这个数字本身就是学习材料——它直观地说明了为什么枚举只能做一次、为什么属性 ID 必须缓存。



### 13.4 用类型系统防呆

这个领域有几类"看起来对但是错"的代码，编译器默认不会拦：

**裸整数 ID 传错位置：**

```cpp
// 危险：编译器无法区分
void configure(uint32_t plane_id, uint32_t crtc_id);
configure(crtc_id, plane_id);   // 参数写反了，编译通过，运行时 EINVAL
```

改成强类型：

```cpp
enum class PlaneId : uint32_t {};
enum class CrtcId  : uint32_t {};

void configure(PlaneId plane, CrtcId crtc);
configure(crtc, plane);   // 编译错误
```

强类型枚举有零运行时开销，但需要给每个类型写 `to_string`（否则日志格式化用不了）。这个代价换来的是一整类 bug 在编译期消失，
而且日志里能带上类型信息：

```
connector = conn#142   crtc = crtc#84   crtc index = [1]   plane = plane#87
```

注意 `CrtcIndex` 打成 `[1]` 而 `CrtcId` 打成 `crtc#84`，视觉上就区分开了，看日志时不会把下标误读成 ID。

**定点数和整数混淆：** 前面讲过的 `SrcRect` / `CrtcRect`。

**位图和 ID 混淆：** `PossibleCrtcs::contains()` 只接受 `CrtcIndex`。

**文件描述符所有权不清：**

```cpp
class UniqueFd {
public:
    explicit UniqueFd(int fd) noexcept;
    ~UniqueFd();
    UniqueFd(UniqueFd&&) noexcept;
    UniqueFd(const UniqueFd&) = delete;

    int get() const noexcept;                 // 借用
    [[nodiscard]] int release() noexcept;     // 转移所有权

    // 故意不提供 operator int()
};
```

**故意不提供隐式转换**。有隐式转换的话，`close(fd)`、`fds.push_back(fd)` 这类"悄悄丢所有权"的写法会编译通过。要传给 libdrm 就显式写 `.get()`，读代码时一眼能看出这是借用。

配套地提供一个非拥有的类型，让函数签名自解释：

```cpp
class BorrowedFd {
public:
    constexpr explicit BorrowedFd(int fd) noexcept;
    constexpr int get() const noexcept;
};

// 签名就说明了：我只是用一下，不负责关
static Result<PropertyMap> query(BorrowedFd fd, uint32_t object_id, uint32_t type);
```

这在 Step 6 会变得极其重要——那时候会有大量的 fence fd 在进程间传递，double close 和泄漏都是灾难。

关于 `close()` 还有一个细节值得知道：

```cpp
void UniqueFd::reset(int fd) noexcept {
    if (fd_ >= 0 && fd_ != fd) {
        // Linux 上 close() 返回 EINTR 时 fd 已经被回收，
        // 重试会关掉别人刚拿到的同号 fd。所以既不重试也不报错。
        ::close(fd_);
    }
    fd_ = fd;
}
```

这是 Linux 特有的语义（POSIX 没有明确规定），写多线程程序时踩过这个坑的人不少。



### 13.5 运行时能力探测，不用 `#ifdef`

一个原则：

> 同一份二进制要能在不同内核版本、不同驱动、不同平台上跑起来，只是走不同的分支。

编译期开关会让"在这台机器上能编过"变成"只能在这台机器上跑"。

具体做法是把所有能力探测收敛到一个结构体：

```cpp
struct DeviceCaps {
    // 阶段 A：drmGetCap / drmSetClientCap，不需要枚举资源
    bool atomic, universal_planes;
    bool dumb_buffer, prime_import, prime_export;
    bool addfb2_modifiers, timestamp_monotonic;
    bool syncobj, syncobj_timeline;

    // 阶段 B：需要真实对象的属性表才能知道
    bool prop_crtc_out_fence_ptr;
    bool prop_plane_in_fence_fd;
    bool prop_plane_in_formats;
    bool prop_plane_zpos;
    // ...
};
```

分两阶段是因为有鸡生蛋问题：`drmGetCap` 不需要枚举资源，但"这个驱动实现了 `OUT_FENCE_PTR` 没有"只能从真实对象的属性表里看。

然后区分**硬性前提**和**可选能力**：

```cpp
Status DeviceCaps::check_minimum() const {
    // 只检查真正没有替代路径的能力
    if (!atomic)            return Err(NoAtomicSupport, ...);
    if (!universal_planes)  return Err(NoUniversalPlanes, ...);
    return Ok();
    // dumb_buffer 之类是"某个阶段需要"，由各阶段自己检查——
    // 否则后面的纯 DMA-BUF 路径会被一个用不到的能力挡住
}
```

这一点在对接**还在开发中的驱动**时特别重要。现在探不到的能力不代表永远没有。所以自检要区分：

- `check`：硬性前提，失败就是 FAIL
- `note`：能力缺失，WARN 但不算失败

驱动补上什么功能，重跑一次就能看见，不用改代码。



### 13.6 让程序自己验证不变量

比人工比对工具输出高效得多。我们真正依赖的不变量只有十几条：

```
PASS  atomic modesetting is available
PASS  universal planes are available
PASS  CrtcId <-> CrtcIndex round-trips for every CRTC
PASS  every CRTC has at least one primary plane
      plane types: 2 primary, 4 overlay, 2 cursor
PASS  hardware cursor plane present
PASS  at least one connected non-writeback connector
PASS  every connected connector has modes and a usable encoder
PASS  pick_output() succeeds
      -> conn#142 crtc#84 [1] plane#87 @ 1920x1080@60.000
PASS  the chosen primary plane supports XR24
PASS  the freshly computed OutputPath validates
```

与其把几百行 dump 和参考工具逐行比对，不如把这些性质直接判定成 PASS / FAIL。退出码 0 全过、2 有失败，可以直接进 CI。

其中"`CrtcId <-> CrtcIndex` 是双射"这一条特别值得强调：这条错了，所有 `possible_crtcs` 匹配都会**静默地**选错 CRTC，症状是很久以后一个莫名其妙的 `EINVAL`。



### 13.7 静态分析的价值

这个项目的编译告警开到近乎苛刻：

```
-Weffc++ -Wconversion -Wsign-conversion -Wold-style-cast
-Wzero-as-null-pointer-constant -Wshadow -Wnon-virtual-dtor
-Woverloaded-virtual -Wcast-qual -Wcast-align ...
```

外加一批直接升级为错误：`-Werror=return-type`、`-Werror=uninitialized`、`-Werror=suggest-override` 等。

两个必须知道的约束：

- **系统头必须用 `-isystem` 而不是 `-I`**。libdrm 的 `fourcc_code()` 宏体里是 C 风格强转，用 `-I` 会被 `-Wold-style-cast` 打中——而那不是我们能改的代码。`-isystem` 让编译器忽略系统头里展开的宏产生的告警。
  
- **`-Wpedantic` 和 GNU 扩展冲突**。如果代码里用了语句表达式（`({ ... })`）之类的 GNU 扩展，`-Wpedantic` 会对每一处报警。

`cppcheck` 也很有价值。它抓到过一个这样的问题：

```cpp
auto first = try_with_modifiers(...);
if (first) return first;
// ...
return first;    // cppcheck: identical condition and return expression
```

cppcheck 报的是"这个返回值恒为假"。顺着看下去，发现底下藏着一个真 bug：判断"要不要降级"用的是 `errno_of(first.error())`，
但 `first` 返回的是**语义域**的错误码，`errno_of` 恒返回 0，**降级路径永远不会触发**。

这个 bug 光看代码很难发现：两个函数分别都对，错在**跨函数的错误域假设**上。修法是把下发 ioctl 那层拆成返回 `int errno` 的内部函数，两个公开接口共用。

**教训**：静态分析工具报的位置未必是问题所在，但它指出的"这里逻辑上有冗余"往往是更深问题的表象。



### 13.8 构建变体要隔离

一个小但会浪费很多时间的坑：

```bash
make SANITIZE=1   # 编译出插桩过的 .o
make              # 重新编译改动的文件，没插桩
# 链接时插桩和没插桩的 .o 混在一起
```

报错是 `relocation against __asan_option_detect_stack_use_after_return`，完全看不出根因。

修法是把构建变体编进输出目录：

```makefile
O := build/$(BUILD)$(if $(filter 1,$(SANITIZE)),-asan)
```

### 14.2 几条值得记住的经验

1. **物理约束决定软件设计。** VBlank 之所以重要，是因为 CRT 的电子束需要时间回扫。今天没有 CRT 了，但这个时间窗口仍然是唯一安全的切换时机。
   
2. **名字有历史包袱，但概念是清晰的。** CRTC 不是阴极射线管控制器，它是一路显示输出的时序引擎。
   
3. **不要假设拓扑是全连接的。** `possible_crtcs` 位图不是摆设。

4. **区分"能力不存在"和"探测方式不对"。** syncobj 在 KMS 节点上没有，不代表这个平台不支持——它在 render node 上。
   
5. **让数据自己证明自己。** 外部工具不可用时，打印原始结构 + 验证内部一致性，比猜测有效得多。
   
6. **可观测性是设计的一部分，不是补丁。** ioctl 记账、密封检查、请求 dump、属性级定位，这些在写第一行功能代码之前就该规划好。
   
7. **用类型系统表达约束。** 强类型 ID、定点数封装、fd 所有权，都是把运行时错误提前到编译期。



### 14.3 已经能做什么

到这一讲结束，我们的代码可以：

- 枚举系统里所有 DRM 设备，识别哪个有 KMS 能力
- 完整解析 KMS 资源拓扑，包括 `possible_crtcs` 位图和 `IN_FORMATS` blob
- 运行时探测几十项能力，区分硬性前提和可选功能
- 正确地做拓扑匹配，选出一条可用的输出通路
- 分配 dumb buffer，用 CPU 绘制
- 用纯 atomic 接口做完整的模式设置
- 以 60fps 稳定翻页，零丢帧
- 精确统计帧间隔和丢帧
- 退出时干净地释放所有资源

在两个完全不同的环境（虚拟 KMS 设备和真实硬件）上都验证通过。



### 14.4 还不能做什么

- **CPU 绘制太慢。** 1080p 每帧 8 MiB 的 write-combining 写入，在弱平台上就要好几毫秒。需要 GPU。
- **只能用线性排布。** dumb buffer 不支持 tiling，GPU 读它效率很低。
- **只有一个平面。** 没有利用硬件的多平面合成能力。
- **单进程。** 没有任何跨进程的 buffer 共享。
- **隐式同步。** 没有精确的时序控制。

## 附录 D：几个常见的误解

写这一讲的过程中，发现有些说法在网上流传很广但不准确。列出来避免误导。

**误解一："DRM 就是显卡驱动"**

不准确。DRM 是内核里的一个**框架**，厂商驱动（i915、amdgpu、nouveau 等）在这个框架里实现自己的部分。DRM 提供了统一的对象模型、统一的 UAPI、以及大量共享的辅助代码（模式解析、EDID 解析、atomic 状态机等）。

而且渲染驱动的大头在**用户态**（Mesa），内核里的部分主要做内存管理、命令提交和安全校验。



**误解二："framebuffer 就是 /dev/fb0"**

`/dev/fb0` 是 **fbdev** 子系统，比 DRM 更古老，现在只作为兼容层存在。它没有 plane、没有 atomic、没有多缓冲、没有显式同步的概念。

现代显示编程应该用 DRM/KMS。网上大量的"Linux 显示编程入门"教的是 fbdev，那些内容学了对理解现代栈没有帮助。



**误解三："Wayland 比 X11 快"**

这个说法太笼统。Wayland 的优势主要在于：

- **少一次进程往返和一次拷贝**（合成器直接拥有硬件）
- **原子的状态更新**（不会看到中间态，视觉上更"干净"）
- **更好的安全隔离**

但"快"要看指标。在某些场景下（比如大量小窗口的 2D 绘图），X11 的服务端绘图理论上能更省。实际差异更多来自实现质量而不是协议设计。

Wayland 真正的价值是**架构上更简单、更可预测**，而不是绝对性能。



**误解四："atomic 就是为了原子性"**

原子性只是其中一个好处，而且不是最重要的。更重要的是：

- **可预先验证**（TEST_ONLY）——这是硬件平面调度的基础
- **可扩展**（新功能 = 新属性，不改 UAPI）
- **状态完整**（一次提交描述完整配置，不依赖历史状态）

如果只是要原子性，legacy 接口加个"批量提交"就够了。



**误解五："modifier 就是 tiling 格式"**

modifier 描述的是"内存排布"，tiling 只是其中一类。还包括压缩方案、元数据平面的布局、以及一些格式变体。

而且从合成器的角度，**它就是一个不透明的 token**，不该被解释成任何具体的东西。

**误解六："VBlank 是显示器在等"**

VBlank 是**扫描过程**里的一段时间，源于 CRT 的电子束回扫。今天的 LCD/OLED 没有电子束，但整个时序体系保留了下来，因为接口协议和显示器控制器都是按这个模型设计的。

它现在的作用是：给同步信号、给音频/元数据留传输空间、以及作为唯一安全的地址切换窗口。



**误解七："双缓冲就不会撕裂"**

双缓冲**加上在 VBlank 时切换**才不会撕裂。如果你用双缓冲但随时切换（async page flip），照样撕裂。

反过来，单缓冲加上"只在 VBlank 期间写"理论上也不撕裂，但那个时间窗口太短，实践中做不到。



**误解八："帧率 60fps 就是每 16.67ms 一帧"**

只有在 `vrefresh` 恰好是 60 且时钟精确时才成立。实际的 HDMI 1080p60 是 `148500 / (2200 × 1125) = 60.0000 Hz`，
但 1080p59.94（NTSC 兼容）是 `148352 / (2200 × 1125) = 59.9401 Hz`，帧时长 16.6833ms。

差 0.1% 听起来很小，但一分钟就是 3600 帧里差 3.6 帧。做 A/V 同步时这个误差会累积成可听见的音画不同步。

所以：**永远用 `clock / (htotal × vtotal)` 算，不要用 `vrefresh`。**
